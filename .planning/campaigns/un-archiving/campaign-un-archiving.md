# Campaign: Un-archiving for identities, roles, and apps

**Opened:** 2026-09-29
**Status:** in_progress
**Workspace:** /home/ubuntu/fleet/identities/cypher-box-maintainer-2/workspace/skynet/.planning/campaigns/un-archiving/

## Concept

Three of Skynet's persistent objects — identities, roles, and apps — can be archived by the user (right-click → Archive) and by agents (self-triggered for identities via `/id archive`, sentinel-drop patterns for others). Archive today is a one-way trip: the object moves to an archive folder alongside the live one (`~/fleet/identities-archive/`, `~/fleet/roles-archive/`, `~/fleet/apps-archive/`) and there is no un-archive gesture. Each of the three archive route files in the Skynet backend explicitly notes "no un-archive" as a design decision.

This campaign reverses that decision consistently. Un-archive becomes a first-class, symmetric-with-archive gesture across all three types — same sentinel pattern archive already uses (an `.unarchive-requested` empty file dropped inside the archived folder), the same agent-supervisor doing the reverse work on its next reconcile tick, and the same user + agent surfaces available for triggering it. The gesture is available in the app UI (a discoverable affordance the user can find without knowing which of the three types the object is) and via disk-side sentinel drops for agents (paralleling how they already do archive).

For apps specifically, the campaign also consolidates architecture: today's app archive is sentinel + supervisor + `archive-app.sh` script (in the app-development skill) split across three places; the un-archive counterpart moves `restore-app.sh`'s logic INTO the supervisor so the supervisor becomes the single authority for un-archiving an app, and the standalone restore script is obsoleted. The archive script's split is left as-is for now (not in this scope), but the un-archive side lands cleanly consolidated.

Restore semantics differ by type:

- **Identity** un-archive is deliberately low-impact. Matrix account is reactivated and the folder is moved back so the identity is visible in the sidebar again, but the harness is NOT auto-spawned. The un-archive path drops a dormancy signal on the identity so the supervisor leaves the claude process alone; the identity wakes on the usual triggers (a relay DM, a scheduled wake-up, or the user opening the conversation). This means un-archiving doesn't accidentally re-start work; it's the reverse of the archive gesture, not a "resume" gesture.
- **Role** un-archive restores the role folder so it becomes available for new (or un-archived) identities. It does NOT cascade to un-archive the identities that were retired alongside during archive — those are separate un-archives.
- **App** un-archive restores the folder and re-registers the app with the supervisor so it appears in the sidebar and is servable.

**Cross-object dependency.** An identity depends on its role existing. If the user tries to un-archive an identity whose role is still archived, the un-archive is blocked — the backend refuses the request and the frontend surfaces a clear reason ("un-archive role X first, then this identity can be un-archived"). Whether the frontend goes further and offers to un-archive the role in the same gesture is a shape 2 discussion.

## Success criteria

- A user can un-archive an identity, a role, or an app from the Skynet UI. Exact surface(s) — one unified affordance across all three types vs per-type placements — is a shape 2 decision; the load-bearing criterion here is that all three types are un-archivable through UI.
- Un-archiving an identity reactivates its Matrix account and moves the folder from archive back to live, but leaves the harness dormant — a dormancy signal on the identity keeps the supervisor from auto-spawning claude. The identity is visible and reachable at its original mxid; it wakes on the usual triggers (relay DM, scheduled wake-up, user opening the conversation).
- Un-archiving a role restores the role folder from archive back to live, making the role available for new identities. Identities that were retired alongside the role during archive are NOT auto-restored — they remain archived until separately un-archived.
- Attempting to un-archive an identity whose role is still archived is blocked at the backend (returns a clear error identifying the missing role); the frontend surfaces the reason and directs the user to un-archive the role first. Whether the frontend also offers a "un-archive the role too, then this identity" convenience path is a shape 2 discussion.
- Un-archiving an app restores the folder and re-registers the app with the supervisor so it appears in the sidebar and is servable. The logic for this lives inside the supervisor (not in a shell script in a skill); the previous `restore-app.sh` in the `app-development` skill is obsoleted by this campaign.
- Agents un-archive by dropping `.unarchive-requested` inside the target's archive folder — the same disk gesture pattern they already use for archive, in the reverse direction. No new slash-command is added.
- The id skill teaches every agent about (a) the user-facing affordance in the app (so agents can point users at it when asked) and (b) the sentinel-drop pattern (so agents can un-archive on the user's behalf when asked).

## Shapes

- **[declared] shape-unarchive-host-side** — the host-side half: agent-supervisor reconcile-tick scanners for each of the three types. For identities the scanner reactivates the Matrix account via the admin user-update endpoint (fleet admin token, deactivated=false, password preserved), mints a fresh access token via the admin login-as-user endpoint and rewrites `relay.json` in the archive folder to replace the stale token, then — unless the archive folder carries `.no-dormancy` from before archive (in which case the always-on intent is preserved) — writes `.dormant` inside the archive folder so the reconcile loop leaves the harness alone after mv. Then it deletes `.unarchive-requested` and mv's archive→live. For roles it's a folder move (no cascade — identities retired alongside the role stay retired until independently un-archived). For apps it's the moved-into-supervisor version of what `restore-app.sh` did (port collision check under the create-app flock, folder move, unit file re-install, daemon-reload, enable+start). The identity scanner enforces the roles-must-all-be-live precondition — parses the archived identity's `role:` frontmatter (handles scalar + flow-list + block-list YAML shapes via Python inline), refuses with a LOUD log naming missing role(s). Name collision (live object already exists at the target slug/key/name) refuses at every type — sentinel deleted, LOUD log, no clobber. `restore-app.sh` is removed from the `app-development` skill folder and its entry stripped from the substrate distributor's catalog. Retry semantics mirror archive: transient failures leave the sentinel for next tick, permanent failures delete + log. Verification of end-to-end Matrix reactivation behavior (does the account come back cleanly with rooms and E2EE state intact, or does something break in a way that needs a compensating flow?) is a load-bearing task within this shape — it is the campaign's biggest technical unknown; if room memberships are lost, a compensating force-join step (via the admin `/join/{roomId}` API with `user_id=<mxid>`) folds into the identity scanner.

- **[declared] shape-unarchive-frontend-backend** — the frontend + backend half. Three new POST endpoints paralleling the archive routes (identities, roles, apps), each dropping `.unarchive-requested` inside the corresponding **archive** folder (not the live folder — the live folder doesn't exist yet at un-archive time). Requires per-type primitive extensions so the existing per-*-file writes can target the archive tree rather than the live tree. Endpoint-side fast-path preconditions mirror the host-side scanner's (archive-exists, name-collision, all-roles-live for identities) so the frontend gets a structured 409 with `missingRoles: [...]` before the supervisor tick — the scanner remains authoritative but the endpoint's precheck gives the frontend a clean immediate reason. The user-facing surface where archived items are visible and un-archivable (exact placement decided at the start of this shape — leading candidates: a unified "Archived" drawer/modal accessible from a menu item, or per-type sections within existing type modals like the drama-masks roles modal). Edits to the id-skill's "The app's user interface" section documenting the new affordance (so agents can point users at it correctly), and edits to the archive-related sections adding the sentinel-drop pattern for un-archive (paralleling how the archive sentinel-drops are already described). Standing distribution rule applies (edit substrate source, never hand-edit the distributed copy).

## Open questions

- **[RESOLVED, shape 1 spike, 2026-09-30] Matrix reactivation fidelity.** Live-fleet spike on a throwaway `@unarchive-fidelity-test-*` account confirmed: account reactivates cleanly (whoami works, fresh token /syncs 200), but room memberships do NOT survive `deactivate erase=true → PUT deactivated=false`. No admin API lists historical room memberships for a deactivated account, so recovery is impossible without a retire-time snapshot. Shape 1 landed with the accepted caveat (option B): un-archive reactivates + moves folder + refreshes token; rooms are not restored; new DMs work naturally via Matrix's auto-create-DM-room behavior. Rejoin path deferred to a follow-up shape if peer stale-cache trouble becomes user-visible. Full spike results + rationale in shape-unarchive-host-side.md § Matrix fidelity spike.
- **What if the workspace was cleaned during archive?** Identity archive cleans safely-cloneable workspace repos (git repos with a remote). Un-archive moves the folder back but doesn't re-clone. Is that the right behavior — the identity comes back with an empty workspace and re-clones on next task — or should the un-archive path also re-clone anything the identity file records as its working repo? Answer probably lives in shape 1.
- **UI surface placement.** Where exactly does the un-archive affordance live? Unified "Archived" drawer with tabs by type, per-type integration into each type's existing modal (roles modal already exists via drama-masks; apps and identities would each need a new archived-view surface), or a new sidebar section. Deferred to shape 2's discussion beat.
- **Convenience path for orphan-identity un-archive.** When a user tries to un-archive an identity whose role is still archived, does the UI just refuse-with-reason, or offer a one-click "un-archive the role first, then this identity"? The former is safer (surfaces the dependency without doing anything the user didn't ask for); the latter is friendlier. The user wanted this discussed rather than pre-decided. Shape 2 topic.
- **Dormancy signal mechanism.** The un-archive path drops a dormancy signal so the supervisor doesn't auto-spawn claude. Whether that's an inverse of the existing `.no-dormancy` sentinel (some new `.dormant-hold` file), or a one-shot `.no-auto-start` the supervisor consumes on first wake, or an existing supervisor knob I haven't found yet — decided during shape 1. The invariant is: un-archive doesn't accidentally start work.
- **Should `/id unarchive <name>` exist as an agent slash-command?** User's call so far: no — agents just drop sentinels, same pattern as archive from an agent's peer perspective. Left here as a "decided-no" pointer so the shape 2 id-skill edits know not to add it.
