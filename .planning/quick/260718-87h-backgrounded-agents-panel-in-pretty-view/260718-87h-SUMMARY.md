# Patch #61: Backgrounded-Agents Panel in Pretty View

## Overview

Adds a sibling panel above the ComposeBox (below HarnessTasksPanel
when both are visible) that displays currently-running
`Agent{run_in_background:true}` subagent invocations for the tailed
Claude Code session. Ashley's motivation: while coordinating N
parallel Claude sessions, backgrounded subagents run silently until
the assistant surfaces their result — no visible "is that Explore
agent still going?" signal.

**Detection mechanism** (from `github.com/delexw/claude-code-trace`
spec 09 — reference-not-dependency, per the pretty-view shape file):
every background Agent tool_use in the parent session's JSONL is
definitively paired with a `tool_result` block carrying the same
`tool_use_id`. Ongoing = tool_use observed with no matching
tool_result yet; completed = tool_result observed → drop from the
list. **No new file reads, no new SSH poller, no timer** — the same
JSONL patch #43 already tails carries both signals.

Ships as ONE atomic feature commit
(`feat(pretty-view): backgrounded-agents panel (patch #61)`, SHA
`fe506e0`), followed by this docs commit for PLAN.md / SUMMARY.md /
STATE.md handled by the `/gsd:quick` finalize step.

## Backend Changes

### `src/backend/claude-session/claude-session-server.ts`

**WS protocol comment** (~line 22-30) — added one line documenting the
new event type between `harness_tasks` and `inactive`.

**Per-connection closure state** — three new locals alongside the
existing `harnessTasks*` locals (line 128-130):

```ts
const backgroundedAgents = new Map<string, {...}>();
let backgroundedAgentsLastSerialized = "[]";
```

**Load-bearing init to `"[]"` not `""`.** `tail -F -n +1` replays the
whole JSONL on WS attach. A background Agent that completed earlier
in history gets added to the map then removed within a few lines; the
final serialized list is `[]`. If we initialized `lastSerialized = ""`
the first-ever match would fire a spurious empty emit. `"[]"` matches
the empty-array `JSON.stringify(agents)` on that first tick, so no
emit fires until the map actually contains a live agent.

**Parallel raw-line scan** in the existing `tailSessionFile` onLine
callback, BEFORE `parseSessionLine(line)`. Runs **alongside** the
parser, not through it — RENDER-01 HARD LOCK strips
tool_use/tool_result blocks structurally at `session-file-parser.ts`,
so they never reach the parser's output. A second `JSON.parse(line)`
per tail line is trivially cheap at these volumes.

Wrapped in try/catch (malformed lines silently ignored — same posture
as the parser). The scan:
- On `type:"assistant"` with array `message.content` — for each block
  matching `{type:"tool_use", name:"Agent", input.run_in_background:true}`,
  `backgroundedAgents.set(block.id, {...})` with `startedAt` from the
  entry's `timestamp` (falls back to `Date.now()`).
- On `type:"user"` with array `message.content` — for each
  `{type:"tool_result", tool_use_id}`,
  `backgroundedAgents.delete(tool_use_id)`.
- After: build sorted-by-startedAt array, `JSON.stringify`, compare to
  `backgroundedAgentsLastSerialized`. On change: `ws.send({type:
  "backgrounded_agents", agents})` and update lastSerialized.

**No `teardownPane` change needed** — the Map and serialization string
are closure vars that die with the connection.

### `src/ui/features/pretty-view/PrettyView.tsx`

Five additive edits:
1. Extended `@/api/claude-session-api` import to include
   `BackgroundedAgent` type.
2. Added `BackgroundedAgentsPanel` import next to `HarnessTasksPanel`.
3. New state hook `backgroundedAgents` after `harnessTasks` with a
   short comment matching surrounding style.
4. Added `setBackgroundedAgents([])` reset next to `setHarnessTasks([])`
   in the mount effect.
5. New WS handler case `case "backgrounded_agents":
   setBackgroundedAgents(parsed.agents); break;` after the
   `harness_tasks` case.
6. Panel mount BELOW the HarnessTasksPanel IIFE, ABOVE the ComposeBox
   mount, gated on `status === "streaming" &&
   backgroundedAgents.length > 0`.

**Order rationale (tasks above agents):** matches causal reading — a
task can spawn an agent; the agent runs while the task remains
in-progress.

**Why sibling not folded:** different mental models. Harness tasks are
things Claude has planned or is stepping through; backgrounded agents
are parallel work happening RIGHT NOW under the assistant's feet.
Ashley's ask was specifically for the agents — a distinct visual
affordance reads correctly. Also cheaper to iterate on independently
later. Cost is one extra border-t row when both are non-empty, which
is rare.

## Scope explicitly out (deferred for later patches)

- **60s subagent-mtime staleness fallback** for parent-JSONL-crashed
  cases where a background agent's tool_result never lands. Requires
  reading `session_dir/<uuid>/agent-*.jsonl` from the tail box —
  another SSH read pass. Low-frequency case; punt until it actually
  bites.
- **Failure surfacing.** A `tool_result` with `is_error:true` today
  just removes the agent from the list. Distinguishing "completed
  cleanly" vs "errored" would need a short-lived "recently failed"
  row. Not clear the panel needs it — the parent session surfaces
  the failure in the chat anyway.
- **Progress detail** (what the subagent is currently doing, tokens
  spent). Requires reading the subagent's own `agent-*.jsonl` —
  same extra pass as staleness. Genuinely nice-to-have but out of
  scope for v1.
- **Also-Bash / also-Monitor** backgrounded work. Ashley explicitly
  out-of-scoped these; if wanted later, extend the raw-line scan's
  detection predicate.
