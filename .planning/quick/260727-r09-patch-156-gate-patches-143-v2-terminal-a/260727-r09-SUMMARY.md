# Quick Task 260727-r09: Patch #156 iOS-PWA gate on visibilitychange reconnect — Summary

Frontend gate that narrows patch #143 v2 (`Terminal.tsx`) and patch #148 (`PrettyView.tsx`) visibilitychange force-reconnect effects to iOS-PWA-only via a new `isIosPwa()` helper — Chrome desktop tab-switch away and back no longer force a fresh WebSocket + surface the Reconnect/Close overlay, iOS PWA behavior is preserved byte-for-byte.

## What Was Built

- `src/ui/lib/is-ios-pwa.ts` — new gate helper exporting `isIosPwa(): boolean`. Returns `true` only when `window.navigator.standalone === true` AND UA matches `/iP(hone|ad|od)/`. SSR-safe via `typeof window === "undefined"` guard (matches the existing pattern in `src/ui/lib/tab-url.ts` and `mobile-flow.ts`). Header comment references patch #156 and explains why gating is needed.
- `src/ui/lib/is-ios-pwa.test.ts` — five-case vitest coverage of the four (standalone × iOS UA) combinations plus the SSR guard. Uses `Object.defineProperty(navigator, ...)` for the DOM surfaces and `vi.stubGlobal('window', undefined)` for the SSR case. `afterEach` restores UA to the captured original and deletes the injected `standalone` property so no state leaks to sibling suites in the same worker.
- `src/ui/features/terminal/Terminal.tsx` — added `import { isIosPwa } from "@/lib/is-ios-pwa";` in the existing `@/lib/*` cluster (double-quoted to match). Prepended `if (!isIosPwa()) return;` as the first statement inside the visibilitychange `useEffect` body (currently ~line 344), before `const handleVisibilityChange = ...`. Layered a patch #156 comment paragraph on top of the existing patch #143 v2 rationale block (rationale preserved verbatim for the iOS-PWA case).
- `src/ui/features/pretty-view/PrettyView.tsx` — same treatment. Import added next to `@/lib/utils`, guard added as the first statement inside the visibilitychange `useEffect` (~line 793), and the comment block above updated with the patch #156 rationale.
- `src/ui/features/pretty-view/PrettyView.test.tsx` — three changes:
  1. Added module-scope `enableIosPwa()` / `restoreIosPwa()` helpers immediately after the existing `fireVisibilityChange()` helper. They install an iPhone UA + `navigator.standalone=true` and restore both on tear-down.
  2. Updated the existing `describe("PrettyView — patch #148 WebSocket auto-reconnect", ...)` block: `beforeEach` calls `enableIosPwa()`, `afterEach` calls `restoreIosPwa()`. Without this opt-in, Test C (`visibilitychange:visible resets counter and reconnects after cap`) would silently pass its cap-hit assertion but never reach stub 7 because the gate would bail. All four patch #148 tests still exercise the real gated code path.
  3. Added a new `describe("PrettyView — patch #156 non-iOS-PWA visibilitychange no-op", ...)` block that deliberately does NOT call `enableIosPwa()`. Its single `it(...)` mounts PrettyView in jsdom's default env (no `standalone` flag, non-iOS UA — sanity-asserted at the top of the test), fires `fireVisibilityChange(true)` + `fireVisibilityChange(false)`, and asserts `wsStubs.length` did not grow past its post-mount baseline.

## WsStub Factory Note

The plan asked the executor to discover whether the existing WsStub factory in `PrettyView.test.tsx` exposes an instantiation count or whether a minimal tweak was needed. **No tweak was required.** The patch #148 test setup already declares a module-scope `const wsStubs: WsStub[] = [];` and pushes each fresh stub into it inside the `openClaudeSessionSocket` mock factory (lines 28-56 of the test file). The `wsStubs.length` invariant is the direct observable used by the new patch #156 no-op test to prove `retryKey` did not bump.
