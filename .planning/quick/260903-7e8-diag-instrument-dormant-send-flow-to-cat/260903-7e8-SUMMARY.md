## Handoff Note for Follow-up Bug-Fix Phase

To diagnose Ashley's next repro of the dormant-send failure, grep both sources:

```bash
# Container logs (backend)
sudo docker compose -f /opt/skynet/docker-compose.yml logs skynet | grep '\[diag-dormant-send\]'

# Frontend console-forward pipe
grep '\[diag-dormant-send\]' /opt/skynet/console-forward-logs/console-forward.log
```

Cluster by `mqid=<value>`. The sequence answers the four hypotheses:

**Hypothesis A (wrong timer branch):**
Look for: `arm dormant=false` followed by `fire dormant_at_fire=true branch=normal`
This means the client armed with the 20s timer even though the pane became dormant before the timer fired.

**Hypothesis B (early-flip via non-timer path):**
Look for: `arm dormant=true timeoutMs=220000` followed by `ws-paste-send-failed` OR `ws-send-keys-error` OR `cleanup matched_by=ws-close-unmount` arriving well before 220s.
The `elapsedMs` on the cleanup/failed line tells you how early.

**Hypothesis C (backend full-resend producing duplicate):**
Look for: `watchdog-fire-full-resend elapsedMs=~95500` on the backend
after an `incoming-user-frame matched_by=fifo-head-match` or `watchdog-matched` already cleared the send.
This means backend's Stage 2 fired after delivery — duplicate real bubble.

**Hypothesis D (matrixEventId dedup gap):**
Look for: multiple `dedup-store` lines for the same matrixEventId across different paths (inbound, inbound-cap, range-fetch) without a corresponding `dedup-drop` on the repeat arrivals.
OR: two `cleanup matched_by=fifo-head-match` lines for different mqids against the same physical message.
