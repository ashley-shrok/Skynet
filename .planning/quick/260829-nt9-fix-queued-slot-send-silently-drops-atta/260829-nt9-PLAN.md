<objective>
Fix silent attachment loss on queued-slot sends. Three send call sites in
`src/ui/features/pretty-view/ComposeBox.tsx` (`handleQueueSlotSend` at :1312,
`fireNextQueued` at :1113, `handleVoiceSend` slot-target branch at :1526)
currently route through the text-only `onSend(payload)` path and silently
discard staged attachments living under target `queued:${slotId}`. Ashley
UAT 2026-08-29 confirmed empirically: PDF staged into a queued slot's chip
strip, Send hit, text arrived, PDF vanished with zero `upload_start` server
event and zero file on disk. Fix adds a target-aware attachment branch at
each of the three sites (mirroring the byte-identical pattern already shipped
in primary `handleSend` at :1384-1415 by quick-260823-8ji), threads a
`target?: string` parameter through `onSendWithAttachments` and
`uploads.startBatch` / `retryBatch` / `resetBatch`, and preserves the
`outcome.ok`/`reason` failure-preservation posture. Primary compose send
stays byte-identical (target defaults to `"primary"`).

Purpose: Close a data-loss bug across THREE parallel entry points that
users interact with routinely (manual slot Send, cadence auto-send, voice
slot send). Without this fix any attachment staged into a queued slot's
chip strip is a silent black hole.

Output: One production diff across three files + one self-contained
regression test file. Backward-compatible for all primary-compose callers.
</objective>
