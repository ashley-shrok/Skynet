# Quick 260912-0t4: hostId-scope identity lookup fixes cross-host cosmetics collision — Summary

**One-liner:** Fixed Alice's "both willows show the same avatar" bug by removing the backend's first-host-wins dedup on GET /identities and routing every fix_scope-enumerated cosmetics consumer through a new hostId-scoped `byHostKey` composite-key map (additive alongside the preserved bare-name `byKey`).

## Design Decisions

### 1. Additive `byHostKey` (kept `byKey`)

The fix_scope's literal wording suggested renaming `byKey → byHostKey` throughout `identities-store.ts`. A pure rename would break ~15 out-of-scope existence-check consumers whose semantics are "does an identity with this name exist ANYWHERE on the fleet?" — namely:

- `src/ui/AppShell.tsx` L2153, L2744, L2897, L3067 (identity-pane discriminator)
- `src/ui/AppShell.tsx` L667 (title resolver — any-host winner as display name)
- `src/ui/shell/tabUtils.tsx` L284 (identity-pane vs terminal-pane discriminator during hydration)
- `src/ui/shell/IdentitySessionPane.tsx` L105, L253, L457, L461 (identityKey → identity resolution)
- `src/ui/features/terminal/IdentityBadge.tsx` L83 (badge that only knows an identityKey string)
- `src/ui/state/conversation-store.ts` L378, L400, L536, L1455 (role fallback for sort key)
- `src/ui/features/pretty-view/relay-mxid-resolve.ts` L48 (MXIDs don't carry hostId)

Instead: **additive** — add `byHostKey` alongside `byKey` on the store. Cosmetics consumers in fix_scope switch to `byHostKey`; existence-check consumers keep working with `byKey`. Delta from the literal "rename" wording is documented inline in PLAN.md § Design decision.

### 2. Rule 3 auto-fix — `hostId` on publicIdentity return + wire Identity type

The plan's `<context>` block asserted:

> Backend `publicIdentity(identityKey, hostId, ...)` already puts `hostId` on every row (see identities.ts:400-407).

Grep confirmed **this was NOT true** — `publicIdentity()` bakes hostId into `avatarUrl` as a query param but does NOT surface it as a top-level field. Without a top-level hostId on the wire row, the frontend has no way to construct the `${hostId}::${identityKey}` composite key for `byHostKey`.

Fix (Rule 3 blocking-issue auto-fix, coupled with Task 1's atomic commit):

- Added `hostId,` to the `publicIdentity()` return object with an explanatory comment referencing quick-260912-0t4.
- Added `hostId?: number` to the wire `Identity` interface (optional to preserve pre-quick-260912-0t4 test-fixture compat).

### 3. Rule 3 auto-fix — byKey fallback on every byHostKey lookup

Initial pure-swap crashed ~15 test cases with `TypeError: Cannot read properties of undefined (reading 'get')` on `identitiesByHostKey.get(...)`. Two failure modes surfaced:

1. Test mocks of `useIdentities` return only `byKey` (no `byHostKey` field) — `.get` on undefined throws.
2. Test fixtures seed identity objects WITHOUT `hostId` — even where `useIdentities` returns a real store, `byHostKey` is empty because setIdentities skips rows without a valid hostId (deliberate: seeding `undefined::name` buckets would mis-serve production lookups).

Fix (Rule 3, coupled with Task 3's commit): every byHostKey lookup site tries the composite first and falls back to bare-name `byKey.get(matchKey)` when the composite misses. In production the backend surfaces hostId on every row (Task 1), so byHostKey hits first and the fallback never fires. In tests, the fallback lets legacy fixtures keep resolving identities the way they used to.

`useSessionIdentity` got the same treatment — hostId-scoped first, bare-name fallback second.

## Follow-on Bounties (deferred from this fix)

### 1. IdentitySessionPane bare-name lookup (terminal-mode identity badge / modal-open path)

`src/ui/shell/IdentitySessionPane.tsx` L457 and L461 currently do `identitiesByKey.get(identityKey)!` — bare-name lookup. If two identities share a name across different fleet hosts, the badge-click that opens IdentityModal from a terminal-mode identity pane resolves the identity via this bare-name lookup and can pick the WRONG host's identity (even though the pane itself knows its own `host.id` via its `host` prop).

**Two-line fix once IdentitySessionPane is in a subsequent phase's scope:**

```ts
// L457-461 area:
const hostIdNum = parseInt(host.id, 10);
const identity = identitiesByHostKey.get(`${hostIdNum}::${identityKey}`)
                 ?? identitiesByKey.get(identityKey)!;
```

Documented as a comment at the top of `IdentityModal.tsx` for future planners.

### 2. Relay-side MXID lookups

MXIDs (`@localpart:homeserver`) do NOT carry hostId natively. The following relay sites resolve identities via bare-name / MXID lookup and would need a separate design decision to disambiguate cross-host same-localpart identities in relay rooms:

- `src/ui/features/pretty-view/relay-mxid-resolve.ts:48` (`resolveMxidToIdentity(mxid, byKey)`)
- `src/ui/features/pretty-view/RelayInboundBubble.tsx:145`
- `src/ui/features/pretty-view/MultiBadgeAnchor.tsx:139` (HumanBadgeCell → resolveMxidToIdentity)

These paths are explicitly out of quick-260912-0t4 scope per the plan's MXID exclusion. Design work needed if Alice ever encounters relay-room collision.
