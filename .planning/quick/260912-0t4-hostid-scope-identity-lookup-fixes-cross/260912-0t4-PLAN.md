Output: backend returns per-(hostId, identityKey) rows; scoped consumers pick the RIGHT row for their pane's host.

## Design decision embedded in this plan (flag for Alice at PR review)

The `<fix_scope>` bullet under "Frontend state" says "Rename `byKey: Map<string, Identity>` → `byHostKey: Map<string, Identity>` throughout the file." A pure rename would break ~15 out-of-scope callers whose semantics are "does an identity with this name exist ANYWHERE on the fleet?" — namely:
- src/ui/AppShell.tsx L2153, L2744, L2897, L3067 (identity-pane discriminator via `identitiesByKey.has(name)`)
- src/ui/AppShell.tsx L667 (title resolver — takes any-host winner as the display name)
- src/ui/shell/tabUtils.tsx L284 (identity-pane vs terminal-pane discriminator during hydration)
- src/ui/shell/IdentitySessionPane.tsx L105, L253, L457, L461 (identityKey → identity resolution — pane already knows its own host, but this file is out of fix_scope so we don't rewire it)
- src/ui/features/terminal/IdentityBadge.tsx L83 (badge that only knows an identityKey string, not a hostId)
- src/ui/state/conversation-store.ts L378, L400, L536, L1455 (role fallback for the sort key when fleet-authoritative role hasn't landed yet — bare-name lookup is fine here, this is a fallback path)
- src/ui/features/pretty-view/relay-mxid-resolve.ts L48 (MXID → identity; MXIDs don't carry hostId — fix_scope EXPLICITLY excludes this path)
- src/ui/features/pretty-view/MultiBadgeAnchor.tsx L139 (HumanBadgeCell → resolveMxidToIdentity — this IS a MXID path, so it's also out of scope per the fix_scope MXID exclusion, even though the fix_scope "Frontend consumer sites" bullet #6 lists MultiBadgeAnchor.tsx:139 — internal contradiction in the fix_scope; the AgentBadgeCell path at L173 uses `fleetIdentityHosts[identityKey]` NOT byKey, so there's no byKey lookup in MultiBadgeAnchor that touches identity-scope cosmetics)

To honor the fix_scope's explicit consumer enumeration AND the "out of scope" MXID exclusion AND keep this a quick self-contained fix, the plan uses an **additive** approach: add `byHostKey` alongside the existing `byKey` on the store. `byHostKey` is the new hostId-scoped map; `byKey` stays bare-name and keeps its "any-identity-with-this-name-exists" semantics for the existence-check consumers. In-scope cosmetics consumers switch to `byHostKey`.

This means the MultiBadgeAnchor.tsx:139 line remains untouched (it's on the MXID path — out of scope per the explicit exclusion). If Alice wants the pure-rename form, that's a scope-widening decision she should make at PR review; it multiplies the changed-file set roughly 3× and threads hostId through IdentityBadge / tabUtils / IdentitySessionPane call chains, which is outside the "quick" mode's budget.

## Data model recap

Backend `publicIdentity(identityKey, hostId, ...)` already puts `hostId` on every row (see identities.ts:400-407). The dedup at L432-437 is what drops the second-host row. Removing the dedup delivers per-(hostId, identityKey) rows to the wire; wire type is `Identity[]` and already carries `hostId: number` per row (see @src/ui/api/identities-api if wire type ever gets flagged in tsc).

Frontend `${hostId}::${key}` composite matches the shape used elsewhere: conversation-store's `fleetRowId(hostId, sessionName)` = `fleet::${hostId}::${sessionName}` (single-namespace-separator convention).
