<objective>
Close the compose attachment-path silent-failure hole in PrettyView. Today, `handleSend`'s attachment branch (`ComposeBox.tsx:1317-1327`) fires `onSendWithAttachments(captionPayload)` as pure fire-and-forget, then unconditionally logs `submit-success`, clears the textarea, and clears the attachment slots — even when the batch's WS drops, times out, or backend never emits `upload_ready_to_inject`. Ashley has hit this four times in a row across two different hosts (wanda + nelly, 2026-08-23); each attempt: submit-entry → submit-success → composer cleared → backend `upload_start` fires → no `upload_complete`, no `paste_send`. The attachment and text vanish, no recovery affordance.

Purpose: Mirror the non-attachment path's outcome-gated clear pattern (`ComposeBox.tsx:1350-1385`, Phase 50 D-20 / D-56) so the attachment path clears the composer ONLY on a genuine success signal from the batch lifecycle. On failure/timeout/ws-drop, preserve the textarea + attachment slots and surface an inline error — same UX contract Ashley already knows from the text-only path.

Output:
  - `use-pretty-view-uploads.ts` gains a per-batch outcome Promise. `startBatch` (and `retryBatch`) return `{ messageQueueItemId, outcome: Promise<BatchOutcome> }` where `BatchOutcome = { ok: true } | { ok: false; reason: 'upload_failed' | 'timeout' | 'ws_not_open' | 'ws_send_threw'; message?: string }`. The hook arms a 30-second timer at successful `upload_start` dispatch; `upload_ready_to_inject` resolves ok + clears the timer; `upload_failed` resolves !ok with the reason's `UploadFailureReason` in `message`; the timer resolves !ok with `reason: 'timeout'`. Batch supersession (retry/reset before terminal event) resolves the OLD outcome with `reason: 'superseded'` (BatchOutcome union extended accordingly) so no dangling awaits linger.
  - `onSendWithAttachments` prop shape widens from `(caption: string) => void` to `(caption: string) => Promise<BatchOutcome>`; `PrettyView.tsx` L3178-3184 wiring updates to `return uploads.startBatch(caption).outcome` (or the retry equivalent). Any other in-repo callers get the same widening.
  - `ComposeBox.tsx` `handleSend` attachment path (`if (hasAttachments && onSendWithAttachments)` at ~L1317) rewrites to:
    - log `submit-entry` including `mqid=` placeholder (mqid becomes known post-await — see below);
    - `const outcome = await onSendWithAttachments(captionPayload);`
    - on `outcome.ok`: log `submit-success hostId=… mqid=…`, `setText("")`, `clearAfterSend()`;
    - on `!outcome.ok`: log `submit-failed hostId=… mqid=… reason=… message=…` at WARN, call `setErrorMessage(<reason-specific string>)`, DO NOT clear text or attachments;
    - reason → user-facing string mapping (`getBatchFailureUserMessage(reason)` helper — colocated in ComposeBox for now, extractable later): `upload_failed` → `Upload failed — try again.`; `timeout` → `Upload timed out — check connection and try again.`; `ws_not_open` → `Not connected — try again in a moment.`; `ws_send_threw` → `Connection dropped — try again.`; `superseded` → no error surface (a superseding action already ran, don't stomp its state).
