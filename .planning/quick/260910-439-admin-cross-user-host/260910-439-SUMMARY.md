## What Was Built

### Task 1 — Admin READ bypass

- `callerIsAdmin(userId)` helper added to both `host.ts` and `credentials.ts`, mirroring the `users.ts:442` "read isAdmin from DB, not JWT" pattern.
- `users` symbol added to the existing schema import block in each file (no duplicate imports).
- Four host GET endpoints: `GET /db/host`, `GET /db/host/:id`, `GET /db/host/:id/export`, `GET /db/hosts/export` — each drops the `eq(hosts.userId, userId)` WHERE filter when `isAdmin === true`. Non-admin path is byte-identical to pre-change.
- For `GET /db/host` (list): when admin, all raw rows are treated as "own" for the decrypt loop so the `decryptedOwnHosts` path covers every row. Foreign-user sensitive fields fall through `LazyFieldEncryption`'s empty-string fallback (acceptable: admin's use case is linking rows to credentials, not reading other users' passwords).
- Two credentials GET endpoints: `GET /credentials` and `GET /credentials/:id` — same userId filter drop when admin. Cross-user cred sensitive fields: same empty-string fallback (see `T-Q439-04` in threat model — documented with code comment in credentials.ts).
- Audit log: `operation: "admin_cross_user_read"` with `callerUserId` and table name added inside each of the 6 modified handlers.

### Task 2 — Admin targetUserId on POST + PUT

**POST /db/host:**
- `targetUserId` destructured from `hostData` in the existing block alongside `runsFleetSubstrate`.
- Admin gate fires AFTER basic validation (`ip`/`port`/`userId` check) and AFTER `effectiveRunsFleetSubstrate` computation, BEFORE `sshDataObj` construction. D-08 guard fires after the admin gate (ordering: D-08 → after sshDataObj, admin gate → before sshDataObj, so admin gate fires first).
- `effectiveUserId` computed after gate: `targetUserId ?? userId`. Used in `sshDataObj.userId` and `SimpleDBOps.insert(hosts, "ssh_data", sshDataObj, effectiveUserId)`.
- `try/catch` around `SimpleDBOps.insert` catches `DataCrypto.validateUserAccess` throws → 400 with "Target user not logged in — Skynet cannot encrypt on their behalf."
- Audit log: `operation: "host_create_admin_cross_user"` with `callerUserId`, `effectiveUserId`, `hostId`.

**PUT /db/host/:id:**
- `targetUserId` destructured from `hostData`.
- `isAdminForUpdate` read ONCE at the top of the `try` block (before `permissionManager.canAccessHost`) to avoid a second DB round-trip.
- Admin gate with sensitive-field-block check fires before `canAccessHost`.
- `canAccessHost` `hasAccess` gate: `if (!accessInfo.hasAccess && !isAdminForUpdate)` — admin bypasses.
- `isOwner` gate: `if (!accessInfo.isOwner && !isAdminForUpdate)` — admin bypasses.
- Credential-change and authType-change owner restrictions: also bypassed for admin.
- `sshDataObj.userId = effectiveUpdateUserId` set ONLY when admin AND `effectiveUpdateUserId !== userId` — re-assigns row ownership.
- `encryptKeyUserId` uses `effectiveUpdateUserId` (target's key) for the SimpleDBOps.update call.
- `try/catch` around `SimpleDBOps.update` for same validateUserAccess error handling.
- Audit log: `operation: "host_update_admin_cross_user"`.

**Error shapes:**
- Non-admin with targetUserId → `403 { error: "Only admin users can set targetUserId" }`
- Admin cross-user + inline sensitive creds → `400 { error: "Cross-user writes cannot include inline sensitive credentials — use credentialId instead" }`
- Target user not logged in → `400 { error: "Target user not logged in — Skynet cannot encrypt on their behalf. Ask them to log in first." }`
