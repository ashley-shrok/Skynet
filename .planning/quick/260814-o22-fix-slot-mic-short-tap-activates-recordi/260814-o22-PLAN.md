<objective>
Fix the iOS-Safari-only regression where short-tapping a queue-slot mic
activates the RecordingControls UI in the PRIMARY text area instead of the
slot. The root cause was diagnosed with live iPhone log evidence at
2026-08-14 16:48:37Z: `useHoldToRecord.onPointerDown` calls `voice.start()`
synchronously (D-16-02) but does NOT set `micTarget`; `setMicTarget` only ran
inside `beginRecord(target)` which is wired to `MicButton`'s `onClick`; quick-
260814-iwy added `e.preventDefault()` on pointerdown to MicButton to suppress
the iOS long-press callout, which — on `<button>` elements in iOS Safari —
also suppresses the synthesized `click` event, so `beginRecord(slot.id)`
never runs and `micTarget` stays at its default `"primary"`. The primary
mic works only accidentally because `"primary"` is the default.

The fix is two JSX-seam edits in `ComposeBox.tsx` that wrap each MicButton's
`onPointerDown` prop with a handler that calls `setMicTarget(target)`
SYNCHRONOUSLY before delegating to the hook's `onPointerDown`.
`setMicTarget` is a synchronous React `setState` (no microtask boundary), so
this is safe under the D-16-02 iOS Safari sync-gesture invariant — the ref
write inside `useHoldToRecord.onPointerDown` (`holdInitiatedRef.current =
true`) already establishes precedent for a single synchronous statement
before `voice.start()`.

Purpose: Restore Ashley's ability to short-tap a queue-slot mic on her
iPhone and have RecordingControls appear on THAT slot, not on the primary.
