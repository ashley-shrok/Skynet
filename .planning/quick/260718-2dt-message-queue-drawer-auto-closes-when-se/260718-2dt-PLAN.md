<objective>
Auto-close the per-pane message queue drawer when Send empties the queue.

Purpose: Ashley's current UX after sending the last queued message is "drawer sits open with 'No queued messages' visible → she reaches for the drawer's close button (or Ctrl+Shift+;) to dismiss it." Send emptying the queue is a strong signal the drawer's job is done for this pane, so it should close itself. Trash and Retry-cleanup paths keep the drawer open (Trash may be an intermediate step, Retry needs the row visible).

Output: One two-line insert in `MessageQueueDrawer.tsx`'s `handleSend` that reuses the already-wired `onClose` prop. No new prop, no Terminal.tsx change, no i18n, no backend, no nginx.

Discovery during planning: the design_locked note assumed the plan would need to add a new `onClose` prop and a wire-in at Terminal.tsx. The prop ALREADY exists (`MessageQueueDrawerProps.onClose` at MessageQueueDrawer.tsx:19, wired at Terminal.tsx:2863 to `setIsMessageQueueOpen(false)`). It's currently only invoked by the drawer's own explicit close button (line 306). We just extend its firing sites to include "send emptied the queue." This makes the change one file, one location, ~3 lines.
</objective>

In `src/ui/features/terminal/MessageQueueDrawer.tsx`, modify `handleSend` (the useCallback declared at line ~251).

The existing success branch (inside the `try` after `await deleteMessageQueueItem(item.id)`) currently does:

    setItems((p) => p.filter((it) => it.id !== item.id));

Replace that single-line functional updater with a form that checks whether the filtered result is empty and, if so, invokes `onClose?.()`. Use the functional-updater form (do NOT read `items` from the closure — it may be stale by the time the async DELETE resolves). Do this by capturing the filtered array inside the updater and calling `onClose?.()` after computing it (before returning it), or equivalently: capture the length inside the updater and fire onClose after the setItems call using the captured length via a local `let`.

Preferred form (self-contained inside the setItems updater — no external let, no race):

    setItems((p) => {
      const next = p.filter((it) => it.id !== item.id);
      if (next.length === 0) onClose?.();
      return next;
    });

Note: `onClose` is `required: () => void` on the Props type (line 19), not optional — the `?.` guard is defensive belt-and-braces for future prop-optionalization and is harmless. Feel free to drop the `?.` if you prefer, but `onClose()` is also correct given the current Props signature.

**Do NOT touch:**
- The `catch` branch (sent-pending fallback that puts the id in `sentPendingIds` and shows Retry cleanup). This path must leave the drawer open so the user can see and click the retry button.
- The `handleDelete` path (line ~219, called by the Trash button). Trash emptying the queue must NOT close the drawer per the design_locked note.
- The `handleRetryCleanup` path (line ~238). Same as Trash.
- `MessageQueueDrawerProps` — `onClose` already exists as a required prop.
- `Terminal.tsx` — the wire-in at line 2863 (`onClose={() => setIsMessageQueueOpen(false)}`) already exists and does exactly what we need.

Rationale: keeping the change entirely inside the handler that owns the "send succeeded" semantic keeps the surface area minimal (one file, three-line diff net) and preserves the existing close-semantics for every other path. `onClose` is idempotent from Terminal's perspective (`setIsMessageQueueOpen(false)` on an already-closed drawer is a no-op), so firing it once from the setItems updater is safe even in the corner case where onClose runs during render commit.
