<objective>
Fix the PV claude-session backend-zombie: a WS whose bound `currentTmuxSession` / `sshConn` goes null on server-driven teardown (holding_timeout via `transitionToDead`, FALLBACK-01 initial-inactive path that nulls `sshConn`) but leaves the WS open with `readyState:1 OPEN`. Silent short-circuit at `claude-session-server.ts:2567` swallows every subsequent input frame with no log, no ack — Phase 56-01 dormant-send wake never fires. Root cause pinned today via a client-side ws.close() probe that forced reconnect + fresh session-bind and immediately produced the first-ever `pv-input rx` for the affected tmuxSession across the whole log.

Two-part fix (both required):
  (a) Close-with-reason: call `ws.close(1011, "session_torn_down")` on every server-driven teardown path BEFORE the state gets nulled — client's existing reconnect handler fires onclose → schedules reconnect → new WS runs the session-bind handshake → `currentTmuxSession` re-bound. Verified working today.
  (b) Log the drop: add `sshLogger.warn("[pv-input] drop_no_session", …)` at the `:2567` entry guard so future teardown paths that slip through fix (a) leave a forensic trail instead of vanishing silently.

Purpose: Restore correct send delivery through a dormancy / teardown cycle without user intervention. Add the forensic log so the class of failure cannot silently recur.

Output: Modified `claude-session-server.ts` + expanded `claude-session-server.compose-send.test.ts`; scoped tests green; backend typecheck passes; single commit `fix(pv-ws): …`.
</objective>
