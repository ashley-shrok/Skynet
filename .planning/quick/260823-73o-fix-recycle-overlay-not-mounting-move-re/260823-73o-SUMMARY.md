# Phase quick-260823-73o Plan 01: fix-recycle-overlay-not-mounting-move-re Summary

One-liner: **Migrated all three recycle axes (`.recycle-requested`, `.recycled-at`, Layer 1 /id reset JSONL scan) out of ssh-poll-orchestrator source A's per-PID `processPid` loop and into source B's per-identity `pollDormantOnlyIdentities` iteration; source B is now the sole publisher of `SessionState.recycling`; live-PID skip conditionally lifted when `isRecycling === true`; transition-edge publish added so evicting an identity whose cached recycling was true first emits a final `recycling:false` frame.**

## Objective

Close the RCA Ashley narrated 2026-08-23 04:45:47Z: patch #495 shipped
`fleet_status_recycling_armed` diagnostic + `.recycle-requested` axis in source A,
but the overlay never mounted during her full /id reset cycle. Preliminary log
analysis showed Layer 1 (`transitionToHolding reason:id_reset`) fired correctly
but `fleet_status_recycling_armed` NEVER fired for identity `tina` across the
reset window. Root cause: source A iterates `~/.claude/sessions/*.json` (PID
files); during tina's reset the outgoing claude PID is being torn down and
source A's per-PID iteration hits a lifecycle-timing gap where none of the
three axes ever evaluate true across the sentinel-present window. Source B is
identity-folder-keyed and runs unconditionally per identity per tick — the
correct architectural seam. The agent-supervisor renames `.recycle-requested` →
`.recycled-at` on the first reconcile tick after touch, then schedules deletion
of `.recycled-at` 8s after `drive()` returns, so `.recycled-at` is on disk from
`t=~+2s` through `t=~+drive_returns+8s` — the sentinel-present state precisely
brackets the entire "should show overlay" window with an 8s guard band. No PID
observation needed.

**2. [Rule 2 — Auto-added critical functionality] Transition-edge publish before source-B skip-and-evict**

- **Found during:** Task 2 GREEN pass (Test T1-vi failing after initial implementation).
- **Issue:** The plan's Phase 5 skip-and-evict semantic said "if `liveTmuxSet.has(name) && !isRecycling`, delete the cache entry and continue". Executing that literally means: on tick 1 an identity with live PID + `.recycle-requested`=yes publishes source-B frame with recycling:true. On tick 2 `.recycle-requested`=no → skip + evict silently. The registry now holds a stale source-B frame with recycling:true (from tick 1) plus a source-A frame with recycling:false. Fresh browser subscribers see the stale recycling:true and the overlay stays armed indefinitely. Test T1-vi locks the transition semantics explicitly.
- **Fix:** In the source-B skip-and-evict branch, check `cached?.recycling ?? false` before evicting. If cached was true, publish a `recycling:false` source-B frame BEFORE the `delete + continue`. Registry now sees the transition and consumers correctly un-arm the overlay. Log line is
  `"Fleet-status: source B frame published (recycling-false transition, pre-evict)"`
  with the standard `operation: fleet_status_source_b_publish` so log-scrapers grep the same operation code.
- **Rationale:** This is Rule 2 (auto-add missing critical functionality) — without it, the overlay would arm correctly at t=0 but never un-arm on the recycling→false transition while the same identity retains a live PID (which is exactly the reverse of Ashley's bug and would create a NEW UAT failure).
- **Files modified:** src/backend/fleet-status/ssh-poll-orchestrator.ts (pollDormantOnlyIdentities skip-and-evict branch, ~15 lines added).
- **Commit:** 303c87b1 (bundled into the Task 2 GREEN commit).

None of these deviations required user consultation (Rule 4). Both are direct consequences of the migration surface — the first is test-infrastructure adaptation to reflect the new architecture; the second closes a semantic hole in the plan's evict semantics that would have re-created a similar bug in reverse.
