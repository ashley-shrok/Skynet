## Deviations from Plan

1. **Unified `queueSlots.length >= 2` gate on both primary and queued
   armed overlays.** The plan flagged this as a small ambiguity in Ashley's
   ask — the primary is not a queued slot, so a strict read of "fire order
   in the queued messages" could gate the primary at `queueSlots.length >= 1`
   (one queued slot + primary = 2 armed things). I went with the simpler
   unified gate per the plan's recommended reading. If Ashley wants the
   primary badge to appear one slot earlier, easy follow-up: swap the
   primary overlay's gate to `>= 1`. Documented for Ashley to redirect if
   the interpretation is wrong.

2. **Fire-order badge total uses `queueSlots.length`, not `queue.length`.**
   `queue.length` counts only the ARMED subset (`isSourceArmed` sources);
   `queueSlots.length` counts the visually-queued messages Ashley sees on
   screen. "1/1" reading would appear even when 3 slots exist but only 1 is
   armed, which reads as "misleading" per the plan's analysis. Went with
   `queueSlots.length` per the plan's recommended reading; noted here for
   Ashley to redirect.

3. **Fresh delete-tab corner styling `-top-2 -right-2 z-20 p-1 rounded-full
   bg-[rgba(10,12,20,0.85)] border border-[rgba(220,225,245,0.12)]`.** The
   plan gave an approximate treatment; my implementation adds `z-20` to
   survive any future overlay stacking, uses `bg-[rgba(10,12,20,0.85)]`
   (matches the armed-overlay scrim tone at higher opacity for the tab
   pill), and a 1px `rgba(220,225,245,0.12)` border for pill-edge
   readability. If Ashley's UAT flags size / border / rounding, easy CSS
   tweak — no structural change needed.

4. **QueuedRow accepts `onSlotsChange` wrapper prop instead of raw
   `setQueueSlots`.** The plan sketched a large prop surface with 24-ish
   props; I picked `onSlotsChange` as the single write path (parent wraps
   `setQueueSlots(next); scheduleAutosave(latestBodyRef.current, next);`)
   so QueuedRow doesn't need to know about `scheduleAutosave` at the
   change site — only the parent's wrapper does. Both Textarea change
   and delete tab call `onSlotsChange`. Cleaner than plumbing both
   separately.

5. **Chip strip overlay wrapper always renders (matches Quick A's Deviation
   #1).** AttachmentChipStrip's return-null-when-empty contract does the
   right thing: empty state → chipStripRef.current is null → useLayoutEffect
   sets chipStripHeight to 0 → Textarea's paddingTop falls back to base.
   No wrapper conditional needed. QB-8 verifies 0 chip-strip DOM elements
   render when the target is empty.

## Known stubs / follow-ups

1. **Queued-textarea onPaste handler not wired to per-slot target.** Paste
   on the primary Textarea routes to primary via `handlePaste` +
   `onAttachFiles`; paste on a queued Textarea currently has no `onPaste`
   handler (verified via grep of the queued Textarea render — absent), so
   paste falls through the primary path via the top-level dropzone.
   Adding per-slot paste would require an `onPaste` on the QueuedRow's
   Textarea + `activeStagingTargetRef` routing — trivial mechanically but
   Ashley didn't ask for it in the paired-ship spec. Note as a genuine
   follow-up, NOT a stub.

2. **Queued-slot send with attachments does NOT currently trigger the
   primary chunk-pump `startBatch` flow.** Queued sends today are plain-
   text sends via `handleQueueSlotSend` → `onSend(text)`. If Ashley wants
   queued sends to inject an attachments turn like the primary's
   `onSendWithAttachments` path, that's a separate wiring task requiring
   either per-slot batch identity or a shared batch across slots.
   Non-trivial. Out of Quick B's scope; note as a follow-up.

3. **QB-1..QB-14 fixture ordering assumptions.** Tests assume queued slots
   render BEFORE the primary in DOM order (index 0 = first slot, index
   N-1 = last slot, index N = primary). This matches the queueSlots.map
   rendering above the primary Row 2 textarea. If a future refactor
   changes the DOM order (e.g. moves queued slots below primary), QB-2,
   QB-5, QB-10..QB-14 will need reindexing. No planned change today.
