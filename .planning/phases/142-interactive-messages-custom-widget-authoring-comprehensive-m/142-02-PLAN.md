<objective>
Add a `## Custom widget authoring` section to `substrate/skills/interactive-messages/SKILL.md` teaching agents how to build widgets from scratch when the six preset templates don't fit their case.

The six presets (poll, checklist, form, ranking, list-actions, color-picker) cover the common shapes and are the fast path. Custom is the escape hatch for genuinely different interactions — e.g. a canvas-drawing widget, a rating widget with continuous input, a step-through wizard, a two-panel comparison, a live-updating leaderboard, a media-annotation UI.

The section must teach:
1. **When to reach for custom** — with 3-5 concrete example widget ideas that would NOT fit any preset.
2. **The minimal contract** — the five-file dir shape and what each file does, sourced from the existing preset templates as ground truth.
3. **Two authoring recipes** — a worked terminal-on-click custom widget and a worked non-terminal custom widget, each showing the postMessage / /update discipline in enough detail that an agent could adapt them.
4. **Mandatory disciplines** — the arc-wide invariants every custom widget must observe.
5. **How to scaffold a custom widget** — the exact drop-in-dir + systemctl commands, since `create-widget.sh` only knows the six presets.

Purpose: shape file's `## Scope edges` v1 list ends with "Custom-widget authoring instructions in the skill, with the earns its interactivity and mobile-friendliness disciplines taught broadly." This plan ships that.

Output: SKILL.md gains a new top-level `## Custom widget authoring` section, inserted between the existing `## Buttons vs passive selectors` section and the `## Phase 140 limits` section (which Plan 04 will rewrite as Phase 142 completion notes).

- Do NOT touch the per-template blocks (that's Plan 04's job, since Plan 04 needs Plan 01's mobile-audit findings).
- Do NOT rewrite the `## Phase 140 limits` section (Plan 04).

    Document the five files every widget dir must contain, with one-line role descriptions each:
    - `widget.html` — the UI. Loaded at the pane root (`GET /` and `GET /index.html`). Must set `<meta name="viewport" content="width=device-width, initial-scale=1">`. Uses `__PROMPT_JSON__`-style substitution markers if you wire an `args.sh` hook (custom widgets can also hard-code and skip substitution entirely).
    - `server.py` — the Python stdlib HTTP server. Binds `127.0.0.1:$PORT` (env var, systemd-provided). GET `/` and `/index.html` serve `widget.html`. POST endpoint(s) write `state.json` atomically under a threading lock. Zero external dependencies.
    - `args.sh` — the scaffold-time hook. Only needed if you want to use `create-widget.sh`'s dispatcher (which requires editing the dispatcher's template allowlist too). Custom widgets typically SKIP this file and hard-code widget.html content instead.
    - `im-SLUG.service.template` — systemd user unit template. Substitution markers: `__SLUG__`, `__WIDGET_DIR__`, `__PORT__`. Written to `~/.config/systemd/user/im-<slug>.service` after substitution.

      2. POSTs `{rating, submitted_at}` to `PANE_BASE + "/submit"` (or `/submit` relative).

    - `persistState(data)` function that:
      1. POSTs `{...data, updated_at}` to `PANE_BASE + "/update"`.
      2. NEVER calls `window.parent.postMessage` (non-terminal widgets do not wake the agent).
      3. On fetch success, updates the status line to "Saved."; on fetch failure, prompts the user to interact again.

    Show the server.py skeleton with a POST `/update` endpoint (NOT `/submit`) writing state.json under the lock, forcing `data["template"] = "sketch"` before write.

    Reference `substrate/skills/interactive-messages/templates/poll-non-terminal/{widget.html,server.py}` as the source-of-truth precedent.

    ### `### Mandatory disciplines`
    A bulleted list of arc-wide invariants every custom widget must observe. Each bullet is grep-checkable per shipped widget:
    - **Affordance matches behavior**: button-shaped elements act on click; passive selectors (radios, checkboxes, sliders) do NOT fire terminal actions on interaction. Terminal-mode uses buttons; non-terminal uses passive selectors.
    - **Earns its interactivity**: apply the "would typing be easier?" test BEFORE authoring. If a plain text reply would be easier for the user, do not author the widget.
    - **Mobile-first-class**: touch targets ≥44px (Apple HIG), no horizontal scroll at 320px viewport, keyboard-accessible (Tab-focusable, Space/Enter to activate).
    - **postMessage discipline**: terminal widgets fire `window.parent.postMessage(payload, window.location.origin)` — NEVER `"*"` as the origin argument. Non-terminal widgets never call `postMessage` at all.
    - **Fetch-before-postMessage**: terminal widgets fire postMessage ONLY after the `/submit` fetch resolves OK. On fetch failure, do not fire postMessage — the agent must not wake to a submit that didn't persist.
    - **No streaming**: widgets render atomically. Never stream partial state; never poll state.json from the client; never SSE / WebSocket.
    - **Filesystem is the source of truth**: state.json lives on the agent's box under `~/fleet/interactive-messages/<slug>/`. The agent reads it directly. The invisible submit message carries only a wake ping, never the value.
    - **Port range**: bind the systemd unit's `Environment=PORT=` to a port in the 9601-9699 range that no other im-* service is using. Custom widgets share the same 99-port pool as preset widgets.

    ### `### Scaffolding a custom widget`
    Give the exact sequence an agent runs after writing the five files locally (say, in `~/my-widget-source/`):

    1. Copy the widget dir to `~/fleet/interactive-messages/<slug>/`.
    2. Write `metadata.json` with `template`, `widget_id`, `message_id`, `conversation_id`, `config`, and `created_at: $(date -u +"%Y-%m-%dT%H:%M:%SZ")`. The `created_at` field is what the seven-day GC sweep reads.
    3. Choose a free port in the 9601-9699 range (grep `~/.config/systemd/user/im-*.service` for `Environment=PORT=` to see what's taken).
    4. Substitute `__SLUG__`, `__WIDGET_DIR__`, `__PORT__` in `im-SLUG.service.template` and write to `~/.config/systemd/user/im-<slug>.service`.
    5. `systemctl --user daemon-reload`
    6. `systemctl --user enable --now im-<slug>.service`
    7. Verify: `systemctl --user status im-<slug>.service` — must be `active (running)`.
    8. Wait ~5-10 seconds for the discovery sweep to pick up the new widget, then embed the anchor URL `[label](/interactive/<hostid>/<slug>/pane/)` in your agent message.

    Note: `create-widget.sh` does NOT know about your custom widget name — do not run it against a custom slug. Its `--template` flag has a hardcoded allowlist of six values. Do not modify that allowlist for one-off custom widgets.

    Note: `teardown-widget.sh` DOES work on custom widgets — it operates purely on slug + filesystem paths, no template awareness. Run `bash ~/.claude/skills/interactive-messages/teardown-widget.sh <slug>` when done, same as with preset widgets.
