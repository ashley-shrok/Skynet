<objective>
Emit a byte-stable build-ID (git short SHA, 12 hex chars) into the browser bundle at Vite compile time AND make the identical string available at backend startup via `process.env.VITE_BUILD_ID`. Wire up the plumbing all the way from the ship runbook's `SKYNET_BUILD_SHA` env → `docker-compose.yml` build args → Dockerfile stages → both the frontend-builder stage (where Vite reads it) and the final runtime image (where Node reads it at boot). Ship two thin getter modules — `src/ui/lib/client-build-id.ts` and `src/backend/config/server-build-id.ts` — that all downstream consumers (interceptors, WS clients, WS servers, middleware) import from, so no consumer touches `import.meta.env.*` or `process.env.*` directly except through the getter.

Purpose: this is the tag-source Plan the entire phase depends on. Nothing else can stamp requests, refuse mismatches, or detect drift until both sides can produce byte-identical strings from the same source. Doing this in Wave 0 gate-blocks the whole tree cleanly (per D-18 candidate b — git short SHA — chosen by RESEARCH.md Q1 with byte-identity + no-redundant-reload rationale).

Output: browser bundles carry `VITE_BUILD_ID` as a string literal (baked via `define`); backend containers boot with the same string as an env var; both sides log their build-id at startup for operator visibility (Pitfall 4 mitigation).
</objective>

| Boundary | Description |
|----------|-------------|
| Ship-runbook → docker-compose env | Operator sets SKYNET_BUILD_SHA outside container; propagates via compose interpolation |
| docker-compose → Dockerfile | Build-arg interface, trusted (both operator-controlled) |
| Dockerfile → runtime env | Container-scope env var; readable by any process inside the container |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-132-01 | Tampering | Missing ARG declaration in a Dockerfile stage | mitigate | Task 3 acceptance criterion asserts three separate `ARG SKYNET_BUILD_SHA` lines exist (grep-checked). Missing declaration in the final stage would silently leave `VITE_BUILD_ID=dev-unknown` in production → Pitfall 4 reload-loop precursor. |
| T-132-02 | Repudiation | Operator can't distinguish "correct build shipped" from "stale env vars" | mitigate | The startup log line (added in Plan 03) emits `operation: "server_boot_build_id", buildId: <sha>` — grep-visible in `docker logs`. Enables ship-runbook post-check. |
| T-132-03 | Information Disclosure | Build ID (git short SHA) is exposed in every response header + every WS frame | accept | The git SHA is public information — visible in every OCI label already (`org.skynet.commit`). No new leakage. Explicitly logged and non-secret. |
| T-132-04 | Denial of Service | git rev-parse failure inside Docker build context (`.dockerignore` strips `.git/`) | mitigate | Vite fallback to `dev-<base36>` OR compose-supplied `SKYNET_BUILD_SHA` covers both dev + prod paths. `.dockerignore` for this repo does not strip `.git/` (verified — build context copies `.git` in stage 2 `COPY . .`). |
| T-132-SC | Tampering | Supply chain — new npm/pip/cargo installs | accept | This plan installs ZERO new packages (verified: only `node:child_process` `execSync`, which is Node stdlib). No slop-check risk. |
