<objective>
Widen `src/ui/state/bounty-counts-store.ts` so the internal keyed value is `{pinnedCount: number; needsDeskCount: number}` per (identityKey, hostId), and the public hook returns that pair. This is the frontend consumer of the widened WS response from Plan 26-01; nothing else changes about the store's semantics (same poller cadence, same focus listener, same invalidate piggyback, same per-target-error last-known preservation).

Per CONTEXT.md D-07 Claude's Discretion (whether to widen or split the hook): we widen the single existing hook to return the pair rather than splitting into two hooks. Rationale — both consumers (PrettyBountyCountBadge in Plan 03 and PrettyConversationsPanel filter in Plan 04) need BOTH counts at the same call site, so splitting would force each consumer to subscribe twice to the same composite key. Widening keeps a single subscription per (row, identity) and matches the row-badge's already-single call site pattern in `PrettyConversationRow.tsx:209-212`.

Purpose: Plan 03's combined `pin·desk` pill renders both numbers side-by-side per row; Plan 04's filter popover AND-intersects two predicates that each read one count. A single hook returning the pair serves both without duplicate WS subscriptions.

Output:
- Rename `useBountyCount` → `useBountyCounts` (plural) returning `{pinnedCount, needsDeskCount} | undefined`.
- Internal `Map<string, number>` widens to `Map<string, {pinnedCount: number; needsDeskCount: number}>`.
- `useAllBountyCounts()` widens its return type accordingly.
- `bountyCountsCompositeKey`, `refreshBountyCounts`, `startBountyCountPoller`, `invalidateIdentity`, `__resetBountyCountsForTest` — semantics preserved; only the internal value shape changes.
- `bounty-counts-store.test.ts` updated end-to-end; new test proves the widened pair round-trips + a test asserts a per-target error preserves the LAST-KNOWN PAIR (both counts) rather than only the pinnedCount.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-04 | Tampering | Malformed response entry missing `needsDeskCount` field | accept | Backend Plan 26-01 always emits both counts on every entry (fulfilled + rejected + host-not-found + group-failure). Frontend `refreshBountyCounts` widening reads `c.needsDeskCount` directly — a missing field becomes `undefined` and the pair-set would carry `undefined` in place of a number. TypeScript's compile-time check (`BountyCountResult.needsDeskCount: number`) is the mitigation at the API-type boundary; there is no separate runtime guard because the trust boundary is already validated at the WS handler layer. Single-tenant Skynet, so a runtime schema-drift risk is bounded to a fork-mismatched deploy which is a fleet-rebuild event not a security concern. |
