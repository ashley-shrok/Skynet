<objective>
Wire the PrettyConversationsPanel mount lifecycle to the server-side pinnedIds endpoint. On mount, fetch the current server-authoritative set via getPinnedIds and reconcile into the Zustand store via hydratePinnedIdsFromServer. This completes the round-trip: Wave 1 built the backend, Wave 2 wired the write path, this plan wires the read/hydrate path.

**Design decision — First-render UX (planner locks per 15-CONTEXT.md § Claude's Discretion):**
- **First-render behavior:** Option (a) — empty pinned tier that hydrates on fetch-complete. Locked over Option (b) fetch-blocking initial render. Rationale: (1) Perceived responsiveness — pins are additive; showing "no pins yet" briefly then popping them in feels faster than a blank-panel spinner, (2) the pin tier already renders as flat conditional list — an empty pin section rendering for ~50-100ms then re-rendering with items is a normal Zustand-store data flow (same pattern that fleetSessions and openTabs use), (3) CONTEXT.md § Claude's Discretion explicitly prefers this option, (4) matches the neighboring `addToActiveSet(selectedId)` effect at PrettyConversationsPanel.tsx:182-184 which fires on mount without blocking render.

**Design decision — Retry cadence on mount-fetch failure:**
- No explicit retry inside the mount effect — a failed GET leaves state.pinnedIds as-is (empty on first mount; whatever's in memory on subsequent mounts). The natural retry surfaces are (a) any subsequent pin/unpin click fires a PUT with the current in-memory set, which the server then persists — meaning even in the failure case, the FIRST write after mount will overwrite the server with the local set (which is empty on first mount, so Ashley loses no data), (b) the next remount fires a fresh GET. This matches CONTEXT.md § Deferred: "No offline queue / durable client-side retry beyond next-sync". If Ashley opens the app while server-down, she sees empty pins; when the server comes back and she pins something, the write goes through. This is acceptable for v1 per Ashley's greenlight.

Purpose: Complete the end-to-end persistence loop. After this plan lands + deploys, Ashley's pin on desktop survives tab close / browser close / hard-refresh / PWA close, and appears on her iPhone on next mount.
Output: Panel fetches on mount; store hydrates on success; existing tests remain green; one new integration test asserts the fetch-hydrate round-trip; baseline vitest count grows by at least 1.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Panel mount effect → getPinnedIds → axios → nginx → backend | Read-only fetch on mount; browser-side call inherits the authApi's JWT/cookie headers |
| Backend response → hydratePinnedIdsFromServer → Zustand store | Server-authoritative array replaces the local set; api-layer's runtime validation is the boundary check |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-12 | Spoofing | Mount fetch runs before auth cookie is set (401 race on cold reload) | mitigate | Silent-catch on the fetch — if 401 returns, pinnedIds stays empty this mount; the next remount (which happens naturally after auth completes) will succeed. No crash, no user-visible error |
| T-15-13 | Tampering | React 18 StrictMode double-mount in dev fires the effect twice and hydrates twice | mitigate | Cancel-token pattern: the first-mount cleanup sets cancelled=true before the second mount fires; the resolved response for the cancelled first-mount does NOT call hydrate. Second mount runs its own fetch fresh |
| T-15-14 | Tampering | User navigates away from the panel before the fetch resolves; a stale response later hydrates a re-mounted panel | mitigate | Cancel-token on cleanup; the effect's cancelled boolean is captured per-mount, so a stale promise from an unmounted effect early-returns before touching state |
| T-15-15 | Information Disclosure | Backend response bloats to include other users' pins (regression in Wave 1) | mitigate | api layer only extracts pinnedConversationIds field via runtime `Array.isArray + every typeof string` check — any other field is ignored. Wave 1's WHERE-clause scoping is the primary defense |
| T-15-16 | Denial of Service | Mount fetch is on the critical render path; a hung server blocks the panel | accept | Fetch is async and non-blocking — the panel renders with empty pinnedIds and hydrates when the fetch resolves. Ashley sees the panel immediately with all fleet/open-tab rows; pin tier just appears empty until fetch resolves. Slow-server latency is exposed only as "pins take a beat to appear" |
| T-15-SC | Tampering | npm/pip/cargo installs | accept | No new dependencies added this plan — only existing @/api/user-preferences-api and @/ui/state/conversation-store are imported |
</threat_model>
