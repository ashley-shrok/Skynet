<objective>
Wire the Zustand conversation-store to the server-side pinnedConversationIds endpoint from Wave 1. Every pinConversation/unpinConversation call fires an optimistic UI update AND a fire-and-forget PUT to /user-preferences. A new hydratePinnedIdsFromServer setter accepts the server-authoritative set (called by Wave 3's panel mount effect) and reconciles it into the store. On PUT failure, the optimistic UI persists (per PIN-05 locked semantics: no rollback — retry on next sync).

**Design decision — Client integration pattern (planner locks per 15-CONTEXT.md § Claude's Discretion):**
- **Where the fetch lives:** Panel mount-effect ONLY (implemented in Wave 3). Rationale: PATTERNS.md § 5 lists three reasons — (1) mount fires after AuthManager is initialized, (2) no dependency on axios-instance being ready at module load, (3) mirrors the existing `addToActiveSet(selectedId)` neighbor effect at PrettyConversationsPanel.tsx:182-184. No module-init fetch — keeps the store pure and testable.
- **Optimistic reconciliation on error:** Leave optimistic update; retry on next sync (LOCKED by CONTEXT.md § Persistence semantics, not a discretion — but the retry MECHANISM was open). Retry mechanism: no pendingMutations queue — the natural retry cadence is (a) next pin/unpin fires a fresh PUT with the current set which includes the previously-failed mutation, and (b) next panel mount fires a fresh GET which reconciles from the server. This matches CONTEXT.md § Deferred ("No offline queue / durable client-side retry beyond next mount / next mutation"). Simpler than a queue, no state to leak.
- **Store mutator shape:** Variant B from PATTERNS.md § 4 — try/catch around the fire-and-forget `void putPinnedIds([...nextPinnedIds])` call, matching `addToActiveSet` at conversation-store.ts:713-722 exactly. State mutation + notify() run AFTER the try/catch (both variants have identical UI semantics; Variant B is chosen for literal parallelism to the sessionStorage precedent — one convention across all mutators).

Purpose: Land the persistence integration in the store — Wave 3's panel-mount fetch has a well-typed hydrate setter to call, and every existing pin click on the mounted panel now writes to the server.
Output: Store fires network writes on pin/unpin (verified by mocked-spy in tests); tests 30j-30o pass; existing 44+ store tests unaffected.
</objective>
