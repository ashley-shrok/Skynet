<objective>
Add server-side persistence for pinned conversation IDs by extending the existing `/user-preferences` endpoint with a `pinnedConversationIds: string[]` field, backed by a new nullable TEXT column on the `user_preferences` table storing a JSON-serialized array. This is the backbone that fixes the concrete bug Ashley hit: pins die on tab/PWA close because they live only in Zustand memory.

**Design decision — Storage shape: Option B (JSON column on user_preferences)**
Locked over Option A (new pinned_conversations table). Rationale:
1. pinnedIds is semantically a flat opaque Set<string> with no per-pin metadata, ordering, or timestamps (per 15-CONTEXT.md § Scope fences — locked "No pin-ordering, pin-groups, pin-labels, or pin-metadata").
2. Migration is trivially safe via the existing `addColumnIfNotExists` helper at `src/backend/database/db/index.ts:670-674` (already used for theme/font_size/accent_color/language on this exact table). One new call adds the column on next boot with no risk to existing rows.
3. Set-size is 1 (single-tenant Skynet); a whole table for one row per user is over-engineered for this scope.
4. Read-modify-write semantics fit naturally with the existing PUT contract that already does upsert on the same row.

**Design decision — Endpoint shape: Option A (extend /user-preferences)**
Locked over Option B (new /user/pins) and Option C (extend /identities). Rationale:
1. **Zero nginx changes.** The existing `location ~ ^/user-preferences(/.*)?$` block at `docker/nginx.conf:258` and `docker/nginx-https.conf:265` already routes /user-preferences/* to backend :30001. Option B would require adding `^/user-pins(/.*)?$` blocks in BOTH nginx configs (CLAUDE.md nginx caveat) — real risk, small avoidable surface.
2. **Zero new auth wiring.** The existing PUT handler at `user-preferences.ts:79` already runs `authenticateJWT` middleware and extracts `userId` from `(req as AuthenticatedRequest).userId` (line 80). PIN-07 (401-for-unauth) is inherited for free — no new middleware invocation to review.
3. **JSON body, response echoes state.** The existing PUT already returns `res.json({ success: true, ...updates })` at line 144 — the response body includes the persisted values. Extending it to include `pinnedConversationIds` in the response gives the client optimistic reconciliation without a follow-up GET (PIN-08 JSON branch).
4. **Option C (identities) rejected by inspection** — multipart/form-data trap from patch #77 (silent-200 no-op with wrong field name). JSON path avoids it entirely.

Purpose: Land the schema column + endpoint contract + direct-handler tests so Wave 2 (store integration) and Wave 3 (panel wire-up) can consume a stable server surface.
Output: `/user-preferences` GET returns `{...existing fields, pinnedConversationIds: string[]}`; PUT accepts and persists the same shape; test suite validates all branches.
</objective>
