## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser history/hashchange events → mobile-flow listeners | The browser can fire popstate/hashchange from user gestures OR from replaceState calls made elsewhere in the app (URL-sync effect). The listener must distinguish "user pressed back" from "app updated URL," or downstream navigation will fire spuriously. |
| URL fragment ↔ mobile-flow state | The fragment is a public surface (user can bookmark it, share it, paste it). A malformed `mv=` value must not crash the flow. |
| ConversationsPanel row tap (mobile) → navigateToView | The row's existing onSelect callback (Plan 06-01) now composes with navigateToView. Any drop between the two would leave the user on the list screen with a selected conversation invisible in the view — a confusing state to escape from. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|

The existing `tab=`, `active=`, `only=` keys are untouched. `mv` chosen as short and unlikely to collide with any future URL param. Test round-trip: `encodeWorkspaceSpec(consumePendingWorkspace())` idempotent when `mv=1` present. |
| T-06-03-02 | Denial of Service (popstate re-entry loop) | mobile-flow.ts hashchange listener | mitigate | The listener reads the current fragment and compares to internal state before setting; if unchanged, skip. navigateToView / navigateToList call `window.history.pushState` (view) / `window.history.back()` OR `replaceState` (list) — never both, so no push-then-pop loop. **Step B — Create `src/ui/lib/mobile-flow.ts`:**

Design: a small module with a subscription mechanism (matches identities-store / conversation-store patterns from Plan 06-01), plus a React hook backed by useSyncExternalStore, plus imperative action functions.

Module-scoped state:
```
type MobileScreen = "list" | "view";
let currentScreen: MobileScreen = readScreenFromLocation();
const emitter = new EventTarget();

function readScreenFromLocation(): MobileScreen {
  if (typeof window === "undefined") return "list";
  const params = new URLSearchParams(window.location.hash.slice(1));
  return params.get("mv") === "1" ? "view" : "list";
}
```

On module load, register `window.addEventListener("hashchange", handleHashChange)` and `window.addEventListener("popstate", handleHashChange)` where handleHashChange recomputes currentScreen and emits if changed. Guard with `typeof window !== "undefined"` so the module can be imported in Vitest without DOM.

Public API:

- `export function useMobileScreen(): MobileScreen` — useSyncExternalStore wrapper.

- `export function navigateToView(): void`:
  ```
  const url = new URL(window.location.href);
  const hashParams = new URLSearchParams(url.hash.slice(1));
  if (hashParams.get("mv") === "1") return; // already there
  hashParams.set("mv", "1");
  const nextHash = "#" + hashParams.toString();
  const nextUrl = url.pathname + url.search + nextHash;
  window.history.pushState({}, "", nextUrl);
  // pushState does NOT fire hashchange; manually recompute + emit
  currentScreen = "view";
  emitter.dispatchEvent(new Event("change"));
  ```

- `export function navigateToList(): void`:
  ```
  // Prefer window.history.back() so the browser back-stack stays consistent with the user's mental model. But only if the previous history entry is our own list state — if the user got here via a fresh navigation (pasted mv=1 URL), history.back() would leave the page entirely.
  // Heuristic: if window.history.state has our sentinel from navigateToView, use back(); otherwise strip the fragment key via replaceState.
  const state = window.history.state;
  if (state && (state as { __termixMobileView?: boolean }).__termixMobileView) {
    window.history.back();
    // popstate will fire; the listener recomputes currentScreen from location
  } else {
    const url = new URL(window.location.href);
    const hashParams = new URLSearchParams(url.hash.slice(1));
    hashParams.delete("mv");
    const nextHash = hashParams.toString() ? "#" + hashParams.toString() : "";
    const nextUrl = url.pathname + url.search + nextHash;
    window.history.replaceState({}, "", nextUrl);
    currentScreen = "list";
    emitter.dispatchEvent(new Event("change"));
  }
  ```
  Actually — simplify: pushState with a sentinel state object on navigateToView, and always window.history.back() on navigateToList (which fires popstate; the listener recomputes). Handle the "pasted-URL" edge case with a first-render check: if page loads with mv=1 and no prior state, navigateToList will hit "back leaves the page." Accept this tradeoff — the user pasted a mobile-view URL, back exits, that's reasonable behavior. Document in the summary and add a comment in code.

  Simpler alternative that avoids the edge case: always use replaceState (both navigateToView and navigateToList), and let the SITE-LEVEL back button do the semantic "go to list" via calling navigateToList directly. Browser back then behaves like "go to previous page." This is LESS Telegram-like but avoids the history-stack complexity. **Decision: use pushState in navigateToView + history.back() in navigateToList. The one edge case (pasted URL with mv=1 + browser back exits) is acceptable per the shape's "browser back also works" requirement — a pasted mobile-view URL landing directly in the view is a valid deep-link, and back leaving the app is the standard browser behavior.**
