<objective>
Cut the frontend over from the two retired feeders (PTY-scraping ttyBusy + backgrounded_agents/shells WS-frame hasBgWork) to the new backend-authoritative fleet-status channel. This is the final structural change of Phase 34 and the one that actually eliminates the accumulated signal-quality noise (harness bottom-bar redraws polluting PTY-idle; sibling-tmux status-line refreshes flapping WIP; hidden-pane WS drops freezing the signal). After this plan lands, the composite isWorking formula sourced from the box-side session JSON per D-CTX § Composite state is the single source of truth. The WaitingBubble (Plan 03) is mounted for the harness-waiting state.

Purpose: The payoff plan. Every earlier plan (01 watcher, 02 backend, 03 waiting bubble, 04 deploy transport + Stop hook + nginx, 05 external ambient-tagging gate) exists so this cutover can happen safely. This plan MUST NOT execute until Plan 05's `resume-signal` is received, otherwise the composite isWorking will be permanently true for every identity in the fleet (persistent Monitors would count as non-ambient background work without the tag).

Output: New fleet-status browser client + rewired session-working-store + new session-waiting-store + PrettyView WaitingBubble mount + retirement of feeder call sites in Terminal.tsx and PrettyView.tsx + AppShell boot-time WS mount + end-to-end integration test proving the whole pipe.

Non-goal: This plan does NOT touch per-pane WS lifecycle beyond removing the feeder call sites. Does NOT touch dot semantics (LOCKED by Ashley 2026-07-23). Does NOT touch patch #433's 60s WS-close debounce (orthogonal, stays). Does NOT retire the backgrounded_agents / backgrounded_shells WS frames themselves — PrettyView still renders the BackgroundedAgentsPanel + BackgroundedShellsPanel from those frames as UI surfaces (Task 4 verifies this).
</objective>
