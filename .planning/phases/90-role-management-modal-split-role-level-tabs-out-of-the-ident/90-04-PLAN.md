<objective>
Create the new `RoleModal` component: a global-viewport modal (portals to `document.body`) addressed by role name, wearing the role's own hue, hosting the four tabs that used to live in the identity modal's role scope (role file / runbooks / bounties / wakeups). Add the role-file tab's cosmetic edit block (`RoleCosmeticEditBlock` — Title + ColorPicker + VoicePicker + avatar generator, MINUS the inherit/override affordance layer that Identity modal carries).

Purpose: implements the load-bearing D-01 (role cosmetic edit UI belongs here), D-03 (global modal, portals to document.body), D-06 (role modal chrome wears role's own hue), D-09 (new component, not IdentityModal reparametrized). This is the surface the roles-list modal (Plan 90-05) opens on row click AND the surface the identity-modal title-line jump (Plan 90-06) opens.

Output: three new component files + companion test.

## Wave-2 identity-shim (planner note)
The existing bounties + role-scope wakeups + role-file-read WS wire types (`identity:list-bounties`, `identity:list-role-wakeups`, `identity:get-role-file`) are all identity-keyed. Plan 90-03 added a role-name-keyed WRITE path (`role:update-file`), but adding role-name-keyed READ variants for THREE wire types would balloon this phase. Discretion-pick: for read paths in this plan, `RoleModal` accepts an `identityShimKey` prop — the caller (RolesListModal for row click, PrettyView for identity-modal title-line jump) resolves ANY identity holding the target role on the selected host and passes its key. If the selected host has no identities holding the role (edge case only — post-Phase-86 every role on a host is typically held by at least one identity), the modal renders an error state on the affected tabs and disables save. This is a wire-shim, not a semantic tie: the modal never displays identity data, and the shim key is invisible to the user. Future Phase can add role-name-keyed READ variants; this phase does not.
</objective>
