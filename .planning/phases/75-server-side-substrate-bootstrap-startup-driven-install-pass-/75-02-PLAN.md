<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| orchestrator → runSweepForHost | orchestrator invokes runSweepForHost with `channel` from acquireChannel. runSweepForHost has a documented never-reject contract; the orchestrator adds defense-in-depth try/catch anyway. |
| orchestrator → logPersistentFailure | new log-tag surface. Payload must never include credential material. The orchestrator only passes `{fleetHostId, hostName, consecutiveFailures}` — no credentials, no key material. |
| orchestrator internal state ↔ SIGTERM | stop() must clear state deterministically or the persistentAlertFired Set could leak across container-restart tests in the same Node process. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-75-02-01 | Denial-of-service | An unbounded consecutiveFailures Map grows if the same failed host is retried thousands of times over container lifetime | accept | Map is keyed by fleetHostId (bounded by DB row count — small in practice, dozens at most). Map values are small integers. Growth is O(hosts), not O(failures). |
| T-75-02-02 | Tampering | logPersistentFailure payload could contain arbitrary strings if hostName is attacker-controlled | mitigate | hostName comes from the DB hosts.name column, which is operator-set (not attacker-set). Log injection surface is limited to structured-log fields consumed by our log pipeline (JSON-encoded — no shell interpolation). Never-log-credentials invariant holds because credentials are not passed to logPersistentFailure. |
| T-75-02-03 | Repudiation | Persistent failures could be missed if logPersistentFailure only fires once per uptime and the alert is lost | accept | D-07 explicitly locks the once-per-uptime semantic. Operator alerting is downstream of the structured log surface — that's a separate concern for a monitoring plan, not this phase. Retries continue forever, so no data loss. |
| T-75-02-04 | Information disclosure | runSweepForHost is called with a live SSH channel; if runSweepForHost throws an unexpected error containing credential material and the catch propagates it into logSweepHookError, credentials could leak into logs | mitigate | logSweepHookError already scrubs — it only accepts `{fleetHostId, hostName, errorMessage}` where errorMessage is `err.message` (never `err.stack` or full serialization). Existing pattern from Phase 72/73 which is production-vetted. Defense-in-depth: this plan does not change logSweepHookError. |
| T-75-02-05 | Denial-of-service | Startup pass is serial (D-01); a single hanging host blocks all subsequent hosts | accept | D-01 explicitly locks serial. `acquireChannel` and `runSweepForHost` have their own SSH-timeout semantics (via `connectOneShot`); if a host hangs at TCP-connect, it errors out after the standard SSH timeout. The 75-05 plan wires `acquireChannel` using the existing `connectOneShot` + `execCommand` composition which already handles timeouts. |
| T-75-02-06 | Tampering | Fire-and-forget install-pass errors could surface to some caller (e.g., host-create HTTP response) leaking internal machinery detail | mitigate | This plan's `sweepOneHost` has a never-reject contract enforced by test NT2 (`await expect(orch.sweepOneHost(h)).resolves.not.toThrow()`). Plan 75-06 further wraps the call in try/catch inside the queueMicrotask body. Two layers of defense-in-depth. |

**Load-bearing security invariant (from RESEARCH.md § threat model surface):**
- `runSweepForHost` never-reject contract must be preserved throughout — introducing a path that could throw uncaught into the fire-and-forget queueMicrotask would take down the orchestrator. Enforced by test NT1 (rejecting mock → logSweepHookError called, no exception escapes) and NT2 (sweepOneHost never rejects).
</threat_model>
