<objective>
Create the session-less host enumerator that the server-context orchestrator will call. The existing `listIdentityHostingHosts` in `starter.ts:378-442` is unusable here because it requires `currentSubscriberUserId` (set by `registry.onFirstSubscriber` — a browser-session concept). The new module builds the same shape of return value but uses CSKEK-based decryption instead of per-user DEK, so it works at container boot with zero users logged in.

This is a shared dependency that 75-02's orchestrator consumes and 75-05's starter.ts wiring injects. Building it as its own module (rather than inline inside starter.ts) makes it independently unit-testable with mocked DB + mocked SystemCrypto, and keeps starter.ts's boot IIFE from bloating further.

Purpose: Deliver D-08 (CSKEK-only decrypt), D-10 (non-substrate hosts untouched — enforced by the WHERE clause narrowing), and half of D-17 (the input-side of the startup-pass integration test).

Output: New enumerator module + comprehensive tests + defense-in-depth filters for the edge cases the API-layer guard (75-04) is supposed to prevent but which the enumerator can't assume have been enforced (e.g., pre-existing data before the 75-04 guard shipped).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| module → SystemCrypto | reads CSKEK Buffer from SystemCrypto singleton. CSKEK MUST never leave this module in any observable form (log, exception, return value). |
| module → sshCredentials table | reads ciphertext from system_* columns. Ciphertext values are safe to log at debug; plaintext is NEVER logged. |
| module → orchestrator | returns SubstrateHostRecord[] containing plaintext credentials in _connDetails. The consumer (75-02 orchestrator) passes these to `connectOneShot` and the SSH channel — never to any log surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-75-03-01 | Information disclosure | Plaintext credentials could leak via log calls if the per-host catch serializes the wrong error | mitigate | Per-host catch only logs `err.message` (matches production logSweepHookError shape). Test S1 + S2 assert no CSKEK or plaintext appears in any log call across the test suite. |
| T-75-03-02 | Information disclosure | CSKEK Buffer could be included in an error object if a nested library throws it in its message | mitigate | CSKEK is derived by SystemCrypto ~200 lines from where it is consumed; the FieldCrypto layer accepts the Buffer as an argument but does not include it in error messages. Test S1 asserts this at the module boundary. |
| T-75-03-03 | Elevation of privilege | An attacker who can insert rows into `hosts` table with `runsFleetSubstrate=true AND credentialId → their own sshCredentials row` could get the orchestrator to SSH into that host with credentials derived by the server | accept | Row-level write access to the DB IS already root-equivalent — attacker who can write to `hosts` can do arbitrary things. This threat exists before Phase 75 and is not made worse by this plan. |
| T-75-03-04 | Tampering | A malicious hosts row could point credentialId to a non-substrate user's sshCredentials row — enumerator would happily decrypt with CSKEK if the system_* columns are populated | mitigate | The `sshCredentials.userId` column is projected in the query result (as `cred_userId`) so a downstream audit tool can cross-check. Plan 75-04 additionally enforces that host and credential owners must match at CREATE time. For pre-existing rows, this is caught by the migration (75-08) refusing to touch a credential whose sshCredentials.userId doesn't match any of the operator-provided input entries. |
| T-75-03-05 | Denial-of-service | A single very slow FieldCrypto.decryptField call could stall the enumerator | accept | FieldCrypto uses synchronous crypto.createDecipheriv — CPU-bound, fast (microseconds per field). Enumerator is called from a 30s tick (75-02) so the whole enumeration budget is generous. |
| T-75-03-06 | Repudiation | The four warn log tags could be swallowed by a downstream log filter | accept | Log-tag naming follows the `fleet_substrate_*` convention — operators already monitor for this prefix. Alerting on these tags is downstream, not this plan's concern. |

**Load-bearing security invariant:** The enumerator NEVER calls `DataCrypto.getUserDataKey()` — enforced by grep gate (returns 0 hits). This is what makes it session-less and what makes D-08 real.
</threat_model>
