<objective>
Wire the on-add trigger and the flag-flip / credentialId-change triggers into the host route handlers. This is what makes D-02 real: a freshly-provisioned substrate host doesn't wait for the 30s retry tick — the sweep fires immediately as fire-and-forget, so the sweep is typically finished by the time the operator refreshes their host list.

The wiring is small in code volume but load-bearing in security: this is the boundary where "fire-and-forget install-pass errors must NEVER surface to the host-create HTTP response" is enforced. The wrapper is deliberately paranoid: null-check on the singleton (test/boot-race safety), try/catch around the sweepOneHost call (defense-in-depth on top of the 75-02 never-reject contract), no error propagation to the response object.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| POST /host/db/host handler → substrate orchestrator | authenticated HTTP request triggers a background sweep. Sweep runs with the orchestrator's CSKEK-level credential access — the caller of POST does NOT need decrypt authority for that credential; the orchestrator holds it. |
| PUT /host/db/host/:id handler → substrate orchestrator | same as POST but on update — flag-flip and credential-rotation are the trigger conditions. |
| queueMicrotask body → HTTP response | fire-and-forget contract: NO sweep result, NO error, NO log line can flow back into the HTTP response. Enforced by the microtask running AFTER res.json() resolves. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-75-06-01 | Information disclosure | Fire-and-forget sweep error surfaces to HTTP response, leaking internal machinery or credential-decrypt failure hint | mitigate | Trigger runs INSIDE queueMicrotask AFTER res.json() has resolved. Even if sweepOneHost threw synchronously (impossible per 75-02 NT2, but paranoid), the outer try/catch swallows. Test T4 asserts the response body is unaffected by a sweepOneHost throw. |
| T-75-06-02 | Denial-of-service | Attacker POSTs many substrate hosts to spike SSH load | accept | Same DoS surface as any authenticated write endpoint. Rate-limiting is an existing framework concern, not this plan. The orchestrator's serial-per-host contract limits concurrent sweeps naturally. |
| T-75-06-03 | Elevation of privilege | An operator without decrypt authority on the credential could nonetheless trigger a sweep that uses CSKEK-level decrypt | accept | This is INTENTIONAL per D-09: the whole point of Phase 75 is that the system itself decrypts substrate credentials without requiring the owner to be present. An authenticated write on a host is already authorized to modify that host — a background sweep with system credentials is a natural consequence. |
| T-75-06-04 | Tampering | Concurrent POST + PUT of the same hostId race — two microtasks both call sweepOneHost concurrently | mitigate | 75-02's sweepInFlight Set gates concurrent sweepOneHost calls for the same host id. Second call is a no-op (test G2). Pitfall 4 in RESEARCH.md called out this exact race; the Set is the mitigation. |
| T-75-06-05 | Repudiation | Null-orchestrator log line hides that a sweep didn't happen | accept | Log line at `fleet_substrate_on_add_no_orchestrator` explicitly names the miss. Operator monitoring for that tag would surface an unusual concentration of misses (indicates the orchestrator failed to initialize on boot — a real problem worth alerting on). |
| T-75-06-06 | Denial-of-service | An unhandledPromiseRejection from the microtask crashes the Node process (default Node behavior on some versions) | mitigate | The outer try/catch inside the microtask body catches synchronous throws AND awaited-promise rejections. Test T5 asserts no unhandledRejection is raised. |
| T-75-06-07 | Denial-of-service | Fetching the BEFORE-state in PUT adds a DB roundtrip to every PUT request, even non-substrate ones | accept | Single indexed lookup by primary key — microseconds. Cost is negligible. Alternative (only fetch when runsFleetSubstrate is in the body) is possible but adds branching complexity for negligible savings. |

**Load-bearing security invariant (from RESEARCH.md § threat model surface):**
- "Fire-and-forget install-pass errors must NEVER surface to the host-create HTTP response" — enforced by: microtask ordering (runs after res.json), null-check on singleton, defense-in-depth try/catch. Tests T3/T4/T5 assert all three defenses.
- "runSweepForHost never-reject contract must be preserved throughout" — this plan does not call runSweepForHost directly; it calls sweepOneHost which wraps it. 75-02 test NT2 proves sweepOneHost's never-reject contract.
