<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container boot → orchestrator.start() | first moment the CSKEK path is exercised at scale. Called fire-and-forget — the container is considered ready immediately after the singleton is populated; the pass runs in the background. If start() throws (unexpected — the module has never-reject contracts, but defense-in-depth matters), the container still boots; the .catch() logging at operation `fleet_substrate_orchestrator_start_failed` surfaces the failure. |
| SIGTERM → orchestrator.stop() | graceful shutdown. If the interval isn't cleared, Node won't exit. |
| starter.ts → substrate-orchestrator-singleton | writer/reader indirection. If another module (e.g., a test harness) also calls setSubstrateOrchestrator, the last write wins (see singleton test SG4). Production has exactly one writer (starter.ts). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-75-05-01 | Denial-of-service | Startup pass consuming excess time delays container readiness | mitigate | Fire-and-forget `substrateOrch.start().catch(...)` (NOT awaited) lets the container be ready immediately while the pass runs in the background. This aligns with D-01's "runs at container start" (which does NOT mandate blocking boot on completion). If future health checks need to gate readiness on the pass, that is a separate plan. |
| T-75-05-02 | Denial-of-service | Retry-tick setInterval leaked if SIGTERM handler doesn't fire (e.g., SIGKILL) | accept | SIGKILL bypasses all cleanup by definition; Node process death releases everything. Non-issue. |
| T-75-05-03 | Information disclosure | connectOneShot could log the plaintext credential from host._connDetails | accept | connectOneShot is the same production code used by fleet-status; if it had a leak, fleet-status already has the same leak. Not this plan's scope to fix an existing behavior. |
| T-75-05-04 | Tampering | Test harness could set the singleton to a malicious orchestrator and route real host-create sweeps through it | mitigate | The `__resetSubstrateOrchestrator` accessor is clearly tagged "Test-only" in the singleton module. Production callers use only set/get. Real defense: `process.env.VITEST !== "true"` gate on the boot IIFE means production paths and test paths cannot coexist in the same process. Singleton test SG4 documents last-write-wins semantics explicitly. |
| T-75-05-05 | Repudiation | If start() silently rejects and .catch() somehow doesn't fire, no evidence of the failure | accept | .catch() on a Promise is language-guaranteed. If Node's event loop is dead, we have bigger problems. |
| T-75-05-06 | Elevation of privilege | Substrate orchestrator has CSKEK-level access to all substrate credentials; if the module has a bug, it could exfiltrate | mitigate | The orchestrator only uses credentials to invoke `runSweepForHost` which sends bytes to a specific SSH channel per-catalog-item. No arbitrary code execution surface. Never-log discipline enforced by 75-02/75-03 test suites. |
