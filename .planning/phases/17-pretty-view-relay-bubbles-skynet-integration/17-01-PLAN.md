<objective>
Extend the backend session-file parser to detect Matrix relay activity in
Claude Code JSONL turns and emit two new WS event kinds (`relay_outbound`,
`relay_inbound`) alongside the existing `message` / `image` / etc frames.
Port the three regexes byte-for-byte from the validated prototype
(`OUTBOUND_CURL_RE`, `OUTBOUND_PUT_RE`, `OUTBOUND_URL_RE`, `INBOUND_REGEX`)
so the 6/6 acceptance-battery detection contract carries into Skynet
unchanged.

Purpose: Detection has to happen backend-side because the current parser
actively strips `tool_use` blocks (never surfaced) and skips
`<task-notification>`-only user turns (drops them as `harness_wrapper`).
The frontend cannot detect what it never receives. Emitting typed
`relay_*` events keeps the wire small (structured room/body/sender fields
instead of raw JSONL) and keeps the byte-shape regex source of truth in
one place.

Output: `parseSessionLine` gains two new `ParsedLine` variants,
`claude-session-server.ts` emits matching WS frames, and the client's
`ClaudeSessionServerEvent` union is extended so downstream plan 17-03
compiles against strongly-typed events. Unit-tested against the same six
cases Ashley walked through in the prototype 2026-07-28.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| JSONL session file → backend parser | Session file is written by Claude Code on remote host. Content is agent output + user typing — user-controlled text traveling to Skynet backend. |
| backend WS → browser client | Skynet emits relay body over WebSocket to the browser. Body is embedded in DOM via React rendering (auto-escaped). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-01-01 | Tampering | detectRelayOutbound regex | mitigate | Regexes are ported byte-for-byte from prototype's 6/6 validated conjunction — loose variants explicitly rejected (see acceptance battery). Unit tests 2 + 3 lock the false-positive gates. Byte-verbatim `grep -Fq` acceptance criteria block any silent loosening at code-review time. |
| T-17-01-02 | Information Disclosure | rawCommand field in relay_outbound WS frame | accept | rawCommand contains the full Bash command including any curl args (may include tokens if the agent inlined a bearer). Same disclosure surface the tmux pane already has — pretty view is a rendering of what's already in the session file. No new attack surface. Comment this in code so a future reviewer understands the tradeoff. |
| T-17-01-03 | Denial of Service | catastrophic regex backtracking | mitigate | All four regexes use bounded character classes (`[^\/\s'"]+` not `.*`) so REDOS is not possible on adversarial input. Verified in code review. |
| T-17-01-04 | Spoofing | Bash tool_use command claims to be a relay send | accept | Detection is descriptive not prescriptive — if a `tool_use` turn LOOKS like a relay send, it IS a relay send from the tmux session's perspective. The browser render mirrors that ground truth. Not a security boundary. |
| T-17-01-SC | Tampering | npm package installs | mitigate | This plan installs zero new packages — extends existing parser + WS server + type file only. No slopcheck needed. |
</threat_model>
