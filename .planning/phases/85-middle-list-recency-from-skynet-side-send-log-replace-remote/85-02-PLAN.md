<objective>
Create the single backend module that owns all reads and writes to the
`identity_send_log` table. Every plan downstream of this one (03: HTTP
endpoint, 04: orchestrator swap, 05: sessions.ts swap) consumes this
module's two exported functions.

Purpose: A single seam for the store operation keeps the forceSave
invariant, the monotonic-write invariant, and the structured-logging
convention in ONE place. Downstream consumers don't need to remember to
call forceSave — the store does. Downstream consumers don't need to
guard against regressing an older stamp — the store does.

Output: `identity-send-log-store.ts` with two exports and a companion
`.test.ts` covering insert-new, update-existing, monotonic-skip,
read-missing, read-hit, and the forceSave call fires exactly once per
write (mocked via spy).
</objective>

    - Export `async function stampIdentityLastSend(identityName: string, ts: number): Promise<void>`:
      - Validates: identityName is a non-empty string; ts is a finite positive number. On invalid input, log warn with structured context and return without throwing (matches D-05 "attempts count" spirit — a bad input is not a failure worth propagating up the send funnel).
      - Reads current row via `db.select().from(identitySendLog).where(eq(identitySendLog.identityName, identityName))`.
      - Monotonic guard: if a row exists AND `row.lastSendAt >= ts`, log info (`operation: "identity_send_log_stamp_skip_monotonic"`, includes identityName, ts, currentTs) and return without writing (no forceSave call — nothing was written).
      - Otherwise, upsert via drizzle's `.onConflictDoUpdate({ target: identitySendLog.identityName, set: { lastSendAt: ts, updatedAt: sql\`CURRENT_TIMESTAMP\` } })` — insert path fires for the first-ever call for an identity, update path fires for subsequent calls.
      - After the write, awaits `DatabaseSaveTrigger.forceSave("phase-85-stamp-identity-send")` inside try/catch. On save failure, log warn with structured context; do NOT propagate.
      - Logs info on the write path with `operation: "identity_send_log_stamp"`, identityName, ts, previousTs (or null if new row).
    - Export `async function getIdentityLastSend(identityName: string): Promise<number | null>`:
      - Reads row via `db.select({ lastSendAt: identitySendLog.lastSendAt }).from(identitySendLog).where(eq(identitySendLog.identityName, identityName)).limit(1)`.
      - Returns `row?.lastSendAt ?? null`.
      - Logs debug on hit (`operation: "identity_send_log_get_hit"`, identityName, ts); no log on miss (would be too chatty — this is called per-tick per-session by the orchestrator).
      - Never throws for a routine miss. If drizzle itself throws (extremely unlikely — the table exists), catch, log warn, and return null (fail-open — the row's absence looks the same as a query failure to the middle-zone comparator).
    - Neither function opens its own transaction — drizzle's auto-commit-per-statement is sufficient. The forceSave call is the flush boundary.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → stampIdentityLastSend | Untrusted input from downstream (Plan 03 HTTP route receives external input from the frontend). Identity name is a text primary key — a maliciously long or non-UTF-8 name reaches the DB. |
| store → DB | Trusted — drizzle parameterized queries prevent injection. |
| store → forceSave | Trusted — internal utility, no external input. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-85-02-01 | Injection | identityName column | mitigate | Drizzle's parameterized `.where(eq(identitySendLog.identityName, identityName))` prevents SQL injection. NO raw string interpolation in the store module. |
| T-85-02-02 | DoS | unbounded identity name length | mitigate | Validate identityName as non-empty string in `stampIdentityLastSend`. Add a length ceiling (e.g., reject > 256 chars) — this is a stricter bound than any legitimate tmux session name. Log warn on rejection. |
| T-85-02-03 | Tampering | monotonic-guard bypass | mitigate | The monotonic guard runs inside the same async transaction context as the read + write. A concurrent write from another Node.js turn is impossible in single-threaded JS; between async boundaries, worst case is a stale read → older ts wins by 1 tick, corrected on the next send. Not a security concern. |
| T-85-02-04 | Information Disclosure | log output | accept | Identity names are logged in operation-scoped structured logs. Same trust model as every other backend module logs (hostId + identityName appear widely already). |
| T-85-02-05 | Repudiation | write without audit trail | accept | The `updatedAt` column + info log line at write time provides an audit trail. Skynet does not require a full audit-log entry for compose-surface sends. |
| T-85-02-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages. Consumes existing drizzle + DatabaseSaveTrigger. Audit-clean. |
</threat_model>
