<objective>
Hook the frontend universal compose-send funnel to (a) fire a backend POST
to /identity-send-log/stamp on every send-attempt (D-04, D-05), and (b)
call `advanceSessionLastMessageAt` on the working store for instant local
row reorder (D-06). Attempts count regardless of delivery success. Every
compose-surface button counts automatically because the hook is on the
single funnel (D-03).

Purpose: Without this plan, the store never fills — the backend derivation
swap (Plans 04+05) reads an empty table, and the middle-zone falls
through to insertion-order forever. This plan is the source of the signal.
The optimistic client stamp (D-06) makes the reorder happen on the same
React frame as the send, not 2 seconds later on the next fleet-status
poll cadence.

Output: A new small API client for the POST; the useComposeSend hook
enhanced with both calls; test coverage proving every send path — text
submit + reset + thumbs-up + recap + quick-send — fires exactly one
backend POST + one optimistic advance per send.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-85-06-01 | Denial of Service | POST fires per send | accept | One POST per send action. Ashley is single-user, single-device active at a time. Even the busiest send burst is ~1/s. No rate limit needed. |
| T-85-06-02 | Tampering | client sends fake identityName | mitigate | Backend route (Plan 85-03) validates identityName. The client-side call passes the identityName prop verbatim; a malicious modification of that prop in browser devtools would only affect Ashley's own middle-zone ordering (single-tenant), not other users. Not a security concern for this deploy. |
| T-85-06-03 | Information Disclosure | log line leaks identityName | accept | Same discipline as every other pretty-view log. |
| T-85-06-04 | Repudiation | client-side stamp fires without backend ack | accept | Optimistic stamp is intentional (D-06). If the backend POST fails, the local stamp still applies for the sending device; the other device sees the old value until Ashley's next send succeeds. Acceptable per D-10 (multi-device consistency is best-effort within 2s poll cadence, and the sending device sees the change instantly). |
| T-85-06-05 | Elevation of Privilege | client bypasses auth | mitigate | The POST rides on the existing session cookie via authApi (same auth surface as every other Skynet frontend API call). Route rejects unauthenticated calls (Plan 85-03 Test 1). |
| T-85-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages. Consumes existing authApi + vitest infrastructure. Audit-clean. |
</threat_model>
