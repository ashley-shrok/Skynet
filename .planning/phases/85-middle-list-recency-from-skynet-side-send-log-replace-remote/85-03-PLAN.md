<objective>
Expose the store's `stampIdentityLastSend` as an authenticated HTTP endpoint
so the frontend compose-send funnel (Plan 85-06) can fire a fire-and-forget
POST on every send-attempt.

Purpose: Multi-device consistency (D-10) requires the write to live on the
backend, not client-only. Both Alice's phone and her desktop read from the
same Skynet DB on their next fleet-status frame, so the write path must be
server-side. HTTP is the same channel the frontend uses for every other
Skynet CRUD (compose-drafts, user-preferences, etc.), so no new transport
mechanism.

Output: `identity-send-log-routes.ts` with a single POST /stamp endpoint;
mount registration in `database.ts` next to the existing router mounts;
supertest coverage for auth, validation, success, error paths.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → HTTP route | Untrusted — external browser (Alice's compose surface) posts JSON. AuthManager JWT middleware is the trust gate. |
| route → store | Trusted — the store module is in-process, no serialization. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-85-03-01 | Spoofing | unauthenticated request | mitigate | AuthManager JWT middleware rejects requests without valid session cookie (401). Test 1 proves the gate. |
| T-85-03-02 | Tampering | identityName injection | mitigate | Route validation rejects non-string, empty, or > 256 char identityName with 400. Store module further parameterizes the drizzle query (Plan 85-02 mitigation T-85-02-01). Two layers of defense. |
| T-85-03-03 | DoS | unbounded POST rate | accept | Every legitimate Alice send fires exactly one POST. Adversary would need Alice's session cookie to hit the endpoint. No app-layer rate limit needed for a single-tenant deploy. Skynet's fronting HTTPS ingress does not enforce per-route rate limits today; if this ever changes, add here. |
| T-85-03-04 | Repudiation | client sends fake ts | mitigate | Route accepts client-provided ts (D-06 optimistic-stamp needs client authority). The monotonic guard in the store (T-85-02-03) prevents ts from regressing the row; a client sending a wildly-far-future ts would pin the row until that time passes, then natural fill resumes. Not a security concern (Alice is the only user). |
| T-85-03-05 | Information Disclosure | error response leaks internals | mitigate | 500 response body is a fixed string `"failed to stamp send log"` — no stack trace, no query text. Detailed error logged server-side only. |
| T-85-03-06 | Elevation of Privilege | route bypasses auth | mitigate | The router attaches `authenticateJWT` middleware BEFORE the POST /stamp handler; missing middleware is caught by Test 1 assertion. |
| T-85-03-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages. Consumes existing express + AuthManager + supertest. Audit-clean. |
</threat_model>
