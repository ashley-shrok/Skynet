<objective>
Add the new `identity_send_log` durable SQLite table that persists Ashley's
"when did I last send" timestamp per identity (D-01, D-02).

Purpose: Every other plan in this phase reads or writes this table. Without
it, every store call fails at runtime. This plan lands the schema first so
plans 02, 04, and 05 have a real table to reference on merge.

Output: A new Drizzle `identitySendLog` export in `schema.ts`; a `CREATE
TABLE IF NOT EXISTS identity_send_log` block wired into
`initializeCompleteDatabase()` in `db/index.ts`; a `DatabaseSaveTrigger.forceSave`
call after the CREATE so the encrypted disk copy reflects the new schema
on non-graceful shutdown (Skynet in-memory DB invariant); test coverage
for both the fresh-install path (table created) and the upgrade path
(idempotent no-op on subsequent boot).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| boot-time schema install | Trusted — runs in-process at container startup; no external input. |
| encrypted disk persistence | Trusted — DatabaseFileEncryption handles the at-rest ciphertext; this plan only mutates the plaintext-in-RAM schema and requests a flush. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-85-01-01 | Tampering | new table schema | mitigate | Table has no foreign keys, no cascade rules — deletion of the table's contents (worst case) reverts the middle-zone to insertion-order fallback per D-09. |
| T-85-01-02 | Denial of Service | forceSave on every boot | accept | forceSave is guarded by an internal isDirty flag; the CREATE-IF-NOT-EXISTS is a no-op on subsequent boots, so the trigger fires but short-circuits. Runtime cost is negligible. |
| T-85-01-03 | Information Disclosure | schema exposes identity names in plaintext | accept | Same trust model as every other table in `skynet-data` — the encrypted disk file is the boundary. Identity names are already visible in ssh_data.name and every other durable table. |
| T-85-01-04 | Elevation of Privilege | new table has no permission gate | accept | Store reads/writes happen through backend routes gated by the existing AuthManager JWT middleware (established in later plans 02 + 03). This plan only creates the table shape. |
| T-85-01-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages introduced. slopcheck + blocking human checkpoint would apply if this plan added any; audit-clean. |
