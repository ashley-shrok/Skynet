<objective>
Rewire `POST /identities/avatar/batch` to source both the aesthetic director spec and the gamma value from the branding config at request time, deleting the in-file `ARCHETYPE_SYSTEM_PROMPT` constant entirely and splitting `paletteConstraintLine` so only the mechanical hue→color-name fact stays app-owned. Per D-05 (74-CONTEXT.md Scope Edges "In" bullet 3) — the batch endpoint reads from the branding config, not from a hardcoded constant. Per D-06 (74-CONTEXT.md Scope Edges "In" bullet 4) — palette-constraint is split: mechanical fact stays in code, aesthetic instruction language moves out.

The load-bearing anti-pattern from Ashley `<additional_context>` and 74-RESEARCH.md § "Anti-Patterns to Avoid": DO NOT leave any fallback branch that reads a hardcoded spec constant. Delete the constant outright. No `const FALLBACK_ARCHETYPE = ...` lurking anywhere. A stale fallback silently defeats the whole point of moving the aesthetic into the config.

Per Ashley `<additional_context>` load-bearing anti-pattern list — the test file MUST get `vi.mock("../../branding/branding-config-loader.js")` at file top. Without it, the tests silently pass by reading the bundled defaults with empty spec — they'd all no-op the actual behavior under test.

Per Ashley `<additional_context>` load-bearing anti-pattern list — the three header-comment references to the runbook file at identity-avatar-batch.ts L16, L122, L180 must be scrubbed. When Plan 04 deletes `~/.claude/roles/box-maintainer/runbooks/avatar-flow.md`, those comments become stale pointers to a deleted file.

Defense-in-depth per 74-RESEARCH.md Pitfall 2: even though Plan 02's boot gate catches missing spec at startup, an operator runtime edit that introduces a shape violation would silently revert to bundled defaults (empty spec). The `/batch` handler adds a request-time guard: if `avatarDirectorSpec.trim().length === 0` at request time, return 503 (same status code as the existing OPENAI_API_KEY-missing branch at L242-246). This is defense-in-depth, not a replacement for the boot gate.

Purpose: makes the aesthetic behavior 100% config-driven — the app's own code holds zero aesthetic content after this plan lands. A differently-branded instance can produce entirely different-looking avatars purely by changing its branding config file, no code deploy required.

Output:
- Rewired POST /batch handler: `await loadBrandingConfig()` at top of handler; system message uses `config.avatarDirectorSpec`; gamma parameter flows to sharp
- `ARCHETYPE_SYSTEM_PROMPT` constant DELETED
- `paletteConstraintLine(hue)` REPLACED with mechanical-only `paletteHueLine(hue)` that emits just `"Identity color hue: <deg>° (reads as <name>)."` — no aesthetic instruction language
- `applyGamma07(pngBuffer)` REPLACED with parameterized `applyGamma(pngBuffer, gamma)` (or equivalent — planner is agnostic to the name, but the hardcoded 0.7 must go)
- `_applyCorrectionForTest(inputValue)` test helper updated to accept an optional gamma parameter (default 0.7 preserves backward compatibility with existing Test 4 signatures) or extended to a new signature — planner's call
- Three header-comment refs to `avatar-flow` scrubbed
- Test file gets file-top vi.mock of the branding-config-loader + spec-verbatim assertion + gamma-value assertion + request-time-empty-spec 503 assertion
</objective>
