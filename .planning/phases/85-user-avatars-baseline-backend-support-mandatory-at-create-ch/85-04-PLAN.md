<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network → authenticateJWT | untrusted JWT-in-header crosses here; validated by existing authManager middleware |
| authenticated caller → DB | caller-supplied targetUserId in URL crosses here; own-or-admin guard reads isAdmin from DB (mid-session revocation safe) |
| authenticated caller → filesystem | request has NO ability to influence filesystem path (target's avatar_path is DB-derived, filename composed by writeUserAvatar from targetUserId + whitelisted mime); serve endpoint reads only DB-stored filenames |
| response bytes → browser | Content-Type derived from filename extension only (never from stored mime, never from Content-Type upload header at serve time); SVG mime not in whitelist |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-85-01 | Tampering | PUT multipart body | mitigate | userAvatarUpload (Plan 02) fileFilter + fileSize; Test 8 and Test 9 in Task 1 verify. |
| T-85-02 | Tampering | path traversal on serve | mitigate | GET reads only `users.avatar_path` from DB; readUserAvatar composes path from that filename + USER_AVATARS_DIR only. User-controlled `:id` in URL is used to lookup the DB row, not to compose filesystem paths directly. Even if an attacker crafted `:id = "../etc/passwd"`, the DB SELECT would return no rows (no user with that id) → 404. |
| T-85-03 | Elevation | unauthenticated change | mitigate | authenticateJWT runs before multer; Test 6 (change) verifies 401 for missing token. |
| T-85-03b | Elevation | non-admin changes another user | mitigate | own-or-admin guard at handler top (reads isAdmin from DB not JWT per RESEARCH.md § 6 to defend against mid-session role revocation); Test 3 in Task 1 verifies 403. |
| T-85-04 | Info disclosure | serve auth model too permissive | accept | authenticateJWT-only (no per-user scoping) matches identity-avatar precedent per RESEARCH.md § Q2. Rationale: usernames are already visible in the picker at user-admin-routes.ts:118; a face tied to a public username is less sensitive than the username itself. Stricter scoping would break the downstream "show avatars in tab list" use case that this plumbing enables. |
| T-85-08 | Integrity | new file written + row updated + old-unlink fails → orphan on disk | mitigate | unlinkUserAvatar is best-effort ENOENT-tolerant; if the unlink fails for a non-ENOENT reason, the request STILL succeeds (200) and a WARN is logged. | T-85-17 | Data loss | UPDATE lands in RAM but not on disk across restart | mitigate | Task 1 Step 5 wires `DatabaseSaveTrigger.forceSave("phase-85-user-avatar-change")`. Test 10 asserts label. D-17/D-18 invariant preserved. |
| T-85-CORRUPT | Info disclosure | corrupted-file at serve time | mitigate | readUserAvatar throws on unrecognized extension → GET returns 500 (fail-closed, not fail-open). Test 5 (serve) covers ENOENT branch → 404. |
| T-85-XSS | XSS via mismatched mime | serve pipeline | mitigate | Content-Type set from filename EXTENSION via EXT_TO_MIME (whitelist); a file with `.svg` cannot exist in the store because write path's fileFilter blocks SVG mime → no `.svg` extension ever composed by writeUserAvatar. |

Acceptable per RESEARCH.md § Security Domain "Race between concurrent PUT". |
