<objective>
Unify the two frontend dormancy signals into a single authoritative source so the pending-send timer branch takes the widened 220s ceiling when the agent is truly dormant — including the reconnect-mid-dormancy case that Phase 62 missed.

**Purpose:** Phase 62 shipped `PENDING_SEND_TIMEOUT_MS_DORMANT = 220_000` but wired it to `dormantRef.current`, which mirrors the emit-on-change `{type:"dormant"}` frame (Signal A). Signal A goes stale on any WS reconnect while dormant (backend does not re-fire on reconnect through the poll-tick change guard; the initial-discovery probe at claude-session-server.ts:7813 only fires on `result.reason === "not_claude"`). Signal B (`{type:"pane_state"}`) does not go stale — it always re-emits on WS attach through `startActiveSessionFlow`. Fix option (a) per RESEARCH.md recommendation: fire `setDormant` from BOTH signal cases, so `dormantRef.current` is now authoritative through both channels. Zero consumer migration; arm-site semantics preserved.

**Output:** `dormant` state / `dormantRef` populated from both `case "dormant"` and `case "pane_state"` in the WS onmessage handler. Test 5c added to `PrettyView.optimistic-bubbles.test.tsx` exercising the reconnect-mid-dormancy scenario (WS close → new WS attach → deliver only `pane_state:dormant`, NOT `type:dormant` → send → 220s branch armed). Awake case unchanged. Existing Test 5 and Test 5b still pass.
</objective>
