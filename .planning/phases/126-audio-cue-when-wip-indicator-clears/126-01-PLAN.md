This plan creates `src/ui/audio/ready-cue.ts` — the module that owns the shared `AudioContext`, the decoded tink `AudioBuffer`, the module-level `unlocked: boolean` flag, the first-gesture unlock listener install, and the `playTink()` function that Plan 02 will import.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Web Audio API | Client-side audio playback; no server data involved; no cross-user surface |
| First user gesture → AudioContext.resume() | Standard iOS/desktop autoplay-policy unlock — trusted at the browser level |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-126-01 | Denial of Service | Rapid playTink() calls (e.g. WIP-flicker loop misfiring) | accept | LOW: each fire creates a short-lived AudioBufferSourceNode that self-terminates in ~100ms; browser audio graphs handle hundreds of concurrent nodes without issue. The latch state machine in Plan 02 is the semantic gate that keeps fire rate sane; if the latch misfires, the fix is in the latch, not here. |
| T-126-02 | Information Disclosure | Audio asset bundled in the JS/CSS chunk | accept | LOW: the tink sample is a generic UI cue with no user-identifying content. Ships to every client identically. |
| T-126-03 | Tampering | User devtools-suppresses the audio module | accept | LOW: silencing the chime is not a security-relevant action. There is no opt-out UX by design (D-17), but a technically-motivated user can always disable audio at the browser level. |
| T-126-SC | Tampering | npm/pip/cargo installs | mitigate | No new npm dependencies added — Web Audio API is a browser built-in. The audio asset itself is committed to the repo (not fetched at runtime). No package-manager legitimacy audit needed. |

No new backend routes, no new network requests, no new payload shapes. Zero new attack surface.
