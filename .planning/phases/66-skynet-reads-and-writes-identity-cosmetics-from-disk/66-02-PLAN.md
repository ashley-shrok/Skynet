## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PUT /identities/:id → target-host SSH | authenticated request → SSH write on remote box; identityKey scoped by (id, userId) lookup before hostId is used |
| multipart data field → JSON.parse → disk write | attacker-controlled JSON reaches yaml.dump on cosmetic fields |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-66-02-01 | Tampering | hostId in request body | mitigate | (id, userId) row lookup happens FIRST — the identityKey to be written is derived from the store row (server-controlled), not from the body. hostId only routes the SSH connection; a rogue hostId writes to the caller's OWN identityKey on a box the caller doesn't own only if that box is in the caller's ssh_data table (resolveHostById scopes by userId — same pattern identity-birth uses). |
| T-66-02-02 | Tampering | title/displayName YAML injection | mitigate | js-yaml.dump quotes strings containing YAML-special characters (colon+newline, `>`, `|`, leading `-`, etc.) via forceQuotes:false's type-aware defaults. Test 1 asserts round-trip via yaml.load — implicitly proves injection is impossible. |
| T-66-02-03 | Denial of Service | write-during-read race | accept | Two edits landing on the same identity file within the same second could interleave. Ashley is a solo user editing her own identities — race probability is negligible. The atomic-rename discipline of writeMarkdownFileAtomic ensures the file is never left partially written; a lost-update on cosmetics is preferable to a corrupted file. |
