<objective>
Wire the PrettyView component from Plan 3 into the terminal tab render path so that Phase 1's read-only pretty view is REACHABLE in production — the ROADMAP Phase 1 success criterion demands the pipe be end-to-end observable — without introducing the toggle chord (Phase 2 owns TOGGLE-01..03) or the compose box (Phase 2 owns COMPOSE-01..05).

Vehicle: a URL fragment substring gate. If `window.location.hash` includes the literal substring `pretty=1`, the terminal tab renders `<PrettyView>` in place of `<TerminalFeature>`. Otherwise the tab renders unchanged.

Why a URL fragment rather than a new toggle chord or a new TabType:
- A new TabType would need `enableTerminal` schema changes, persistence in open_tabs, URL encoding in tab-url.ts, sidebar icon plumbing — all Phase 2 concerns that CONTEXT.md defers.
- A new toggle chord IS explicitly Phase 2 (TOGGLE-01). Adding one in Phase 1 would burn Ashley's key-chord budget for the wrong feature and require rollback in Phase 2.
- The URL fragment (#tab=... per patch #25) is already the fork's "how do I reach a specific tab state" convention. Reusing it as `#tab=tmux:host:name&pretty=1` (or by appending `&pretty=1` to whatever fragment is present) is the smallest possible surface area.
- Fragments survive Chrome window-restore (patch #25's `bad8020` lesson), so a Phase-1-deployed pretty view can be bookmarked and tested across restarts.
- Phase 2 replaces this gate with the proper chord + per-tab mode state and can remove the fragment logic without touching anything else.

Output: One file modified — `src/ui/shell/tabUtils.tsx` gains a fragment-check + conditional PrettyView mount inside `TerminalTabContent`.
</objective>
