<objective>
Deliver the frontend half of the optimistic-bubble state machine: the moment Enter is pressed, PrettyView seeds a PendingSend record and ChatMessage renders the outgoing user bubble immediately with a small trailing-edge spinner; the spinner clears when the parser signal from Plan 50-01 arrives (FIFO + content match); a 20s client-side timer, a paste_send_failed WS frame from Plan 50-02, a send_keys_error WS frame, or a synchronous WS.send failure all flip the bubble to a muted red-failure state AND repopulate ComposeBox for edit-and-resend.

Purpose (D-01 through D-08 + D-18 through D-21 from 50-CONTEXT.md): This is the perceived-responsiveness payoff — no more dead moment between Enter and bubble render. The design deliberately reverses the COMPOSE-04 HARD LOCK: bubbles are now always either (a) confirmed via signal or (b) in optimistic-with-spinner state waiting for signal. The load-bearing WhatsApp-precedent invariant (D-05) is enforced structurally: once matched, no client-side timer can ever flip a bubble back to failed.

**Mqid threading (Blocker #4 root-cause resolution):** ComposeBox generates the mqid ONCE (pattern `pv-optim-<timestamp>-<random8hex>`). That mqid flows through EVERY layer: onOptimisticSend seeds the PendingSend under that mqid; onSend(text, mqid) forwards it; PrettyView.handleComposeSend forwards it; IdentitySessionPane's onSend at L237-270 (the actual caller of ComposeBox's onSend prop — see Blocker #4) receives it and DROPS its current pv-adhoc-<uuid> generation; pvSendInputRef.current(text+'\r', mqid) puts it on the wire; backend armPvSendWatchdog keys the pending under it; paste_send_failed / send_keys_error frames carry the SAME mqid back; PrettyView.flipToFailed(parsed.mqid, ...) finds the matching PendingSend and flips it to failed. Without this single-mqid-source discipline, the frontend PendingSend is seeded under 'pv-optim-...' but the backend watchdog fires escalations against 'pv-adhoc-...' and the frontend flipToFailed never finds a match — every 20s-timed-out send just stays with a spinner forever until the frontend 20s timer eventually flips it (masking the backend signal path entirely).

Output: New pending-sends state on PrettyView + ChatMessage pendingState rendering + ComposeBox HARD LOCK removal + IdentitySessionPane onSend widening + WS-message-handler dedup glue + tests. Wire protocol consumes Plan 50-02's paste_send_failed and send_keys_error frames unchanged.
</objective>

| T-50-03-02 | Denial-of-Service | Unbounded pendingSends array | mitigate | Every pending record either matches within seconds (parser signal arrives fast — median ~91-111ms per empirical evidence in 50-CONTEXT.md) or expires at 20000ms. Practical upper bound: the user cannot manually type + Enter more than ~10-20 messages in the 20s window before the oldest expires. If a runaway loop somehow floods pendingSends, the 20s TTL bounds memory; add a hard cap `MAX_PENDING = 50` and log-and-drop-oldest as belt-and-suspenders if the impl finds this simple. |
| T-50-03-03 | Tampering | mqid uniqueness | accept | mqid is generated client-side with `Date.now() + Math.random().toString(36).slice(2, 10)` — 8-hex random combined with millisecond timestamp yields ~2^32 uniqueness per millisecond, more than sufficient for user-typed cadence. Collision would result in the wrong pending being cleared (visual glitch, not a security event). |
| T-50-03-04 | Spoofing | paste_send_failed / send_keys_error frames from wire | accept | The WS is authenticated per existing pretty-view WS auth (JWT); frames on this WS are trusted-by-connection. | T-50-03-SC | Tampering | npm/pip/cargo installs | mitigate | Zero new dependencies added (Loader2 from lucide-react is already imported; no new @lucide/* or spinner/anim library). No package legitimacy gate required. |
