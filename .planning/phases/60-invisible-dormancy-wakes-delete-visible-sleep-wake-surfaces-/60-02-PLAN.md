<objective>
Widen the `pv-send-watchdog` timing chain when the send was dispatched during pane dormancy so a healthy ~90-second wake (MARKER_FALLBACK_MS + normal-send window) never trips the `paste_send_failed` red-bubble backstop. Threaded via a single new `dormantSend: boolean` opt-in on `armPvSendWatchdog` args — call sites that don't set it get today's timing (RETRY_ENTER_MS 2500, FULL_RESEND_MS 5500, GIVE_UP_MS 20_000) byte-for-byte. When `dormantSend: true`, all three stages shift out: retry-Enter stays useful at T+2500ms (bare Enter is harmless — D-16), but full-resend and give-up push out past the marker window.

Purpose: The invisible wake takes ~90 seconds end-to-end on a t1000 (the empirical wake latency Nelly measured, per L771-773 comment "If marker never appears within 90s of wake_trigger_ts, fall back"). Without widening, the send-path's Plan 01 marker wait could complete a normal handoff to send-keys AT T+90s, but the watchdog arms at the send-keys moment which means for the dormant flow the watchdog's own T+20s escalation fires DURING the healthy wake window — user sees a red bubble on a healthy send. That would violate the shape's "same failure surfacing as any other send" AND the "if the message never lands the bubble goes red" contract simultaneously (because in the dormant case the message eventually WILL land, the bubble should stay optimistic).

Output: `pv-send-watchdog.ts` with a new `dormantSend?: boolean` flag on `ArmPvSendWatchdogArgs` and a branch in `armPvSendWatchdog` that swaps the three timing constants to widened variants when the flag is true. `claude-session-server.ts` with the flag wired from the dormant-branch arm-time call in the input handler (introduced by Plan 01). Test coverage in a new `pv-send-watchdog.test.ts` file (or appended to an existing `pv-send-watchdog.test.ts` if one exists).
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-60-02-01 | Spoofing | `dormantSend` flag origin | mitigate | `dormantSend: true` is set BY THE BACKEND at the arm-time call site inside `__applyInputMessageForTests`'s dormant branch (introduced by Plan 01). It is derived from `wasDormant = deps.dormantLastEmitted?.() === true` evaluated at input-handler entry — a getter reading a connection-scoped closure var owned by the backend. No WS payload field can trigger the widened window. Attackers cannot force widened watchdog timings for their own sends. |
| T-60-02-02 | Denial of Service | widened window delays the paste_send_failed backstop | accept | An attacker forcing repeated dormant-branch entries would delay the red-bubble emit by ~100s per send. Acceptable because (a) the failure mode is a UI signal, not a service crash, (b) each pending watchdog is bounded memory (see pv-send-watchdog.ts L120-133 `PendingWatchdog` struct — ~200 bytes), (c) `clearPvSendWatchdogsForSession` at L444-464 already cleans up on session recycle, and (d) the widened window is USE-CASE-JUSTIFIED — the shape file explicitly names this as a load-bearing requirement ("the watchdog window has to be wide enough that a healthy wake never trips the red-bubble backstop"). |
| T-60-02-03 | Tampering | timing constant drift between MARKER_FALLBACK_MS and GIVE_UP_MS_DORMANT | mitigate | GIVE_UP_MS_DORMANT is defined in `pv-send-watchdog.ts` as `MARKER_FALLBACK_MS + GIVE_UP_MS + 10_000` — a formula that stays correct if either upstream constant moves. Cross-file constant coupling documented in a header comment. Note: `MARKER_FALLBACK_MS` lives in `claude-session-server.ts:773`, not in a shared module; the widened-window code MUST NOT import from claude-session-server.ts (circular). Instead, `pv-send-watchdog.ts` re-declares the constant with a comment `// Mirrors MARKER_FALLBACK_MS at claude-session-server.ts:773 — the two must stay in sync.` Add a test that reads both files and asserts the values match to prevent drift. |
