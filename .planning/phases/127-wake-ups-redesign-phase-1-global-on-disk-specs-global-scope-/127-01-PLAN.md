<objective>
Extend the spawn-requests ingress pipeline so it accepts the new global-wake-up request-file shape without rejecting extended bodies as malformed. This is the pre-req for Plan 02's global scheduler fire path — that scheduler will drop `{roles:[...], skills:[...], prompt:..., task:null, requested_at:...}` bodies, and Pitfall 3 in RESEARCH.md warns that today's parseRequestBody rejects extra fields, so any drop today writes `<uuid>.failure.json {reason:"malformed"}`. The schema extension MUST land in the same phase deploy as the scheduler change (D-17 hard cutover).

Purpose: unlock the fire path for D-11, D-12, D-04, D-05 by making the TypeScript-side ingress accept the extended body. Also acts as the D-13 coordination point: this plan defines the extension; multi-role identity work (out-of-tree) adopts it downstream. Bridge via `BirthOptions.role = item.roles[0]` inside worker.ts with a TODO comment (RESEARCH §4 recommendation).

Output: extended types + extended validator + updated all in-tree PendingBirth consumers (queue.ts log, worker.ts BirthOptions, ssh-poll-orchestrator.ts parseSpawnRequestBatch) + updated existing tests + new tests for the extended schema.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local filesystem → parseSpawnRequestBatch | Untrusted request-file bodies written to `~/fleet/spawn-requests/<uuid>.json` on managed hosts cross into the Skynet backend's request-body parser via the SSH scan tick. In Phase 1 the writer is either the global wake-up scheduler (Plan 02, trusted local process) or a coordinator's SSH-scoped drop. In principle anything with write access to `~/fleet/spawn-requests/` can birth an identity — a privilege-escalation surface flagged in the planning context. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-127-01-S | Spoofing | parseSpawnRequestBatch reading a request body from disk | accept | The request-file drop path is already a trusted-filesystem contract per RESEARCH §6 (ASVS V5 note). No auth is added here; the mitigation lives outside phase scope (host-level filesystem permissions on `~/fleet/spawn-requests/`). Same posture as pre-change. |
| T-127-01-T | Tampering | roles[] field content in request body | mitigate | Every element of `roles[]` validated against `ROLE_NAME_PATTERN` in parseRequestBody per D-12; empty arrays rejected; non-string / zero-length elements rejected. Matches the tampering posture the single-string `role` field had pre-change — no regression, tighter coverage (per-element validation replaces single-string validation). |
| T-127-01-T2 | Tampering | prompt field content | mitigate | prompt is a plain string (D-06). Validated as non-empty string; no length cap because RESEARCH §3 D-06 explicitly rejects a cap. Prompt content flows into `BirthOptions.task` (via the `roles[0]` bridge in Task 3) or into the newborn's first turn (out of scope for this plan) — the trust posture is that the prompt originates from the same trusted-filesystem source as the roles field and gets the same treatment. |
| T-127-01-T3 | Tampering | skills[] field content | mitigate | skills[] elements validated as non-empty strings. No pattern validation on skill slugs (skills are a phase-2/multi-role concept and their allowed shape is not yet fixed — RESEARCH §3). If skills[] later needs a pattern (e.g. SKILL_NAME_PATTERN), the multi-role track can tighten this validator without breaking the schema. Acceptable for phase 1: better than the pre-change state where the field didn't exist at all. |
| T-127-01-I | Information Disclosure | systemLogger.info calls in queue.ts and worker.ts logging role context | accept | Log context field `role` continues to carry `roles[0]` — no PII exposure change. Log format preserved so operators keep the same searchability. |
| T-127-01-D | Denial of Service | Extremely large prompt value flooding logs / birth queue | accept | D-06 explicitly refuses a length cap on prompt. `task` field retains its existing TASK_MAX_LENGTH=500 cap. Prompt DoS is a phase-2 concern (the Skynet CRUD API can enforce a UI-side length cap; the on-disk contract stays permissive per user preference). Note: worker.ts logs the full item context — if this becomes a real DoS surface, add a `prompt.length` field and truncate the logged prompt (phase 2 fix). |
| T-127-01-SC | Tampering | npm/pip/cargo installs | mitigate | Zero external packages installed in this plan (RESEARCH § Package Legitimacy Audit: "Not applicable"). No supply-chain surface added. |
