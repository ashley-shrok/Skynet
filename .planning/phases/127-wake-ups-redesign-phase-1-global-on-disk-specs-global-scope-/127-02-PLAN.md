<objective>
Extend `substrate/scripts/wakeup-scheduler.py` with a `--mode global` flag that (a) reads specs from the new nested slug-folder layout `~/fleet/wakeups/<slug>/wakeup.json`, (b) consumes `prompt`/`roles`/`skills` fields (instead of `instruction`), (c) fires by dropping `~/fleet/spawn-requests/<uuid>.json` for Skynet's existing coordinator-birthing pipeline to consume, and (d) disables the orphan-monitor guard because no harness owns this process (agent-supervisor.sh spawns it session-independently — see Plan 03). Per-identity mode is byte-identical to today. Everything else the script does — schedule due-time math, first-sight anchor, one-catch-up-on-missed-slot, .fired sentinel + spec self-delete on one-shot fires, stale-sentinel clearance, timezone handling, `_single_instance` uniqueness — must carry over unchanged (shape § "Fire semantics that must survive the port"; D-07 explicitly locks reuse of the existing script).

Purpose: D-07, D-08, D-10, D-11 — the new mechanism's runtime. The bytes here are the entire fire path from a spec-on-disk to a create-identity request file the spawn-requests pipeline (extended by Plan 01) can validate and enqueue. No forking of the script; a mode flag is the whole extension surface.

Output: a single dual-mode script + a substrate-side bash test (mirroring existing `substrate/scripts/tests/*.test.sh` pattern) that exercises both modes in isolation.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `~/fleet/wakeups/<slug>/wakeup.json` → wakeup-scheduler.py global mode | Anything with write access to `~/fleet/wakeups/` can create a spec that fires an identity birth. Per planning-context (b): this is a privilege-escalation surface — the trust posture is that only trusted local processes (the user, agents-with-user-approval per D-01/D-02 governance in id-skill § "USER-RESERVED") write there. The scheduler does not add authentication; it inherits filesystem-level trust. |
| wakeup-scheduler.py global-mode fire → `~/fleet/spawn-requests/<uuid>.json` | The scheduler now becomes a producer of spawn-request files. Per planning-context (a): anything with write access to `~/fleet/spawn-requests/` births an identity — the scheduler joins the coordinator as a trusted producer. No new auth needed; the file-drop contract is preserved (Plan 01 handles the ingress-side schema validation). |
