<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Systemd-user context → agent-supervisor.sh | agent-supervisor.sh runs as a systemd --user service on managed hosts. Its startup steps run with the fleet user's ambient authority; adding a new setsid+nohup child inherits that authority. No additional privilege is added by this plan — the same authority already runs start_ambient_monitor and the per-identity ambient watchers. |
| ambient-monitor.py child list → per-identity subprocess spawns | The CHILDREN list is the trust boundary between the launcher and each child watcher. Removing an entry (wakeup-scheduler-role) shrinks the trust surface of every coordinator identity by one process; adding no new entries. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-127-03-S | Spoofing | Global scheduler process identity vs the wakeup-scheduler binary at $HOME/.local/bin/wakeup-scheduler | mitigate | The launch is gated on `[ -x "$HOME/.local/bin/wakeup-scheduler" ]`; if the path is missing or not executable, the supervisor logs a WARNING and continues. The exec path is the distributor-installed script (RESEARCH §7 confirms substrate/scripts/wakeup-scheduler.py maps to the wakeup-scheduler catalog slug); trust is the same as any other distributor-managed binary on the host. |
| T-127-03-T | Tampering | wakeup-scheduler binary being replaced between distributor pushes | accept | Same threat model as every other substrate-distributed script; not phase-specific. If an adversary can write to $HOME/.local/bin/, they can already replace any watcher binary. The distributor sweep re-verifies content on the next pass. |
| T-127-03-R | Repudiation | Global scheduler start/stop attributability | mitigate | agent-supervisor.sh logs the launch via the standard `log` helper with dir + log path (both branches — success and missing-binary). Combined with the scheduler's own stderr log at $HOME/fleet/wakeups/global-scheduler.log, every fire and every startup is auditable. |
| T-127-03-I | Information Disclosure | Log content in global-scheduler.log | accept | Same content today's per-identity scheduler logs to its ambient-monitor.log — prompt content, roles, spec slugs. No PII amplification; user-authored content by design. |
| T-127-03-D | Denial of Service | Global scheduler crash-looping if spawn fails | accept | agent-supervisor.sh spawns the scheduler once at startup and does not restart it in-loop. If the scheduler crashes after start, it stays down until the next supervisor restart. This is consistent with the per-identity scheduler pattern (ambient-monitor.py CHILDREN entries have `critical: False` — same posture). If crash-looping becomes an operational issue, a follow-up phase can add a supervise-once helper; not required for phase 1. |
| T-127-03-D2 | Denial of Service | ambient-monitor.py fails to parse after edit | mitigate | Task 2 acceptance requires `python3 -c "import ast; ast.parse(...)"` to succeed as a source assertion before the change is considered done. Any indentation break or bad delete fails this gate. |
| T-127-03-E | Elevation of Privilege | Global scheduler running with more authority than intended | mitigate | The scheduler runs under systemd --user (fleet user), identical authority to start_ambient_monitor, ambient-monitor, and every per-identity watcher. No sudo, no setuid, no capability grant. |
| T-127-03-SC | Tampering | npm/pip/cargo installs | mitigate | Zero external packages installed in this plan. Bash and Python edits to already-distributed scripts. No supply-chain surface added. |
</threat_model>
