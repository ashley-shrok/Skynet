<objective>
Extend the backend wire protocol with two new additive+optional numeric fields (activityMtime, stoppedMtime), extend the ssh-poll-orchestrator processPid loop to derive both fields from the two new marker files installed by Plan 62-02, and keep the Phase 59 lastStopAt + lastStatusChangeAt fields RETAINED for the duration of Phase 62's rollout window.

Purpose: This plan produces the backend half of the direct-signal-consumption architecture. The frontend Plan 62-04 will read these two mtime fields and compute `activityMtime > stoppedMtime` as the WIP predicate — no state machine, no smoothing, no shell-idle gate, just one comparison per session per render. The Phase 59 fields are retained (not retired) because the LOCKED rollout choice for this phase (CONTEXT.md §Rollout Option 1) is "backend detects marker absence and falls back to the old predicate for boxes that haven't been installed yet." That fallback happens on the FRONTEND (Plan 62-04) — the backend publishes BOTH signal sets, the frontend chooses which predicate applies per-session based on marker presence.

Purpose of retention over deletion: The blast-radius rule (CLAUDE.md — a bad deploy loses Ashley access to her whole fleet) makes an all-at-once retire-and-replace unacceptable. Every managed box needs the Plan 62-02 installer to run at least once before its markers exist; until then the OLD predicate is the only working signal source for that session. Retention is the safe direction; the follow-up phase (post-full-rollout, orchestrator-tracked) is where the Phase 59 fields retire cleanly.

Output: Wire schema addition + backend orchestrator extension + comprehensive test coverage on both. No behavior change until Plan 62-04's frontend consumer swap. This plan is the widest of the four — the ssh-poll-orchestrator is a large file — but the surgical scope is limited to processPid's per-PID marker reads, the PidCacheEntry additions, computeFingerprint additions, and the SessionState composition. NO changes to source B (pollDormantOnlyIdentities), NO changes to the ambient-filter/backgroundTasks pipeline, NO changes to the JSONL tail-scan or lastMessageAt/aiTitle/dormant derivations.

## Rollout choice — LOCKED for this phase (documented here so future readers see it in the code plan)

**Option 1 from CONTEXT.md §Rollout: Backend detects marker absence and falls back to the old predicate.**

Rationale for choosing this over Option 2 (default-working on absent markers) and Option 3 (block affordance entirely on unupgraded boxes):

- Option 2 (default-working): The shape's hard failure mode is "false-idle is worse than today's bug" but false-WORKING on every unupgraded box also fails the affordance's job (steer Ashley's clicks). Every session on every unupgraded box would look perpetually working — Ashley would learn to ignore the affordance entirely, and the phase's whole point is that the affordance stops lying.
- Option 3 (explicit install-first with a distinct "unknown" affordance): Requires the most operational discipline AND introduces a new affordance state the shape does not define. Increases blast radius (the "unknown" indicator itself is new UI).
- Option 1 (fallback to old predicate): Preserves current behavior on unupgraded boxes (Ashley has adapted to the known bugs; adaptation is intact). Prove the new predicate on Nelly-on-thenasty (the reproducer), then propagate. The old Phase 59 machinery retires in a follow-up phase after every box is confirmed installed.

The fallback logic lives on the FRONTEND (Plan 62-04) — the backend publishes both signal sets simultaneously. The frontend's session-working-store checks marker presence (activityMtime !== null || stoppedMtime !== null → new predicate applies; both null → fall through to the existing shell-idle-gate predicate).
</objective>
