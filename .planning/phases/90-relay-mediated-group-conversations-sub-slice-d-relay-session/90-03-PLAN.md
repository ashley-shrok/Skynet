<objective>
Extend `src/backend/matrix/matrix-admin-client.ts` with two new primitives that the relay-room WS server (Plan 04) will consume:

1. `getRoomMessages(roomId, {dir, from?, limit?})` — GET `/_matrix/client/v3/rooms/{roomId}/messages?dir=b&from=<eventId>&limit=20` using the admin token. Returns parsed events + cursors (`end`, `start`) for D-14 pagination. Used both for initial history load AND for scroll-back per Pitfall 5 (event-id cursor, NOT line-number).

2. `sendMessageAsUser(senderMxid, roomId, body, txnId)` — PUT `/_matrix/client/v3/rooms/{roomId}/send/m.room.message/{txnId}` using a per-user access token minted via `loginAsUser(senderMxid)` first — NOT the admin token. This is the Pitfall 3 / T-90-BE-03 mitigation: sending as the admin would make every message appear as `@skynet-admin: hello` instead of `@ashley_human: hello`.

Purpose: Every subsequent backend touch (Plan 04 WS server) and frontend touch (Plan 05 message list) depends on these two primitives. Landing them in Wave 2 (parallel with Plan 04's WS server skeleton if the WS server can be developed against a mock and integrated after) unblocks the rest of the phase. The primitives live in-file (extension) not in a new module — following the existing convention of one primitive per exported function in matrix-admin-client.ts (RESEARCH.md § Don't Hand-Roll: 'Extend the file, don't parallel-implement').

Output: Two new exported primitives + tests + `npm run build:backend` clean (per Pitfall 7 — `tsc --noEmit` alone does NOT catch backend errors; must run backend build gate).
</objective>
