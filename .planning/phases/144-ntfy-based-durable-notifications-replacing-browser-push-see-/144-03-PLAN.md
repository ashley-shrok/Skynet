<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Skynet backend REST (via main-axios + JWT) | Authenticated; backend validates every request |
| User's clipboard ← pane copy buttons | Trusted — clipboard write is a user-initiated action; no secret escapes without the user's explicit tap |
| Service worker ← page scripts | Trusted; same-origin |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-144-14 | Information Disclosure | reading_credential rendered in the DOM (visible to anyone shoulder-surfing or screenshotting) | accept | This is intentional — the user needs to see the credential to type it into the ntfy app. CONTEXT.md's "no QR scanner" + "manual entry" shape explicitly accepts this exposure. The credential is read-only (can't publish) and user-scoped (can't read other topics). Pane copy affordance is explicit user action. |
| T-144-15 | Spoofing | A rogue page script could call /ntfy-regenerate without the user's intent | mitigate | window.confirm gate before every regenerate call (PANE-06a/06b); backend requires JWT (authenticateJWT middleware); same-origin SOP + the existing CSRF posture of the Skynet backend covers this. No new attack surface vs the Phase 128 preferences pane. MC-2 ensures both confirm and cancel branches are tested. |
| T-144-16 | Repudiation | A failed test POST silently misleads the user into thinking setup is broken when it's a transient network glitch | accept | Test result shows the inline error message from the backend (RT-05 returns `{error}` on fetch failure); the user can re-tap. Preserving honest signaling means NOT auto-retrying — the user owns their confidence per shape. |
| T-144-17 | Information Disclosure | sw.js's deleted handlers leave stale ServiceWorker registrations on existing user devices still containing the old code | mitigate | sw.js hash will change (file content changed); browsers re-register the SW; `activate` handler already includes the standard "clients.claim() + skipWaiting" pattern (verify in Task 2's read_first); existing push subscription records are discarded by plan 02's schema migration. Any remaining in-browser PushSubscription object becomes a no-op since the backend no longer accepts it. |
</threat_model>
