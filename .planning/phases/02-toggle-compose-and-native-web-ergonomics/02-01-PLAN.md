<objective>
Wire up the keyboard-chord mode toggle. This plan delivers TOGGLE-01, TOGGLE-02, and TOGGLE-03 as a single vertical slice: pressing Ctrl+Shift+O on an active terminal tab flips the top pane between tmux xterm and PrettyView, the queue drawer at the bottom survives the flip unchanged, and there is no persistence of the mode choice anywhere.

The layered structure of the change:

1. Create a new keyboard-chord hook at `src/ui/hooks/use-keyboard-toggle-pretty-mode.ts` — copies the shape of patch #37's `use-keyboard-close-tab.ts` and patch #39's `use-keyboard-message-queue.ts` byte-for-byte, changing only the localStorage key, the window-event name, and the KeyCode (per D-31 / D-63).

2. Extend `TerminalHandle` with a `togglePrettyMode()` method (parallel to the existing `toggleMessageQueue()` — see patch #39 pattern) so AppShell can dispatch to the active tab's Terminal without prop-drilling state up.

3. Lift the mode state INTO the Terminal component (`useState<boolean>(false)` sibling to the existing `isMessageQueueOpen`) and mount PrettyView inside the same flex-column wrapper that the message queue drawer already lives in. Critical: the outer wrapper and drawer sibling are preserved; only the inner xterm div swaps its content (per D-41 / D-44 — heavy re-mount would destroy drawer state).

4. Wire the new hook into `AppShell.tsx` as the fourth keyboard-chord hook call, immediately after `useKeyboardMessageQueue`, following that hook's identical dispatch pattern via `terminalRefs`.

5. Remove the Phase 1 `#pretty=1` URL-fragment gate from `src/ui/shell/tabUtils.tsx`: delete the `isPrettyMode` useMemo (lines 137–143), the conditional `if (isPrettyMode && targetTmuxSession && host?.id) return <PrettyView … />` mount (lines 146–153), and the `PrettyView` import at line 19. TerminalTabContent unconditionally renders TerminalFeature; mode is now Terminal's concern (per D-30 and specifics/D-131). Leaving the fragment gate in place invites the "which one wins" bug.

Purpose: Deliver the primary ergonomic payoff of Phase 2 — the mode flip is real, feels weightless, and preserves the drawer state that makes multi-message prep valuable.

Output: Chord flips top-pane content in place with no side effects; drawer sits below in both modes; the URL fragment cleanup is complete and no Phase-1 scaffold remains.

Chord choice: The plan implements Ctrl+Shift+O per D-32 recommendation (unbound in Chrome, VS Code, and Ashley's OS binding table). If Ashley wants a different chord after seeing the working implementation, only two lines change — the `e.code` literal in the hook and the description text in en.json. The executor should ship Ctrl+Shift+O without asking; the deploy checkpoint in Plan 03 is where Ashley confirms the chord works with her live OS bindings.
</objective>
