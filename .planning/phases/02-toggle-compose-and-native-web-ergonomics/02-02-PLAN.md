<objective>
Build the compose-and-send box that turns pretty mode from a read-only viewer into a real chat surface. This plan delivers COMPOSE-01 through COMPOSE-05 as a single vertical slice: a textarea at the bottom of the pretty view accepts typed and pasted text, Enter sends via the same proven split-send WebSocket path the queue drawer uses (patch #40), and the sent message appears in the conversation only when the Phase 1 session-file tail confirms it landed.

Purpose: Ship the ergonomic payoff. This is the moment pretty mode becomes usable — Ashley can reply to Claude Code from a real web chat surface with native paste, native selection (Plan 01 preserved that), and no "[pasted N lines]" collapse.

Three key design decisions land in this plan, all locked by D-46 through D-58:

1. **Compose box is a NEW component inside PrettyView**, not shared with `MessageQueueDrawer.tsx` (per D-73 Claude's Discretion). The queue drawer is a persisted queue-of-messages; the compose box is a single always-present entry. Duplication of ~120 lines is cleaner than dragging shared-component scope.

2. **Split-send via the terminal WebSocket**, not a new WS or route (per D-49). Terminal.tsx already holds `webSocketRef.current` and already uses the exact split-send pattern for the queue drawer's `onSend` (lines 2804–2814). The compose box's `onSend` reuses the SAME pattern verbatim, called from a NEW callback threaded down as a prop to PrettyView.

3. **No optimistic display of sent messages** — HARD LOCK from the shape file (per D-52 and shape "not optimistic about sends"). After a successful send, clear the compose textarea and rely on the session-file tail to display the message when the JSONL confirms it. Do NOT add a spinner, sending-state bubble, or client-side echo. If send fails (WS disconnected), surface an inline error but preserve the typed text so the user can retry.

Multi-line send policy (per D-50 Claude's Discretion): collapse newlines to spaces on send (matches the queue drawer's patch #39 behavior which is proven against Ink). This is the safer default because Ink's REPL treats an embedded `\r` mid-message as a submit signal, breaking multi-line messages. If Ashley later wants literal multi-line end-to-end (option (b) in D-50), it is a small follow-up patch — record this in the summary but do not build it now.

Output: A working compose box on every active-Claude pretty view; Enter sends and Shift-Enter newlines; sent messages appear via the Phase 1 tail (never before); paste behaves like every other web textarea.
</objective>

**Enter / Shift-Enter semantics** (COMPOSE-02 per D-48):

    function handleKeyDown(e: React.KeyboardEvent<HTMLTextAreaElement>) {
      if (e.key === "Enter" && !e.shiftKey) {
        e.preventDefault();  // suppress the default newline insertion
        handleSend();
      }
      // Shift-Enter: do NOT preventDefault. Browser default is to insert
      // a newline in the textarea, which is exactly what we want.
    }

Note: use `e.key === "Enter"` here (not `e.code === "Enter"`) because Enter is the same across all keyboard layouts and `e.key === "Enter"` matches typed intent. Different from the mode-toggle chord (Plan 01) which uses `e.code` because Ctrl+Shift+O's physical position matters — for a naked Enter, `e.key` is the correct API.

**Send handler** (COMPOSE-03, COMPOSE-04, COMPOSE-05):

    function handleSend() {
      const trimmed = text.trim();
      if (!trimmed) return;                    // empty send is a no-op
      setErrorMessage(null);                   // clear any prior error
      // D-50 policy: collapse newlines to spaces on send. Ink safety.
      const payload = trimmed.replace(/\r?\n/g, " ");
      const dispatched = onSend(payload);
      if (dispatched) {
        setText("");                           // clear compose textarea
        // Do NOT emit any local optimistic bubble here. The message
        // will render in the conversation when the session-file tail
        // confirms it (D-52 hard lock).
      } else {
        setErrorMessage("Not connected — try again in a moment");
        // Do NOT clear text; the user may want to retry as soon as
        // the WS reconnects (D-56).
      }
    }
