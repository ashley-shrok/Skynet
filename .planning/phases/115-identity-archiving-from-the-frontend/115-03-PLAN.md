<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Frontend → backend HTTP | JWT-authenticated user posts an identityKey + hostId. Untrusted input crosses into filesystem write and SSH-remote-write. |
| Backend Express handler → per-identity disk write | Handler passes user-provided key straight to `writeIdentityFile`; the allowlist gate + `IDENTITY_KEY_RE` gate are the defenses. |
| Backend Express handler → SSH remote host | On REMOTE branch, `writeIdentityFile` runs `mkdir -p ~/fleet/identities/<key>/ && printf '' > ~/fleet/identities/<key>/.archive-requested` via ssh2 exec channel. Command construction must not interpolate untrusted strings unescaped. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-115-03-01 | Elevation of Privilege | Unauthenticated caller drops `.archive-requested` on another user's identity | mitigate | `authenticateJWT` middleware runs first; `resolveHostById(hostId, userId)` filters hosts to the caller's own. Test 5 + Test 8 in the behavior block above cover both defenses. |
| T-115-03-02 | Tampering | `identityKey` param containing shell metacharacters or `../` sequences | mitigate | `IDENTITY_KEY_RE` gate at the top of the handler (mirroring `identity-no-dormancy.ts:L529-533` per RESEARCH §6). Any key that fails the regex is rejected with 400 before any disk or SSH activity. Existing primitive-layer test coverage (per RESEARCH §2, §10) already covers path-traversal defenses in `writeIdentityFile` itself. |
| T-115-03-03 | Information Disclosure | 500 error response leaking `writeIdentityFile` error message (stack trace, filesystem paths, ssh error strings) | mitigate | Return generic `{ error: "failed to drop archive sentinel" }` on any thrown error — log the detail server-side. Test 7 verifies this. |
| T-115-03-04 | Denial of Service | Attacker floods the endpoint with archive requests, causing hundreds of `.archive-requested` sentinels on hosts they own | accept | Rate limiting is a cross-cutting concern owned elsewhere (e.g. Express `express-rate-limit` middleware if the project uses one — check `database.ts`). The archive gesture is only meaningful once per identity per host, and the supervisor consumes the sentinel + deletes it within one reconcile tick. Idempotent by construction. |
| T-115-03-05 | Repudiation | User claims they didn't click archive but the identity is now retired | accept | JWT auth + server-side log ("identity archive requested, userId=<n>, hostId=<n>, key=<n>") provides an audit trail. Sufficient for solo-developer trust model. |
| T-115-03-06 | Tampering | Two concurrent archive requests for the same identity race the `writeIdentityFile` primitive | accept | `writeIdentityFile` is idempotent-by-construction for empty files (both writes produce the same result: an empty file). The supervisor's sentinel consumption is single-threaded per tick. No race window is exploitable. |
| T-115-03-SC | Tampering | npm/pip/cargo installs | accept | No new dependencies added — this plan only uses existing modules (`express`, `writeIdentityFile`, `resolveHostById`, etc.). |
</threat_model>
