<objective>
Create the single authoritative pane-entry state machine hook `usePaneResolvingMachine` (SPEC Requirements 1 and 3) that consumes the two resolution inputs (`wsState` + `backendFirstFrame`), threads the three entry-trigger edges (cold mount, warm hidden→visible re-focus, PWA foreground) into a single shared `resolving`-entry code path, exposes a derived `phase` via the pure `resolvePhase` reducer from plan 29-01, delay-arms the spinner mount at ~150ms (D-04, D-05), and enforces the two-mode "initial-resolving-vs-post-resolve-steady-state" semantics from D-10 / D-11 / D-12.

Per D-10, once the machine has resolved to a terminal phase, subsequent input changes transition the phase directly (e.g. active → dormant on a backend re-emit) WITHOUT re-entering `resolving`. Only the three named entry-trigger edges can re-arm `resolving`.

Per SPEC req 5, this hook contains exactly ONE `setTimeout` — the 150ms spinner delay-arm. There is NO wall-clock deadline that resolves to `error` or dismisses the spinner. Only the WS layer's own `failed-permanently` terminal signal can transition to `phase === "error"`.

Per Claude's Discretion in CONTEXT.md, this plan picks:
- **Location:** `src/ui/features/pretty-view/usePaneResolvingMachine.ts` (co-located with PrettyView + resolve-phase.ts — same subdirectory keeps the state-machine module set discoverable together)
- **Failed-permanently derivation:** consumers pass in `wsState` as a controlled input; how it's derived in PrettyView is the concern of plan 29-04. The hook does not observe the WS layer directly — it takes `wsState` as a parameter so it stays testable without WS mocking.
- **Anti-flash delay value:** 150ms (planner default per D-06; UAT can lock a different value in the 100-200ms range without changing the hook's shape).

This plan runs in Wave 2 after plan 29-01 ships the pure resolvePhase reducer. Plans 29-02 (error overlay) runs in Wave 1 in parallel and is a peer, not a dependency, of this plan.

Output: `usePaneResolvingMachine.ts` (hook) + `usePaneResolvingMachine.test.tsx` (behavior tests using renderHook + act + fake timers).

    (a) Compute paneKey inline: `` const paneKey = `${hostId}:${tmuxSession ?? ""}`; ``

    (b) Track "resolved for this paneKey" using a ref sentinel (D-12 hasEverResolved concept, scoped per pane):
    - `const paneKeyRef = useRef<string>(paneKey);`
    - `const hasResolvedThisPaneRef = useRef<boolean>(false);`

    (c) Track whether the machine is currently "in the resolving phase" as local state:
    - `const [isResolving, setIsResolving] = useState<boolean>(true);` (initial mount is always resolving until inputs settle)

    (d) Derive `phase` synchronously in render body:
    ```
    const derivedTerminalPhase = resolvePhase(wsState, backendFirstFrame);
    const phase: Phase = isResolving ? "resolving" : derivedTerminalPhase;
    ```
    NOTE: The literal "resolving" is what the caller sees during the initial resolution window OR during a re-armed entry trigger. Once hasResolvedThisPaneRef flips true and isResolving flips false, phase mirrors resolvePhase() directly on every render — so a backend re-emit that flips backendFirstFrame from "active" to "dormant" produces phase="dormant" on the next render WITHOUT going through "resolving" (D-11 clean swap).

    (e) Cold-mount trigger (paneKey change) — enter resolving:
    ```
    useEffect(() => {
      if (paneKey !== paneKeyRef.current) {
        paneKeyRef.current = paneKey;
        hasResolvedThisPaneRef.current = false;
        setIsResolving(true);
      }
    }, [paneKey]);
    ```

    (f) Warm re-focus trigger (isVisible false→true edge) — enter resolving. Use prevIsVisibleRef pattern from quick-260809-cnx (PrettyView.tsx:1323-1345). Initial ref value = current isVisible (load-bearing: prevents initial-mount false positive):
    ```
    const prevIsVisibleRef = useRef<boolean>(isVisible);
    useEffect(() => {
      const prev = prevIsVisibleRef.current;
      prevIsVisibleRef.current = isVisible;
      if (!prev && isVisible) {
        // Warm re-focus edge — re-arm resolving.
        hasResolvedThisPaneRef.current = false;
        setIsResolving(true);
      }
    }, [isVisible]);
    ```

Use isVisibleRef mirror so the handler reads current pane visibility without stale-closure hazards, but the visibilitychange handler itself is the trigger — even if the pane is currently hidden the trigger arms when it next becomes visible via edge (f). If the pane IS visible when the document visibilitychange fires visible, re-arm immediately:
    ```
    useEffect(() => {
      const onVis = () => {
        if (document.visibilityState !== "visible") return;
        // Only re-arm if the pane itself is currently visible; otherwise (f) will handle it.
        if (!isVisibleRef.current) return;
        hasResolvedThisPaneRef.current = false;
        setIsResolving(true);
      };
      document.addEventListener("visibilitychange", onVis);
      return () => document.removeEventListener("visibilitychange", onVis);
    }, []);
    ```
