<objective>
Turn IdentityBadge into an HTML5 drag source. When mounted with a new `tabId` prop and NOT on a mobile viewport, the badge root becomes `draggable={true}` and a `dragstart` handler writes the Phase 56 wire contract (text/plain=tabId) alongside a new phase-58 MIME (application/x-skynet-badge=JSON.stringify({tabId})) so downstream drop targets (Phase 56 Pane onDrop = rearrange; Phase 58 Plan 02 conv-list drop = close) can discriminate. All three existing gestures (short click, long press, and now drag) coexist without disambiguation code — the browser's ~5px drag threshold fires above the pointerdown/up level the click + long-press paths use.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-page badge → dataTransfer | badge writes its own tabId into dataTransfer, which downstream handlers read. The badge fully controls the payload it emits — not an untrusted-input surface at this layer. |
| dataTransfer → drop target (Phase 58 Plan 02 conv-list drop, or Phase 56 Pane drop) | untrusted-input surface AT THE DROP TARGET, not at the source. Plan 02 owns validation of the tabId against currently-open tabs (per security_config: "the conv-list drop handler consumes a tabId payload that MUST be validated as a real, currently-open tab id"). Plan 01 (this plan) sets the payload from a self-controlled source and is not itself an attack surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-58-01-01 | Information Disclosure | `console.info("[badge-drag] tabId=… hasIdentity=…")` | mitigate | Log emits only tabId (already visible in DOM via data-testid + AppShell state) and a boolean hasIdentity. NO PII (no identity.displayName, no colorHue, no avatar url). Explicit-field extraction per fleet logging directive; do NOT JSON.stringify the DragEvent. |
| T-58-01-02 | Tampering | Attacker-controlled page overrides window.matchMedia to bypass the mobile gate and enable badge dragging on mobile | accept | Purely fork-local UI; no auth boundary at the mobile gate. The gate is a UX guard (mobile has no SplitView per AppShell.tsx:2372 `{!isMobile && (<SplitView…/>)}` gate) not a security guard. If bypassed, drag payload still routes through the same handlers; net effect is nonsensical UX on mobile, not a security violation. |
| T-58-01-03 | Repudiation | Missing dragstart telemetry means a failed drop can't be reproduced from console alone | mitigate | Structured `[badge-drag]` log with tabId + hasIdentity fields (Test B). Mirrors the `[pv-split-tree]` diag prefix Phase 56 established (see AppShell.tsx:1562-1663 openSessionInTree diag pattern). |
</threat_model>
