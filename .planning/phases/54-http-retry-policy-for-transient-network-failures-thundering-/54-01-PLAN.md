<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → backend HTTP | Retried requests re-cross this boundary; the retry logic must not amplify a single client attack into 3× requests. |
| browser → in-process db-health-monitor state | Interceptor calls into the singleton monitor; timing of calls affects toast UX. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-54-01 | Denial of Service (against backend) | retry loop | mitigate | Attempt cap = 3 (max 2 retries), max total wall-clock ~4-6s per originating request. Full jitter spreads retries so 10-tab restore doesn't produce 30 simultaneous retries at T+300ms. |
| T-54-02 | Tampering (duplicate side-effect on POST) | retry loop | mitigate | Method-aware idempotency safeguard: POST/PUT/PATCH/DELETE retry ONLY on connection-never-established errors (ECONNREFUSED, ERR_NETWORK with response=undefined), never on 5xx where the server may have processed the request. |
| T-54-03 | Elevation of Privilege (401 hidden by retry) | retry classification | mitigate | isRetryable returns false for ALL 4xx (including 401) BEFORE any sleep — 401 fast-path preserved with zero retry delay, session-expired UX unaffected. Statistical test asserts `< 50ms` elapsed for 401 case. |
| T-54-04 | Repudiation (silent retries hide forensics) | logging | mitigate | Per-attempt structured log via getLoggerForService(serviceName).warn with {requestId, method, url, attempt, delayMs, errorCode, errorMessage}. Give-up summary line with attempts=3, finalErrorCode. All log lines forward through /debug/console-log to the console-forward log Tanya greps. |
| T-54-05 | Information Disclosure | escape hatch | accept | __noRetry is a client-controlled config field, not user input. No PII risk. |
</threat_model>
