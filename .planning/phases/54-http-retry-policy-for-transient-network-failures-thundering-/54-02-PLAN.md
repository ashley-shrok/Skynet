<objective>
Inject full-jitter into the three fixed-ladder WebSocket reconnect
schedulers so a 10-tab thundering herd on `/claude-session/websocket/`,
`/fleet-status/ws`, and `/ssh/websocket/` does not re-clump into a new
herd one round later on the reconnect ladder.

## Audit finding (documented per R-54-07)

Kickoff grep evidence (2026-08-23) confirms all three WS clients use
fixed-ladder backoff — NO jitter today:

- `src/ui/api/fleet-status-client.ts:35` —
  `BACKOFF_SCHEDULE_MS = [2000, 4000, 6000, 8000, 8000]` used directly at
  `delayMs = BACKOFF_SCHEDULE_MS[Math.min(reconnectAttempts, ...)]`
  (fleet-status-client.ts:198-200).
- `src/ui/features/pretty-view/PrettyView.tsx:2080` —
  `const delay = Math.min(2000 * (reconnectAttemptsRef.current + 1), 8000);`
- `src/ui/features/terminal/Terminal.tsx:1164-1167` —
  `const delay = Math.min(2000 * Math.pow(2, reconnectAttempts.current - 1), 8000);`

Verdict: **all three need jitter injection** (not "already jittered / no
change" — that outcome was not observed at any site).

## What this plan does

Apply the same full-jitter shape used in Plan 01
(`delay = Math.floor(Math.random() * capMs)`, where `capMs` is the value
currently computed) at each of the three sites. Minimum touch: do NOT
change attempt caps, initial-delay scale, termination conditions,
visibility-change handlers, or any surrounding state-machine logic. The
existing schedules already carry the "how far apart" intent; jitter just
smears each individual delay uniformly across [0, capMs) so N simultaneous
reconnects don't fire together at T+capMs.

Purpose: Prevent the reconnect ladder from itself becoming a thundering
herd. When 10 tabs' WS connections all close together (Chrome restore, or
box briefly overloaded), fixed-ladder would re-fire all 10 reconnects at
exactly T+2s, T+4s, T+6s… — the same herd on the ladder. Full-jitter
spreads each individual tab's retry across the whole [0, cap) window.

Output:
- Three surgical jitter-injection edits (fleet-status-client.ts,
  PrettyView.tsx, Terminal.tsx).
- New jitter-range assertion test in fleet-status-client.test.ts (the
  only client that has an existing, isolatable, mock-WS test harness).
- Documented audit finding at top of each patch site (one-line comment
  citing R-54-07 + CONTEXT.md).
</objective>
