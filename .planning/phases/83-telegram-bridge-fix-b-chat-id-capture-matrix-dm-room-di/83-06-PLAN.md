<objective>
Add a 3-second poll inside TelegramTab so that once the user pastes their bot token (Phase 79 flow → transitions to `pending-start`), the tab polls `GET /telegram/status?identityKey=<key>` and automatically transitions to the `connected` state the moment the bridge reports a non-null `chatId` (the user's `/start` message reached the bridge, Plan 83-01 wrote the sentinel, Plan 83-03 reconciled it into the DB, and Plan 83-05's endpoint surfaces the fresh value).

Purpose: This closes the round-trip UX loop. Without this poll, the user would have to close and reopen the identity modal to see "Connected". With this poll, the transition is automatic and typically completes within 3-6 seconds of sending /start.

Depends on Plan 83-05 (the endpoint). Wave 3.

Constraint from CONTEXT § 5 that MUST be honored:
- Interval: 3-5s (choose 3000ms).
- No timeout that flips to error state ("human gets to it when they get to it").
- Existing Cancel button (Phase 79 § 3B) already wires to the disconnect flow; keep it as-is.
- The chatId-derived "human identifier" — since the endpoint returns only chatId (no @-handle), and the CONTEXT specifies the rendered text "Connected. Bot: @X. Human: @Y.", the practical choice for Y here is the chatId string itself (a numeric Telegram user id) — this matches what's actually available in the DB row post-Plan-83-03. The exact rendered value MUST match the connected-state expected text in the existing test file (Phase 79 test coverage; the test file for this plan will assert the exact string).

       ```typescript
       // Phase 83 Plan 06 — poll GET /telegram/status while awaiting /start.
       // Interval fires every 3s; when the bridge reports a non-null chatId
       // (Plan 83-03 has reconciled the bridge's sentinel into the DB), we
       // transition to "connected". Per CONTEXT § 5, no timeout flips to
       // an error state — human gets to it when they get to it.
       //
       // Cleanup semantics: interval is cleared on unmount AND on any state
       // transition (dependency array below). Errors are swallowed silently
       // and the next tick retries.
       useEffect(() => {
         if (state.status !== "pending-start") return;
         const currentBotUsername = state.botUsername;
         let cancelled = false;

         async function tick(): Promise<void> {
           if (cancelled) return;
           const resp = await getTelegramPendingStatus(identityKey);
           if (cancelled) return;
           if (resp.ok === true && resp.chatId !== null) {
             onStateChange({
               status: "connected",
               botUsername: currentBotUsername,
               telegramHandle: resp.chatId,
             });
           }
           // Errors are silently swallowed — CONTEXT § 5 "no timeout that flips
           // to error". Next tick retries.
         }

         const handle = setInterval(() => {
           void tick();
         }, 3000);

         return () => {
           cancelled = true;
           clearInterval(handle);
         };
         // Effect re-runs on identityKey change or when state.status leaves
         // "pending-start". state.botUsername is captured into
         // currentBotUsername above so we don't need it in the dep array
         // for the transition target — but include it so the closure stays
         // fresh if botUsername ever changes mid-pending-start (defensive).
       }, [
         state.status,
         state.status === "pending-start" ? state.botUsername : "",
         identityKey,
         onStateChange,
       ]);
       ```

       Note: the discriminated-union dep on `state.botUsername` requires the ternary because `state.botUsername` only exists in some variants. Alternatively, extract into a local variable computed once before the deps — either is acceptable; keep the version that TSC accepts under strict mode.
