<objective>
Add a new backend route `GET /telegram/status?identityKey=<key>` returning `{ chatId: string | null }` for the caller's own identity. The frontend TelegramTab (Plan 83-06) polls this while in the "waiting for /start" state; once chatId becomes non-null, the UI transitions to "Connected".

Also add the corresponding frontend client function `getTelegramPendingStatus(identityKey)` to src/ui/api/telegram-api.ts.

Purpose: Bridge the reconcile-loop-side chat_id capture (Plan 83-03 writes telegramChatId to the DB) with the UI activation flow. Without this route, the user pastes a token, sends /start, and the UI never updates — they'd need to close and reopen the identity modal to see the "Connected" state.

Design constraint: NGINX already routes `^/telegram(/.*)?$` to the backend (nginx.conf:189, nginx-https.conf:200). No nginx changes needed. This is critical to note in the SUMMARY.

Depends on Plan 83-03 (which populates telegramChatId that this endpoint reads back). Wave 2.

    // ---------------------------------------------------------------------------
    // GET /telegram/status?identityKey=<key>
    //
    // Phase 83 Plan 05 — read-only endpoint the TelegramTab frontend polls
    // (every ~3s per Plan 83-06) while in the "waiting for /start" state.
    // Returns { chatId: string | null } for the caller's own identity.
    //
    // Distinct from GET /telegram/:identityKey (below): that endpoint returns
    // { status, botUsername, telegramChatId } for the modal's initial paint;
    // this one is a hot poll that returns only the chatId and does NOT
    // include botUsername (frontend already has it from the pending-start
    // state) so the payload is minimal.
    //
    // Ownership check: matches /telegram/disconnect L225-228 — 403 when the
    // row's humanUserId does not match the JWT-authed userId.
    // ---------------------------------------------------------------------------
    router.get(
      "/status",
      authenticateJWT,
      async (req: Request, res: Response): Promise<void> => {
        const authUserId = (req as AuthenticatedRequest).userId;
        const { identityKey } = req.query as Record<string, unknown>;

        if (typeof identityKey !== "string" || !IDENTITY_KEY_RE.test(identityKey)) {
          res
            .status(400)
            .json({ error: "identityKey must match [a-z0-9][a-z0-9_-]{0,63}" });
          return;
        }

        try {
          const row = await getTelegramBotToken(identityKey);
          if (row === null) {
            res.status(404).json({ error: "no telegram binding for identity" });
            return;
          }
          if (row.humanUserId !== authUserId) {
            res.status(403).json({ error: "not your identity" });
            return;
          }
          // Minimal payload — chatId only. Bot token NEVER included.
          res.json({ chatId: row.telegramChatId });
        } catch (err) {
          authLogger.error("Failed to read telegram pending status", err);
          res.status(500).json({ error: "Failed to read telegram status" });
        }
      },
    );
    ```

    interface PendingStatusWireResp {
      chatId?: string | null;
      error?: string;
    }

    /**
     * Phase 83 Plan 05 — poll endpoint the TelegramTab hits every ~3s while
     * awaiting the user's /start message. Returns `{ chatId }` (may be null
     * if the bridge hasn't seen a /start yet).
     *
     * Distinct from getTelegramStatus above (which returns the full
     * connect-page shape used for initial modal paint). This one is the
     * hot poll — minimal payload, no botUsername (caller already has it
     * from the pending-start state).
     */
    export async function getTelegramPendingStatus(
      identityKey: string,
    ): Promise<
      | { ok: true; chatId: string | null }
      | { ok: false; error: string; status?: number }
    > {
      try {
        const resp = await authApi.get<PendingStatusWireResp>(
          `/telegram/status`,
          { params: { identityKey } },
        );
        const data = resp.data ?? {};
        if ("chatId" in data) {
          return { ok: true, chatId: data.chatId ?? null };
        }
        return { ok: false, error: data.error ?? "unexpected response" };
      } catch (err) {
        const anyErr = err as { response?: { status?: number } };
        return { ok: false, error: formatError(err), status: anyErr.response?.status };
      }
    }
    ```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (any user with a valid JWT) → GET /telegram/status | Query param `identityKey` is attacker-controlled. |
| GET /telegram/status handler → telegram_bot_tokens SELECT | Regex-validated identityKey feeds into the store's parameterized WHERE clause. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-83-05-01 | Spoofing | unauthenticated user accessing another human's chat_id | mitigate | `authenticateJWT` middleware runs first (test STS-08 asserts 401). Ownership check `row.humanUserId !== authUserId → 403` blocks cross-user reads (test STS-07). |
| T-83-05-02 | Tampering | SQL injection via identityKey | mitigate | Query param regex-validated by IDENTITY_KEY_RE (`/^[a-z0-9][a-z0-9_-]{0,63}$/`) BEFORE it reaches getTelegramBotToken. getTelegramBotToken uses drizzle `.where(eq(...))` — parameterized query. Test STS-04 and STS-05 assert 400 on regex fail. |
| T-83-05-03 | Information Disclosure | bot token leaked in status response | mitigate | Response body is `{ chatId }` ONLY. Test STS-01 asserts bot token is NOT present. Distinct from GET /:identityKey which includes botUsername (not the token). |
| T-83-05-04 | Denial of Service | frontend polls every 3s → route abuse | accept | Poll runs only while the tab is open AND state is "pending-start". Payload is 1 row lookup + JSON serialization. Cost negligible vs. existing per-tab telemetry. If a client hammers, the JWT-auth gate + user's DB row uniqueness limits blast radius to that user's chat_id (already accessible to them). |
| T-83-05-05 | Repudiation | endpoint silently fails without logs | mitigate | Try/catch in the handler calls `authLogger.error("Failed to read telegram pending status", err)` on unexpected throw. 400/403/404 paths intentionally do not log (would spam logs on legitimate 404s during pending-start). |
| T-83-05-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs. All imports are existing modules. N/A. |
