<why_both_sources>
**Read this before writing any code. It is the load-bearing fact of the plan and it is not obvious from the file.**

Both sources publish through `deps.registry.publishSessionState(host.id, state)`, and the registry keys its state Map on `` `${hostId}:${tmuxSession ?? ""}` ``. Source B publishes with `tmuxSession` set to the **identity name**; source A's batch path sets `tmuxSession` from `pidLine.identity`, which is **the same string**. So for a given identity, source A and source B write the SAME registry key.

They do not fight, because of the skip-and-evict at the top of `composeAndPublishPerIdentity`:

  `if (liveTmuxSet.has(name) && !isRecycling) { ...evict...; return; }`

Which means:

| Identity population | Who publishes | Who is silent |
|---|---|---|
| has a live claude PID, not recycling | **source A only** | source B evicts and returns |
| no live PID (dormant), or recycling | **source B only** | source A has no pid line |

**Therefore appearance must ride BOTH.** Putting it only on source B means every busy agent — the common case — renders undressed. Putting it only on source A means every dormant agent renders undressed. RESEARCH's warning ("missing source B means appearance works for busy agents and silently fails for dormant ones") is the second of those two failures; this plan must avoid both.

**Where source A gets appearance without a new read:** `pollOneHostBatch` already builds `identityLineByName: Map<string, SweepIdentityLine>` and already passes it into `pidLineToPerPidFetched`, which already joins to it for `jsonl_path` (the A11 fold). Appearance comes off that same joined line. Zero new SSH channels, zero new reads — which is the whole point of D-01.

**Consequence for the frontend:** because both sources carry the same resolved appearance for the same identity, a source-A frame never blanks what a source-B frame wrote, and vice versa. The frontend's additive merge (Plan 111-04) is a second belt, not the primary defence.
</why_both_sources>

<the_two_fingerprints>

A grep for `computeFingerprint` will NOT find it. **No commit in this repo's history has ever widened source B's fingerprint.** Phase 62's `0b586bfd` supplies the discipline — the rulebook — but not a diff to copy. This is new work with a borrowed rulebook; read that commit's message before writing the code.

**Append-at-END rule**, stated twice in the comments above `computeFingerprint`: "Fingerprint segments MUST live at the END of the template literal so any future axis is appended after these two without disturbing the delta contract." Obey it at both sites.

**Normalization conventions to copy:** strings/numbers → `?? ""`; booleans → tri-valued `x === true ? "1" : x === false ? "0" : ""` so a first-time-null publish stays distinguishable from a cold cache.
</the_two_fingerprints>

<resolved_open_questions>
**Where the merge runs. RESOLVED: in ONE shared helper inside the orchestrator, `appearanceFromIdentityLine`, called by both adapters.** It calls `resolveIdentityAppearance` from Plan 111-02 — it does not reimplement any cascade. Both adapters calling one helper is what keeps a single call site for the merge authority even though there are two consumers.

**`subscription-registry.ts` is NOT modified.** PATTERNS' "Do NOT Copy" table is explicit: the `contextPct` re-stamp pattern is a correct mechanism analog but wrong here, because `contextPct` re-stamps from a separate out-of-band store, whereas appearance arrives ON the frame. Re-stamping appearance would require inventing a second server-side appearance store — a second authority. Appearance rides `SessionState` through the registry untouched, and the registry's existing snapshot-on-subscribe already replays it, which is exactly why "answer instantly on open" needs no work here.
