<resolved_open_questions>
**Absent-key merges: no-op, or stage into a side map? RESOLVED: no-op, plus a debug log.**

A side map sounds appealing — hold the appearance until `GET /identities` populates the row, then apply it. It is rejected because a staging map is a second place appearance lives, which is the "appearance ends up with two sources" failure the shape names, and it would need its own eviction policy, its own ordering rules against `setIdentities`, and its own tests.

The no-op is correct because it costs nothing: `GET /identities` reads the SAME disk frontmatter through `publicIdentity()`, which now calls the SAME merge authority (Plan 111-02), so the row arrives fully dressed from the fetch. The pulse's job is keeping it current, not bootstrapping it. And `ensureFleetSubscription` already fires `refreshIdentities()` on the first non-empty `fleetSessions` notification, so an identity the pulse knows about triggers the fetch that will make the subsequent merge land.

**Does the pulse write `pinned` / `hidden`? RESOLVED: yes, and it must also reach the row-id sets.**

`pinned` and `hidden` live on the `Identity` object, and the panel projects them into row-id space via `deriveDiskPinnedIds` / `deriveDiskHiddenIds` inside a `hydratedRef`-guarded, both-loaded-gated effect that fires ONCE per mount. So merging `pinned` into the store alone does not move a row — the projection has already run. Task 3 handles this WITHOUT touching `PrettyConversationsPanel.tsx` (freshly fixed, 4,906 lines, explicitly "prefer not to touch"): the re-projection is driven from `identities-store` itself.

**Field set the pulse may write.** Exactly the nine the wire carries plus the two sentinels: `displayName`, `title`, `colorHue`, `voice`, `task`, `coordinator`, `role`, `roleDefaults`, `avatarUrl`, `pinned`, `hidden`. **NOT** `avatarMime` or `avatarEtag` — the sweep has no source for them (they derive from the avatar file, not frontmatter), so they are absent from the frame and the additive skip leaves the fetch's values intact. **NOT** `identityKey` or `hostId` — those are the identity of the row, not its appearance.
</resolved_open_questions>

Behaviour, in order:

1. **Guard the inputs.** Return immediately if `!Number.isFinite(hostId)` or `identityKey` is empty. A non-finite hostId cannot key `byHostKey` and would silently mis-serve lookups.

2. **Locate by composite key only.** Find the index in `state.identities` where `i.identityKey.toLowerCase() === identityKey.toLowerCase() && i.hostId === hostId`. Copy the `findIndex` composite shape from `applyIdentityChange`'s locate half — but NOT its bare-name fallback and NOT anything after the locate. **Never use `byKey`** for this: `byKey` collides by design (last wire-order wins) and the store's own comment says cosmetics consumers must use `byHostKey`. A bare-name fallback here would serve one host's appearance to a same-named identity on another host.

3. **Absent → no-op.** If the index is `-1`, emit one `console.debug` with `operation: "identities_store_appearance_merge_no_row"` plus `hostId` and `identityKey`, then return. **Do NOT append.** Add a comment stating that appending a partial row is the path that poisons `byKey` while `loaded` is true, citing `isIdentityPane` in `tabUtils.tsx` and the 2026-09-08 block above. Note that the fuller `GET /identities` will bring the row dressed because it now goes through the same merge authority, so nothing is lost by dropping this write.

4. **Additive field-wise merge with a per-field no-op check.** Build the next `Identity` by starting from `{ ...existing }` and, for each of the eleven permitted keys: skip when the incoming value is `undefined` OR `null`; skip when it is already strictly equal to the existing value; otherwise assign and set a `changed` flag.
   - `null` is skipped, not written. This is D-09 mechanically: `identityAppearance.title === null` means "this identity has no title", but it also arrives for an identity whose file could not be read this tick, and the two are indistinguishable at this boundary. Skipping means a row never undresses. Add a comment saying exactly that, and naming the tradeoff: a title genuinely CLEARED on disk will not disappear from the list until the next `GET /identities`. That is the correct side to err on — the shape's bar is that no row is seen in a state it grows out of, and a stale-but-dressed row is invisible while an undressed row is the bug being fixed.
   - `roleDefaults` is an object; compare with `Object.is` (reference) and accept the incoming value when references differ. A redundant assignment of a structurally-equal object is harmless here because the next step's `changed` flag only controls whether we notify, and Task 2's test 3 pins that a structurally-identical re-merge does not notify — so compare `roleDefaults` by sorted-key serialization, matching the determinism requirement the backend fingerprint already obeys. Use a small local helper; do not import one.
   - `pinned` / `hidden` are booleans and DO get written when they differ, including `true → false`. They are membership and position, not cosmetics: a `false` here is a real fact from a sentinel probe, not an absence. The fail-closed handling already happened server-side (`=== true` in Plan 111-03), so by the time a value reaches this door it is a definite boolean.

5. **`if (!changed) return;`** — copy `patchIdentityFlag`'s no-op suppression verbatim in spirit. No state write, no notify.

   `state = { identities: nextList, byKey, byHostKey, loaded: state.loaded };`
   **`loaded: state.loaded`** — carried forward, never set. Then `notify()`.
   - To keep the index-rebuild in one place rather than duplicated, extract the rebuild + normalize into a private `function reindex(list: Identity[]): { identities: Identity[]; byKey: Map<string, Identity>; byHostKey: Map<string, Identity> }` and have BOTH `setIdentities` and `mergeIdentityAppearance` call it. `setIdentities` then spreads it with `loaded: true`; `mergeIdentityAppearance` spreads it with `loaded: state.loaded`. This is what satisfies D-09's "one place appearance can be written" while satisfying D-10's "the pulse must not set `loaded`": one normalization and indexing tail, two doors with different authority over exactly one field.
