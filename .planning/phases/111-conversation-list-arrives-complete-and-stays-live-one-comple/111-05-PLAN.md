**Grep-verified state of the world before this plan:** the `gone` frame is wired end-to-end (`makeGoneFrame` → `publishSessionGone` → the client's `gone` case → `AppShell`'s `onGone`) but **every consumer only marks per-session STATE** — `publishFleetStatusSessionGone`, `publishFleetStatusWaitingFor(null)`, `publishFleetStatusTmuxSessionGone`. **No WS callback anywhere calls `updateFleetSessions` or `removeFleetSession`.** The only `removeFleetSession` caller in the app is the manual Kill handler.

Rows are built exclusively from `state.fleetSessions` (iterated twice in `computeSnapshot` — once for the role map, once for the synthetic-row builder), and `state.fleetSessions` is written by exactly three things: `updateFleetSessions`, the localStorage cache seed, and `removeFleetSession`. All three are request-response or manual-action paths.

So: the transport is complete, the store mutators exist, and the wire between them has never been connected. PATTERNS ranks `advanceSessionAiTitle` as the closest analog for the additive-merge SEMANTICS and `removeFleetSession` as the analog for the SHAPE. Neither is a drop-in.

<resolved_open_questions>
**Open Question 2 — where does `hostName` come from for a pulse-created row? RESOLVED: resolve from `state.hostsFlat`. Do NOT widen the wire.**

`FleetSession` requires `hostName: string`; `SessionState` carries only `hostId`. `state.hostsFlat` is a `Map<number, Host>` populated from `realHostTree` via `updateHostsFlat`, and the row-builder ALREADY tolerates a miss — `resolvedHost` falls back to `undefined` and `fleetHostNameFallback` exists precisely for the host-absent case (see the Test 28 comment above it). So a miss degrades to today's behaviour rather than breaking. Widening the wire for a value the client already holds would add a field to five type mirrors for nothing. Resolution: `upsertFleetSession` takes `hostName` on the session it is handed, and the CALLER reads `state.hostsFlat` via the store's existing snapshot accessor. Empty string is the honest miss — the row still exists and still groups.

**Open Question 3 — should the pulse's upsert gate on `fleetSessionsLoaded`? RESOLVED: NO gate, plus the test that closes the ambiguity.**

The concern is a pulse-created row being wiped when the one-shot fetch's array-replacing `updateFleetSessions(fresh)` lands. It is self-healing in the steady state (the fetch's snapshot is a superset) and losing a row for one round-trip is invisible. Gating on the flag would be strictly worse: it would suppress exactly the D-06 case the backstop exists for — a session the fetch cannot see yet — and it would make the live path depend on the frozen path's completion, which is the coupling this phase removes. Task 2 case 9 pins the interaction explicitly.

**Appearance does NOT ride `FleetSession`. Locked.** Putting it there costs three coupled edits — bump `FLEET_CACHE_KEY` (currently `v4`), extend `writeFleetSessionsCache`'s deliberate 4-field WHITELIST ("Serializes only the 4 canonical FleetSession fields so future field additions on FleetSession don't silently leak to storage"), and extend `isFleetSession` — for a value the server re-serves instantly from its held Map on every connect. The shape explicitly prefers browser-side appearance memory being unnecessary. **This plan therefore does NOT bump the cache key and does NOT touch the cache writer.**

**`created` for a pulse-created row.** Not on the wire. Use `Date.now()` at the caller. `created` feeds row ordering only as a tiebreaker behind `lastMessageAt`, and a session the pulse just discovered genuinely is newly-known-to-this-client. On a subsequent `updateFleetSessions(fresh)` the authoritative value from `/sessions/list` replaces it. Do NOT invent a sentinel like `0` — that would sort a live session to an ordering extreme.

**`role` for a pulse-created row.** `SessionState` has no `role`, but `identityAppearance.role` does (Plan 111-02), and Plan 111-04 merged it into `identities-store` a statement earlier in the same callback body. Take `role` from `state.identityAppearance?.role ?? null`. This is why appearance-first ordering is load-bearing beyond cosmetics: it is also the row's role.

**D-08 — the two hand-wired refresh exceptions (identity create, relay-room create) stay.** They are now likely redundant, and CONTEXT.md hands the planner the call on whether removal lands here. **Decision: leave them, note the supersession in the SUMMARY.** Removing a working refresh path in the same plan that first makes rows self-appearing means a regression in either half is indistinguishable from a regression in the other. The bounty `sidebar-fleet-sessions-refresh-after-identity-create` closes as superseded only after this plan's behaviour is confirmed in UAT.
</resolved_open_questions>
