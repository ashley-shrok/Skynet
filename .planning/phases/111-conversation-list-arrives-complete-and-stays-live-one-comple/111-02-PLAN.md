<resolved_open_questions>
**Open Question 1 — merge in Python or TypeScript? RESOLVED: TypeScript, in one shared module that `publicIdentity()` also consumes.**

The sweep emits RAW `identity_cosmetics` + `role_cosmetics` (Plan 111-01). This plan extracts the cascade currently inlined in `publicIdentity()` (`identities.ts`, the `mergedTitle` / `mergedColorHue` / `mergedVoice` block) into `src/backend/fleet-status/identity-appearance.ts`, then rewrites `publicIdentity()` to call it. Result: ONE cascade, two callers. A Python reimplementation was rejected because it would place a second copy of the two non-obvious carve-outs (`task` not inherited; `displayName` falls back to `capitalizeFirst(identityKey)`) in a second language with no shared test. The counter-argument RESEARCH raised — a slightly wider wire — is accepted: the wire carries two small raw objects instead of one merged one, which is noise against the 256KB `jsonl_tail` the same wire already carries.

**Open Question 4 — does `SWEEP_FIELD_PARITY` gain the new field names? RESOLVED: yes, `B6`..`B9`.** The map's stated purpose is typo + documentation protection and both still apply to four new field names. The alternative (a prose note that appearance is outside the inventory) forfeits the typo protection that the `sweep-schema.test.ts` parity walk provides.

**Planner decision — ONE nested wire field, not ten flat ones.** `SessionState` gains a single `identityAppearance` field, `.nullable().optional()`, carrying the resolved appearance object. Rationale: appearance is per-IDENTITY while every other `SessionState` field is per-SESSION, and nesting keeps that distinction legible instead of dissolving ten identity-scoped fields into a session-scoped shape; it keeps the additive-optional invariant to a single field; and it reduces both publish-gating fingerprints to one stable segment rather than ten appended ones. The counter-argument — that the seven-precedent convention in `wire-protocol.ts` is flat scalar fields — is real, and is answered by the fact that every one of those precedents added a *scalar*, and no precedent exists for adding ten at once. The CONTEXT.md discretion item asking for `publicIdentity()` field NAMES is honoured: the names inside the nested object are `publicIdentity()`'s names verbatim, so the frontend merge is still a straight field copy.

**Planner decision — `avatarMime` and `avatarEtag` do NOT ride the pulse.** Both are derived from the avatar FILE on disk, not from frontmatter, so the sweep has no source for them. `avatarUrl` DOES ride the pulse because it is deterministic from `(identityKey, hostId)` and requires no read. The frontend merge is additive and skips absent fields (Plan 111-04), so `avatarMime`/`avatarEtag` continue to arrive from `GET /identities` and are never blanked. The row's avatar renders from `avatarUrl` alone, so this carve-out costs nothing at the pixel.
