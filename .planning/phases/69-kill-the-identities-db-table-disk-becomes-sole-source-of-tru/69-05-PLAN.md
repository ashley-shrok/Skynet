    Add a new exported function colocated after runIdentitiesCosmeticDrops (after current L751):
    ```
    /**
     * Phase 69: drop the identities table entirely. Idempotent via IF EXISTS —
     * safe on fresh installs (table never existed) and upgraded installs
     * (table dropped on first successful boot; subsequent boots no-op).
     * Runs AFTER runIdentitiesCosmeticDrops so any lingering column drops
     * from a stale table on legacy installs complete before the whole
     * table goes away (both are no-op if the table is absent).
     *
     * Exported for test coverage (Test 5 + Test 6 exercise this against
     * test-owned in-memory databases).
     */
    export function runIdentitiesTableDrop(sqliteDb: Database.Database): void {
      try {
        sqliteDb.exec("DROP TABLE IF EXISTS identities;");
      } catch (dropError) {
        // Non-fatal per T-66-04-01 precedent — a failed drop leaves the
        // table intact (deadweight, not corruption). Since no runtime code
        // path reads or writes it post-Phase-68, a lingering table is inert.
        // Next boot retries via IF EXISTS.
        databaseLogger.warn(
          "Failed to drop identities table",
          {
            operation: "schema_migration_drop_table",
            table: "identities",
            error: dropError,
          },
        );
      }
    }
    ```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Boot-time schema mutation → encrypted SQLite | DROP TABLE mutates the encrypted DB file (via RAM + forceSave); DLM daily snapshot is the 7-day retention safety net per CLAUDE.md. Same pattern as Phase 66 Plan 04. |
| runIdentitiesTableDrop idempotency | IF EXISTS ensures fresh installs no-op; upgraded installs drop once then no-op forever. Failed drops (rare, e.g. FK constraint from an unrelated table) log and no-op — non-fatal per T-66-04-01 precedent. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-69-05-01 | Data Integrity | boot fails mid-migration between DROP and forceSave | mitigate | The DROP is idempotent via IF EXISTS. If boot crashes after DROP but before forceSave, the encrypted disk still has the pre-drop file. Next boot loads the pre-drop state and re-runs DROP in RAM. Every boot fires the drop until forceSave succeeds ONCE. Not clean but not broken — the RAM state is always post-drop; only the persisted state lags. Documented in SUMMARY. |
| T-69-05-02 | Data Loss | rollback needed post-deploy | accept | DLM daily snapshot restores the pre-Phase-68 file including the identities table + all its rows. Ashley's "git revert + docker recreate + DLM restore" recovery path unchanged from Phase 66 Plan 04. Table drop is one-way at the software layer; DLM is the backup. |
| T-69-05-03 | Compatibility | old client hits new server (any consumer expecting the identities table to exist) | mitigate | Waves 1-4 already removed every runtime consumer. Plan 69-05 is the last remove; no consumer survives the phase. TSC gate at Task 2 verifies. |
| T-69-05-04 | Availability | DROP TABLE fails on the runtime DB (unexpected FK constraint or SQLite quirk) | mitigate | runIdentitiesTableDrop wraps the DROP in try/catch that logs but does not throw.
