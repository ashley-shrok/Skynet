<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| In-process orchestrator publish → in-memory `apps` map | Trusted boundary (both sides are Skynet backend); no injection surface. But the map's key format MUST NOT collide with sibling maps (RESEARCH § Q9 slug-vs-tmuxSession). |
| Registry fan-out → subscriber `send` callbacks | Multiple subscribers may share the same registry; one bad subscriber's `send` throw MUST NOT starve others (existing `fanOut` invariant). |
| Wire boundary — outbound frame → serialized JSON on WebSocket | Frame shape MUST match `AppStateSchema` at runtime, or clients could see malformed frames. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-118-03-KC | Tampering | Key collision between apps map and sessions map (both use `hostId:*` keys) | mitigate | Apps live in a SEPARATE `Map` object with a SEPARATE keying helper `makeAppKey`. The two maps cannot alias — a `slug` and a `tmuxSession` that happen to be byte-identical strings live in distinct maps. `makeKey` is NEVER called with a slug in this plan. |
| T-118-03-IL | Information Disclosure | UNFILTERED fan-out this phase | accept (in this plan; mitigated in 118-05) | This plan deliberately ships unfiltered fan-out. Every subscriber to `/fleet-status/ws` will see every app frame across every box until Plan 118-05 lands the per-user filter. In this intermediate state, the leak matches the CURRENT identity-frame situation (identity frames are also unfiltered today per RESEARCH § Q4 — one call site of `checkHostAccess` and it's a docblock, not a real invocation). This is not a regression; it is a same-shape gap that 118-05 closes for apps (and, per D-15, sets the pattern for identities to adopt later). **Ordering discipline:** 118-05 MUST land in the same deploy as 118-03 + 118-04. This is a plan-set integrity requirement — do NOT ship 118-03 alone. |
| T-118-03-SP | Spoofing | An in-process caller publishing a fake `AppState` for a hostId the user doesn't actually run | mitigate | Only `ssh-poll-orchestrator.ts` (Plan 118-04) calls `publishAppUpdate`; no external caller has access to the registry instance. The orchestrator's data source is the JSONL from `fleet-status-sweep.py` on the specific SSH-managed host, so hostId provenance is trusted at the exec boundary. |
| T-118-03-DoS | DoS | Publish flood (misbehaving sweep on one box) | mitigate | The orchestrator's per-box exec cadence is 2s (unchanged in this phase).
