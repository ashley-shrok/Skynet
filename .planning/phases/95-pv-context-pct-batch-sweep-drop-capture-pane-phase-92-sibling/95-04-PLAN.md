**MEDIUM-confidence decision #2 — SSH-topology for Part C — RESOLVED IN THIS PLAN. Documented rationale:**

RESEARCH G1 flags that claude-session-server has NO per-host shared SSH connection — each PrettyView WebSocket gets its own via `connectOneShot` (grep confirms L1239/L1357/L1429/L1515/L1609/L1669/L1727/L1796/L1874 all use `connectOneShot`). The three topology options:

- **Option 1 (per-host coordinator):** requires a new per-host shared-SSH-connection subsystem — architectural surface + new lifetime + new failure modes. NOT DOCUMENTED in RESEARCH as a small change; explicit warning at G1 "doesn't map directly." Cost: a full sub-plan of connection-pool refactor plumbing, likely doubling this phase's scope. Reject for Phase 95.
- **Option 2 (elected WS):** cross-WS election plumbing + fan-out registry + failover on WS-close-mid-election. Sits atop the same per-WS connection reality; the "elected" WS still uses its own connection, others just don't run their sweep. Reasonable but adds coordination code without the connection-refactor payoff of Option 1. Reject for Phase 95 — the coordination code is meaningful and would need its own plan.
- **Option 3 (per-WS):** each WS runs its own sweep exec each tick. Trivially compatible with today's per-WS connection reality. Reduces exec count from up-to-4 per WS per tick (today's tail-expansion loop) to 1 per WS per tick — 4x reduction. Zero new plumbing.
