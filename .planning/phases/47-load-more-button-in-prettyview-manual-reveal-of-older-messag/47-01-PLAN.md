Land the shared foundations Phase 47 depends on before the frontend integration (Plan 04) or backend handler (Plan 03) touch the same wire contract:

1. Extend `src/ui/api/claude-session-api.ts` with the Phase 47 wire types — client request payload (line-cursor shape, NOT eventId-cursor, to avoid any cursor-search on the server), server response event (with `oldestLine` so the client can advance its cursor), additive widening of the connect-time `session` frame with `totalLines?: number`, and additive widening of every per-turn wire frame with `line?: number` so the client can track its oldest loaded line from initial hydration onward.
2. Create a NEW backend helper `src/backend/claude-session/session-file-range-reader.ts` that reads a bounded contiguous slice of lines from the on-disk JSONL session file, with LOCAL vs REMOTE branches mirroring `identity-artifact-reader.ts § readIdentityFile`. Carry the reader's own file-local `execWithTimeout` (the version in identity-artifact-reader.ts:261 is `function`-not-`export function`; there is no shared exec-with-timeout module to import from — grep across `src/backend/` confirms 5 duplicate file-local copies today, and this new file makes it 6 — planner accepts the duplication over creating a share point in this plan, matching the shellEscape copy-not-share precedent from session-file-tail.ts:27-29).

Purpose: Both consumers (Plan 03 backend handler + Plan 04 frontend integration) need these shared building blocks. Isolating them here lets Waves 03 and 04 run in parallel against a stable contract, and keeps the type-name forbidden-list violation risk (Test H) contained to one file diff. The line-cursor semantic (over eventId-cursor) also removes the need for any server-side cursor-search — the handler does one bounded `readSessionFileRange` call per request. This is a **critical simplification** revised in after checker feedback: an eventId-cursor would have required scanning up to totalLines of the JSONL to find the matching line, which contradicts the reader's 200-line hard cap and would crash on any session larger than 200 lines.

Output: One MODIFIED file + one NEW file. No behavior change on their own — no runtime code consumes these until Plans 03 + 04 land. tsc-clean (frontend) + build:backend-clean (backend) is the observable end state.
