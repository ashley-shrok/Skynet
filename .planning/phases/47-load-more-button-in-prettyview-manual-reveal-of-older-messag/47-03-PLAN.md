<objective>
Land the backend WS message handler that fulfills the `fetch_older_range` request Plan 01's wire type defined. The handler uses Plan 01's line-cursor semantic — client sends `beforeLine: number` — so no cursor-search is needed; the handler does ONE bounded `readSessionFileRange` call for lines `[max(1, beforeLine - count), beforeLine - 1]` inclusive, parses each returned line via the existing `parseSessionLine`, reshapes each parsed line into the wire-frame shape via a NEW shared helper (extracted from the current streaming-tail switch), and emits a `fetch_older_range_batch` response with the parsed+reshaped frames + the batch's `oldestLine` + a `hasMore` flag.

Purpose: This is the server side of the load-more contract. Plan 04's frontend integration cannot ship until the handler exists — Plan 04 will send the request payload and consume the response event. This plan's test suite proves the handler works in isolation via the extracted-function + test-seam pattern established by `handleIdentityGetRoleFile` (L738-795 + `__handleIdentityGetRoleFileForTests` at L873). This plan also lands the SHARED `reshapeParsedLineToWireFrame` helper — extracted from the current streaming-tail switch at L2416-2522 — so streaming and range paths produce byte-identical wire shapes (including the new `line: number` field Plan 01 added to every per-turn wire type). This is a **critical revision** after checker feedback: without the shared helper, the range handler and the streaming-tail would drift on wire shape (parser produces `{ kind: "..." }`, wire expects `{ type: "..." }` with content, role, eventId, ts fields — the reshape is 100+ lines of case handling; duplicating it would guarantee bugs).
