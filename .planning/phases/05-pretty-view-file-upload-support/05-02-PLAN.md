Return shape:

```
{
  stagedAttachments: Array<{ tempId: string; file: File; status: 'staged' | 'uploading' | 'complete' | 'error'; bytesUploaded: number; error: string | null }>;
  folderDropRejected: boolean;                    // flips true for ~3s on folder drop then auto-clears
  batchInFlight: boolean;                         // true from startBatch until onUploadReadyToInject OR failure
  pendingSendWaitingForWs: boolean;               // true when disconnect-mid-batch has parked chunk emission
  stageAttachments(items: File[] | DataTransferItemList | FileList): void;
  removeAttachment(tempId: string): void;
  startBatch(caption: string): Promise<{ messageQueueItemId: string } | null>;
  retryBatch(): Promise<{ messageQueueItemId: string } | null>;
  resetBatch(): void;                             // called by caller after onUploadReadyToInject fires — clears stagedAttachments, clears batchInFlight, ready for next
  onWsReconnect(): void;                          // imperative hook the caller invokes when WS transitions to open after a disconnect
}
```

Internal implementation notes:

- `tempId` generation: `crypto.randomUUID()`. `messageQueueItemId` generation: same — one per batch, retained across retries until resetBatch clears it.
- Chunk pump uses `File.slice(offset, offset + CHUNK_SIZE_BYTES).arrayBuffer()` for streaming (never load the full file into memory).
- Base64 encode chunks via `btoa(String.fromCharCode(...new Uint8Array(chunkBuffer)))` — acceptable perf up to 64KB. For larger CHUNK_SIZE the encoding would need worker offload; 64KB is fine on main thread.
- Concurrency: implement as a per-file async loop, gated by a shared `activeUploads` counter and a `MAX_CONCURRENT_UPLOADS_PER_BATCH` semaphore.
- Backpressure: before each `ws.send(upload_chunk)`, check `getBufferedAmount?.() ?? 0`; if > 4MB (4 * 1024 * 1024), `await new Promise(resolve => setTimeout(resolve, 50))` and re-check up to 60 iterations (~3s hard timeout, then abort with `upload_failed` reason `"sftp_error"` and message "WS buffer stuck"). Alternative: use the browser's `WebSocket.bufferedAmount` polling — same effect. Callers pass in `getBufferedAmount: () => ws.bufferedAmount`.
- Folder detection: for `DataTransferItemList`, iterate items and check `item.webkitGetAsEntry?.().isDirectory`. For plain File objects (paste path), check `file.type === '' && file.size === 0` (imperfect — some Windows shortcuts also present this way, but paste path typically only gets image blobs or explicit File objects, so acceptable). If any item is a directory → set `folderDropRejected = true`, `setTimeout(() => setFolderDropRejected(false), 3000)`, return without staging any files (all-or-nothing per the shape's "refuse the drop entirely, don't stage the file portion" implied posture).
- WS listener: the hook does NOT own the WS. The caller passes it in. The hook attaches a `message` handler on mount (React 19 `useEffect` with cleanup) that filters events to the four upload_* server types via a type guard using the exported `PrettyViewUploadServerEvent` discriminator.
- Retry semantics: `retryBatch()` scans stagedAttachments; any with status `'complete'` are skipped (already landed on the receiving box — no re-upload needed; Plan 03 checks landing paths on complete files to reuse them in the injected turn). Any with `'error'` or `'staged'` are re-sent using the SAME messageQueueItemId. Backend: since the batch was deleted from `activeBatches` after any failure (Plan 01 orchestrator does this), a retry effectively creates a fresh backend batch under the same id — the client's upload_start payload will include ALL files (both already-complete and to-retry) — Plan 01 must handle this idempotently OR Plan 03 must call an `upload_reset { messageQueueItemId }` first. Add a THIRTEENTH message type `upload_reset` to the protocol in Plan 01 to keep the semantics clean; if Plan 01 has already shipped without it, this hook instead re-uploads ALL files including the previously-complete ones (wasteful but correct — makes the retry a fresh batch server-side).

  **DECISION FOR THIS PLAN:** since Plan 01 defines the protocol without an `upload_reset` message, the hook uses the SIMPLER path: on retry, re-upload ALL files under a NEW messageQueueItemId. The frontend surfaces retry as "starting over with the same caption + same files"; the backend sees a fresh batch. The queue-row lifecycle (patch #60) remains intact because the injected-turn's send uses the NEW id, and the OLD id is orphaned server-side (no queue row was ever written for either — the queue row is only created client-side when Plan 03 wires this in). This simplifies the semantics; document clearly in the hook JSDoc.
- `onWsReconnect()`: check if `pendingSendWaitingForWs === true`; if yes, resume by re-emitting from the last unacked chunk offset per tempId. Server-side: since upload_start declared the sizes, the server may have partial temp files from the pre-disconnect run; those may fail with `wx` flag on retry. Simplest: on `onWsReconnect`, tear down (call retryBatch which restarts with a new messageQueueItemId).
- All state is React-only (`useState`, `useReducer`, `useRef`). NO localStorage, NO IndexedDB, NO sessionStorage — attachment bytes MUST NOT persist across tab close per UPLOAD-08.
