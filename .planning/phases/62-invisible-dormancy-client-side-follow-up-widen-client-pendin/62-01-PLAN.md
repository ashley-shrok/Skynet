<objective>
Widen the PrettyView pending-send client-side timer for dormant sends — the symmetric client-side half of Phase 60's backend `pv-send-watchdog` widening. When a send is armed while `dormantRef.current === true` (i.e. the pane is dormant and the send will invisibly wake it), the client timer stretches from `PENDING_SEND_TIMEOUT_MS_NORMAL = 20_000ms` to `PENDING_SEND_TIMEOUT_MS_DORMANT = 220_000ms` (per D-62-02: ceiling MUST exceed the backend's `MARKER_FALLBACK_MS + GIVE_UP_MS_DORMANT` sequence so the client does not race the backend and pre-emptively red-bubble a healthy wake). Awake-pane sends use the existing 20000ms unchanged (per D-62-03: read `dormantRef.current` at arm time only — no retroactive re-arm on late-arriving dormant frames). The flip-to-failed reason label distinguishes the two paths (`client_timeout_20s_normal` vs. `client_timeout_220s_dormant`) so post-ship diagnostics can identify which timing chain fired.

Purpose: On 2026-08-30 Ashley reproduced live on hilda@workstation the exact failure the Phase 60 backend widening was supposed to prevent — client fired `[pv-optim] flip-to-failed reason=client_timeout_20s` at T+20.003s from send, but the backend didn't deliver send-keys until T+31.379s (healthy invisible wake). Bubble went red ~11 seconds BEFORE the message actually landed. Phase 60's shape used singular "widen THE watchdog" wording and only widened the backend; this plan closes the client-side gap.

Output: PrettyView.tsx has two named timeout constants, handleOptimisticSend reads `dormantRef.current` at arm time and branches both the setTimeout duration AND the flipToFailed reason label. PrettyView.optimistic-bubbles.test.tsx gains Test 5b — the locking test that asserts the widened dormant path.
</objective>
