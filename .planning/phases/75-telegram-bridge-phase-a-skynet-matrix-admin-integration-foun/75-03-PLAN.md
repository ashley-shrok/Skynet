<objective>
Land the admin-gated backend endpoint that registers an externally-created mxid against a Skynet user row. Same endpoint handles both cases per Q1 lock:
(a) new-user provisioning runbook — one POST per new user as part of onboarding.
(b) one-shot import for the three pre-existing hand-made accounts (Ashley, Zoe, Laura) — three POSTs at deploy time.

Purpose: this is MXA-04. Without it, there is no way to tell Skynet "this Skynet user maps to that externally-created Matrix account" and Phase B's "mint a token on demand for inbound bridge traffic" cannot know which mxid to mint for.

Output: one new POST /users/:id/mxid handler inside `user-admin-routes.ts` (mirrors POST /users/make-admin at L137-212), plus supertest coverage in a new `user-admin-routes.test.ts` file. Uses the `mxid` column from Plan 75-01.

Decision D-OQ1 (locked here per RESEARCH.md Open Question 1 recommendation A): URL shape is `POST /users/:id/mxid { mxid: string }` — dedicated verb-noun route matching sibling `/users/make-admin`, `/users/remove-admin`, `/users/logout` pattern. NOT `PATCH /users/:id` (no generic user-patch endpoint exists), NOT under a new base path (nginx pass-through is already covered by `^/users(/.*)?$` per Pitfall 1).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → Skynet backend | JWT cookie/Bearer verified by authenticateJWT; admin gate re-verified inside handler (defense in depth) |
| request body mxid string → DB WHERE-parameterized query | Drizzle parameterization is safe; regex-gate blocks shell/URL/SQL injection payloads at handler entry |
| RAM SQLite → encrypted disk SQLite | saveMemoryDatabaseToFile persists after every write; non-fatal warn on transient failure |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-75-10 | Tampering | mxid path-traversal / SQL injection | mitigate | MXID_RE regex-gate at handler entry BEFORE any DB touch; Drizzle parameterized queries for the UPDATE (never string-concat); precedent: Phase 69's IDENTITY_KEY_RE post-review security fix (STATE.md L547) |
| T-75-11 | Elevation of Privilege | non-admin escalates via the new endpoint | mitigate | Defense in depth — authenticateJWT middleware verifies session, in-handler users.isAdmin check re-verifies (matches sibling make-admin at user-admin-routes.ts:152-158) |
| T-75-12 | Tampering | replay POST overwrites correct mxid | accept | Idempotent: a second correct call fixes it. Audit log includes current mxid so any accidental overwrite is grep-able post-hoc. Ashley's operational discipline is the mitigation. |
| T-75-13 | Information Disclosure | admin sets mxid pointing to account they control, then reads agent DMs to that human | accept | Threat model accepts "trust in admin role" — an admin already has Skynet admin power and can do far worse. Audit log with adminId + targetUserId + mxid is grep-able. RESEARCH.md § Security Domain records this same acceptance. |
| T-75-14 | Repudiation | mxid change without audit trail | mitigate | authLogger.info at every successful registration with adminId + targetUserId + mxid; grep-able forever from central log |
| T-75-15 | Information Disclosure | JWT secret leaks via error message | accept | Existing AuthManager handles this class of concern; the new handler adds nothing new — its 401 comes from the middleware, which uses stable error text |
| T-75-SC | Tampering | npm/pip/cargo installs | mitigate | Zero new packages in this plan |
</threat_model>
