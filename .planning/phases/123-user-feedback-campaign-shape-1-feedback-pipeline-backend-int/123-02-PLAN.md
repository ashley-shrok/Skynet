<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → GET /api/feedback/enabled | Auth-cookie-gated fetch — untrusted network transit, trusted response payload (server-controlled) |
| Browser → POST /feedback | Auth-cookie-gated write — payload originates from feedback-api.ts caller, server-side revalidates in Plan 03 |
| feedback-store module scope → React tree | Store is single-tenant per-browser-tab; no cross-user leakage possible |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-123-05 | Tampering (malformed response) | feedback-fetch.ts | mitigate | Inline typeof-guard `isFeedbackEnabledResponse` rejects any response shape that isn't `{enabled: boolean}` — malformed JSON cannot poison the store. Test asserts this via {foo:"bar"} malformed-body case. |
| T-122-06 | Denial-of-Service (fetch throw poisons boot) | feedback-fetch.ts | mitigate | Try/catch around the entire fetch + parse chain with silent retain-default. Test asserts fetch network-throw does not surface. |
| T-122-07 | Information Disclosure (feedback-enabled leak pre-login) | GET /api/feedback/enabled endpoint | mitigate (server-side, Plan 03) | Client-side: fetch fires from AppShell useEffect (after auth) not from main.tsx boot. Server-side: authenticateJWT gates the route (Plan 03 threat model). This plan's mitigation is the docstring divergence note preventing accidental main.tsx call. |
| T-122-08 | Repudiation (silent error surfaces to user as success) | feedback-api.ts postFeedback | accept | D-27 explicitly locks "user always sees Thanks toast regardless." Repudiation risk (user believes send succeeded when it failed) is accepted for v1 per the shape file; console log on backend covers the operator visibility gap. |
