## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ComposeBox handlers → WS `input` frame | User keystrokes become a WS message that the backend interprets as pretty-view input. Payload shape (presence of `messageQueueItemId`) determines whether the Phase 56 backend wake gate fires. |
| Hook → onOptimisticSend | The hook seeds a rendered bubble; any caller-supplied `bubbleTextOverride` becomes visible text in the pretty-view stream. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-68-01 | Information Disclosure | `bubbleTextOverride` in `onOptimisticSend` seed | mitigate | Hook passes `bubbleTextOverride` ONLY to `onOptimisticSend` (render layer); the unmodified `payload` (which may contain the user's actual command text like `/id reset (...)`) always goes to `onSend`. Caller must supply `bubbleTextOverride` as a benign display string (e.g., "👍"), never a lie about what was sent. This plan does NOT introduce any bubbleTextOverride usage (Plan 68-02 does); Task 1 only exposes the parameter. Verify by grep: no call site in this plan passes bubbleTextOverride. |
| T-68-02 | Tampering | mqid predictability / collision | accept | mqid = `pv-optim-<ms>-<8hex-random>`. Not a security token — used only for FIFO matching between ComposeBox seed and returning WS frame within a single browser session. Collision probability across concurrent sends on one tab: negligible (8hex-random ~= 4B space per ms tick). No auth decision keys off mqid; the backend wake gate at claude-session-server.ts L2070-2076 uses mqid presence as a shape check, not as an authorization token. Existing Phase 50 pattern (unchanged). |
| T-68-03 | Elevation of Privilege | Wake path authorization on the funnel | accept | The funnel is a pure frontend refactor. Authorization on wake-then-send is enforced backend-side (`claude-session-server.ts` — same auth middleware the pre-refactor `onSend` calls used). No new auth surface introduced; funnel routes through the SAME `onSend` → `sendInput` → WS chain as today. Verified by inspection: `sendInput` at PrettyView.tsx L996-1011 is unchanged. |
| T-68-04 | Tampering | Render-blacklist bypass | accept-for-this-plan | Task 1 does NOT introduce render-blacklist plumbing (Plan 68-02 does). Task 1's main-textarea flow already renders bubbles today — no new bubble surface added. Threat re-evaluated in Plan 68-02's threat model when reset routes through the funnel. |
| T-68-SC | Tampering | npm/pip/cargo installs | mitigate | No new package installs in this plan. Verify by acceptance criteria: `git diff package.json package-lock.json` produces zero lines. |
</threat_model>
