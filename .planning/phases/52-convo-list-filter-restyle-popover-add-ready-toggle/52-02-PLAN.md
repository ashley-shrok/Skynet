<objective>
Restyle the conversation-list filter popover to match the panel's existing menu vocabulary
(three-dots menu + right-click context menu). Retire the shadcn PopoverContent chrome and
`<Checkbox>`/`<label>` rows; adopt the exact glass chrome + button items pattern that
`PrettyConversationContextMenu.tsx:161-181` (portal-mounted) and the three-dots menu at
`PrettyConversationsPanel.tsx:1622-1675` (also portal-mounted) both use.

Add the `readyOnly` boolean state alongside `pinnedOnly` and `needsDeskOnly`. Wire it as
a third menu-item button in the popover. **This plan does NOT wire the Ready predicate
into `matchesFilterForRow`** — that's Plan 03's job (which needs Plan 01's `useSessionIsDormant`
hook first). The Ready button in this plan flips the `readyOnly` state; Plan 03 makes the
state actually filter rows.

The `anyFilterOn` derivation IS extended in this plan (to include `readyOnly`) so the
filter-icon dot at `.pv-filter-dot` reflects Ready-toggle-on immediately, without waiting
for Plan 03.

**Implementation-shape decision (planner's judgment call per CONTEXT.md):**
Take the **inline-style approach** (option (a) from CONTEXT.md § Popover chrome). Rationale:
the three-dots menu at :1622-1675 uses inline styles exactly this way (portal + inline `style={{}}`),
and CONTEXT.md's own hint says "match whichever the codebase's existing three-dots menu style
implies". Keep Radix `<Popover>` + `<PopoverTrigger>` + `<PopoverContent>` for the trigger +
portal + open/close mechanics (already wired correctly today) — override `<PopoverContent>`'s
chrome via inline `style={{}}` on the PopoverContent element (Radix passes style through to the
rendered element). This avoids `!important` CSS-specificity fighting shadcn's default token
treatment. Item hover/active flashes still use CSS classes (`.pv-filter-menu-item:hover` /
`:active`) so mouse-out state restores automatically without a matching JS listener.

**CRITICAL width-override note (plan-checker W-1 fix, 2026-08-20):** shadcn's
`PopoverContent` (see src/ui/components/popover.tsx:31) carries `w-72` in its Tailwind
className — a fixed 288px `width`. Inline `minWidth: 200` does NOT override `width`
(different CSS properties). The inline style MUST also set `width: "auto"` so the
`w-72` Tailwind utility is overridden by same-property inline wins. Without this
override the filter popover renders 288px wide (way wider than the three-dots menu
which uses no fixed width).

**Task-split judgment call (plan-checker W-4):** Task 2 spans 6 sub-steps
(state, anyFilterOn, markup rewrite, checkbox-import cleanup, matchesFilterForRow
preserve, test adaptations). Plan-checker flagged the option of splitting into 2a
(state + anyFilterOn + imports) + 2b (markup + tests). **Judgment: keep as one task.**
Rationale:
- The state + anyFilterOn changes are 3-line trivial edits; splitting them from the
  markup rewrite forces two executor sessions to re-read the same Panel.tsx region
  for redundant context.
- Test adaptations (existing tests read `data-state` from the old Checkbox → new
  tests must read `aria-checked` from the new buttons) are inextricably coupled to
  the markup rewrite — splitting would force the 2b executor to also re-do the
  markup context load.
- Total task context cost estimate: ~30% (Panel.tsx region already familiar from
  read_first, changes localized to the popover block + one anyFilterOn line + one
  useState declaration + test file adaptations to ~4 assertions). Under the ~50%
  quality-degradation threshold.
