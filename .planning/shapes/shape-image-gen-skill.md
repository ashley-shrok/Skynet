# Shape: image-gen skill

**Opened:** 2026-09-17
**Vehicle:** GSD phase

## What this is

A capability every agent running inside our managed chat surface can invoke to turn a prompt into an image. Today those agents have no native way to generate images because the harness they run in does not ship one; this fills that gap. The image itself is generated by a paid provider — the same one that already produces avatars on the operator side — and the load-bearing constraint is that the credential unlocking that provider must never sit anywhere an agent, or a human on the same machine as an agent, can reach.

## Shape

Two pieces coupled by a shared file protocol.

**The caller side** is an on-demand-loaded skill that ships to every managed host through the existing fleet distribution mechanism. When an agent invokes it, the skill writes a request file into an agreed folder on the local box, waits for the response to appear as a sibling file in the same folder, and hands the caller back either a path to the resulting image on success or a structured failure description.

**The backend side** is a scanner running on the central chat-surface instance that already coordinates every managed box. The backend already sweeps each host on a short tick for one kind of request folder (identity-birth); it grows a second sweep for this one. When a request file appears, the backend claims it atomically, calls the configured image-generation provider with the prompt and parameters, and writes the resulting image plus a small companion metadata file back into the same folder. On failure it writes a structured failure file with a categorized reason.

The request describes what the caller wants. The prompt is required; size, aspect ratio, number of images, a reference image (for editing rather than pure generation), and any other parameter the current provider natively supports are optional pass-throughs, with sensible defaults when absent.

The response on success is an image file plus a small metadata file next to it. On failure it is a single failure file carrying a categorized reason and, where useful, a short human-readable message. The failure categories mirror the pattern already used for identity-birth: a small closed set the caller can branch on — rephrase, retry-after-delay, escalate-to-operator, malformed-request, and everything-else.

There is no per-caller authentication and no per-caller metering. Any agent on any managed host can generate images at whatever pace it wants; the cost lands on the operator's provider account. The trust boundary is the filesystem — the fact that a request file appeared inside the agreed folder on a managed host's disk is the whole authorization signal.

## Philosophy

The generator's credential lives only where the backend is, and never anywhere else. Agents get the capability; humans and agents on the box never get the key. When this is deployed at a company, employees whose agents can generate images should not be able to walk off with the provider key and use it for their own purposes — that is the reason the whole design exists.

The skill is a thin caller with no cleverness of its own. It does not know or care which provider is behind the backend, does not do post-processing, does not enforce style or aesthetic. Anything provider-specific lives on the backend; anything caller-specific lives in the caller's own instructions. This means later swapping the provider, or offering different providers on different instances, requires zero change to callers.

The design intentionally reuses the file-drop broker pattern that already carries other host-to-backend coordination. It does not open new network endpoints, does not introduce a new authentication story, and does not need a new proxy layer. Every additional attack surface is another place the credential story can be circumvented; every new pattern is one more thing operators have to understand and one more failure mode to debug.

The skill body carries a first-class instruction about compliance-sensitive content. It does not attempt to route those cases to a different provider under a compliance boundary; that is deferred to a later version. Instead, it tells the invoking agent — in the freshly loaded skill body — that any prompt it composes will be sent to a third-party provider, and to treat prompt construction accordingly (paraphrase scenes rather than include identifiers, and so on). Freshly-loaded skill instructions are the strongest place to put this constraint; stronger than a persistent directive that drifts with context.

## Prior context

The operator-side image generation already exists. The box maintainer's avatar pipeline uses a provider to create fleet member portraits, and the credential for that provider is already configured in the backend. The mechanism this shape describes shares no code and no aesthetic with that avatar pipeline: it is a generic image-generation capability, not an avatar-flavored one, and no post-processing or style bias is applied on top.

The file-drop broker pattern already exists for identity-birth. The backend already sweeps a per-host request folder on a short tick, claims files atomically, does work, and writes categorized success or failure files back. Agents on managed hosts already understand this pattern; adding image generation as a second consumer of the same broker style extends a known mechanism rather than inventing a new one.

The current state from an agent's perspective is that there is no image generation, and the only workaround is asking a human operator to run the avatar pipeline manually — which the pipeline was never built for and which does not scale to enterprise deployments where agents belong to arbitrary users rather than a single operator.

## What would make it wrong

If the provider's credential ever ends up on a managed host — in a file, an environment variable, a process memory dump, or anywhere else a person with a shell on that host could reach — this feature has missed its point, regardless of whether it works otherwise.

If an agent's ability to generate an image depends on knowing anything about the provider currently in use — its API shape, its parameter names, its authentication story — the abstraction has leaked and the skill has become brittle to provider swaps.

If the failure story reduces to a single "generation failed" bucket with no discrimination between transient causes (retry helps) and permanent ones (retry never helps), agents will retry things that will never succeed, or give up on things that would have succeeded on the next try.

If the caller-facing surface silently ignores parameters the caller specified — because they were misspelled, or do not map to the current provider — the caller gets an image that is not what it asked for and no way to notice. Better to reject the request explicitly than to fulfil it wrong.

If the skill body's compliance-sensitive-content guidance is buried, hedged, or phrased as generic policy rather than as a practical instruction to think about prompt construction, invoking agents will not act on it consistently.

## Scope edges

**In.** The skill body, distributed to every managed host through the existing fleet distribution mechanism. The backend scanner. The backend adapter to the currently configured provider — only one provider needs to be wired up for this version, and it is the same provider already used for avatar generation. The wire protocol between the two sides, including the failure taxonomy. A catalog entry in the fleet distributor so the skill actually reaches every host on the next sweep.

**Out.** A second provider path for compliance-restricted deployments. Per-user or per-agent attribution, metering, or rate-limiting on the backend side. Any post-processing of the image on the skill side (gamma correction, style application, watermarking). Any avatar-specific behavior — this shape is generic image generation only.

**Deferred.** Multiple simultaneous providers configurable per host. Cross-provider abstraction of parameters — this version passes parameters through natively to the one wired-up provider and documents which parameters exist. Long-running generation with a job-handle async pattern; this version is synchronous polling with a generous safety timeout.

**Tempting but no.** Adding avatar-generation as a preset in this skill. The avatar pipeline is a separate, operator-facing tool with its own aesthetic and post-processing; letting it leak into a generic capability every agent in the fleet can invoke would violate the separation between "the operator runs this for fleet-member avatars" and "any agent runs this for whatever image it needs." Similarly tempting: exposing an admin surface on the backend to reconfigure the provider on-the-fly; the configuration surface should stay backend-owned and this version keeps the provider fixed at what the instance ships with.

## Vehicle notes

**Vehicle:** one GSD phase.

The work has three pieces (backend scanner plus provider adapter plus response mechanism; skill body plus distributor catalog entry; documentation and the failure-taxonomy contract) that only make sense shipped together. Shipping the backend without the skill leaves callers with nothing to invoke; shipping the skill without the backend gives callers a skill that hangs on every call. Both sides define a wire protocol together, so they need to be planned as one unit.

The identity performing the work is the box-maintainer role's current session on this machine. The repository the work lands in is the fleet's central chat-surface codebase. The identity's working tree is already prepared and on the fleet's shared branch.

The phase should be slotted into the current roadmap through the standard mechanism — it is not a hot fix that bypasses the roadmap. Once slotted, the phase proceeds through discuss and plan without a stop-and-ask break between them, per the standing rule that the vehicle-pick already carries the "yes, start" decision.
